# Argued surviving mutants.
#
# A surviving mutant means a test executed the line without constraining it —
# `testing.md` rule 15 calls that the characteristic failure of generated tests,
# and rule 17 says such a mutant is killed or argued.
#
# ⚠️ **Killing is the default.** An entry here is a claim that the mutation
# produces behaviour genuinely indistinguishable from the original, not that
# writing the test was inconvenient.
#
# ⚠️ **This is a list nobody grows quietly.** It is reviewed at every milestone
# boundary, the same discipline `baselines/review.txt` and `baselines/unsafe.txt`
# carry, and a baseline that only grows means the tests are losing.
#
# Format: <file>:<line>:<col>: <mutation>  <reason>
#
# ⚠️ The reason is required. A location on its own suppresses a survivor while
# recording nothing about why.
#
# Empty as of `M0.17`: the first full run over `oqueue-core` found 11 survivors
# and all 11 were killed by writing tests rather than argued here. That is the
# ratio to keep.
crates/oqueue-core/src/bundle.rs:50:9: replace RegionAlg::code -> u8 with 0  RegionAlg has one variant, None, whose code *is* 0 -- so returning 0 unconditionally and returning `self as u8` compute the same byte, and no test can separate them. `M8` adds the second variant (doc 10 #40 puts the field in the footer from M3.13 precisely so it can), and this entry comes out then rather than being re-argued: the mutant becomes killable the moment a second code exists, and `from_code` already refuses every value this build does not know.
bin/oqueue/src/serve.rs:38:5: replace serve with ()  `serve` binds a listener and `accept_loop` races it against the coordinator's task; both run until the process is killed, so no in-process test can call either and return. ⚠️ **These mutants are killed, by a gate `cargo mutants` cannot run**: `scripts/kafka-client-harness.sh` starts the real binary, fails within ten seconds if it never prints `listening on`, and then round-trips librdkafka and the Java client through it -- so a `serve` that did nothing, or an `accept_loop` that returned `Ok(())` at once, fails there. These entries record that the coverage exists elsewhere, not that the lines are unconstrained. Every decision either function makes that *can* be tested has been lifted out beside it -- `store_for`, `durability_warning`, `build_cluster`'s composition, `advertised_identity`, `SERVE_LIMITS` -- and each has a test; what is left is the loop.
bin/oqueue/src/serve.rs:128:5: replace spawn_connection with ()  `M4.18` split the per-connection spawn out of `accept_loop` so the TLS handshake happens on the connection's own task rather than in the accept loop. It has the same shape as `serve` above and the same coverage: it spawns and returns, so no in-process test can observe it, and `scripts/kafka-client-harness.sh` is what kills it — six legs round-trip real librdkafka and Java clients through this function on every run, one of them over TLS, so a `spawn_connection` that did nothing fails all of them. ⚠️ `accept_loop`'s own entry was dropped here rather than renumbered: it is killed now by `the_accept_loop_notices_a_dead_coordinator_rather_than_serving_past_it`, and a baseline line for a mutant that no longer survives is a suppression nobody needs.
crates/oqueue-core/src/group_state.rs:113:9: replace MemberEpoch::get -> i32 with 0  MemberEpoch has no constructor beyond INITIAL (0) in this task's own scope -- M4.1 builds the type ADR-0033 asks for, but the first thing that ever advances a member's own epoch is M4.9's Heartbeat handler, which does not exist yet. Every value this build can construct is 0, so returning 0 unconditionally and returning `self.0` compute the same answer, and no test can separate them. This entry comes out the moment a second constructor exists (M4.7/M4.9), the same shape bundle.rs's RegionAlg::code entry above already uses for an identical one-variant-so-far situation.
crates/oqueue-broker/src/sync_group/barrier.rs:233:26: replace > with >= in SyncGroups::refuse  The two differ only when the cell already holds a refusal for *this* generation: `>` rewrites it with an identical `Assignment { generation, map: None }` and notifies again, `>=` returns early. No observer can tell. A follower arriving after the first refusal reads `Known::Refused` without parking, so it needs no wake; one parked before it was already woken by the first refusal, and `Notify::notify_waiters` wakes only waiters registered at the time — a second call with none registered is a no-op. Its neighbours are all killed: `==` and `<` on the same comparison, and `||` to `&&` between the two disjuncts. ⚠️ **Not respectively** — an earlier version of this entry mapped each to one named test, and review measured that `||` to `&&` reddens `a_late_refusal_does_not_reopen_a_later_generations_refusal`, `a_refusal_does_not_overwrite_a_later_generations_assignment` and `a_refusal_does_not_unpublish_this_generations_own_assignment` together rather than one of them; that enumeration also still described the pre-fix guard, which had a bare `map.is_some()` disjunct this one does not. What survives is the one comparison with no behavioural difference, not an unguarded branch. ⚠️ `check-mutants.sh` matches by location prefix only, so the prose half of an entry is checked by nothing — the same undetectable staleness the re-keying note below warns about, one field over. ⚠️ This entry comes out if `refuse` ever carries a payload that differs between calls — a reason string, a timestamp — because then rewriting and not rewriting stop being the same write. ⚠️ **This entry has been re-keyed four times inside one task** — `sync_group.rs:258:43`, then `:264:26` when the guard gained a conjunct, then `barrier.rs:224:26` when the file split at `code-structure.md`'s 500-line limit, then `:233:26` because the last review round asked for a nine-line doc comment nine lines above it. The fourth is the clearest: a comment that touched no code moved a suppression's key, and nothing but the mutant's own survival would have said so. That is `M4.32`'s own subject made concrete: `check-mutants.sh` matches survivors against this list by location prefix and never the converse, so a stale key suppresses nothing and no gate can see that it has gone dead — the only reason all three were caught is that the mutant kept *surviving*, which made the mismatch visible as a failure. An entry whose mutant became killable would have gone quiet instead. `M4.43`.
