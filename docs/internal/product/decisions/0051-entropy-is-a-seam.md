# 0051. A fresh DEK's randomness comes through a seam, not from the OS

Status: accepted
Date: 2026-09-20
Requirements: NFR-33, NFR-51, FR-43

⚠️ **Taken without the user's answer, and saying so**, as `ADR-0049` and
`ADR-0050` were. It adds a `pub trait` to `oqueue-crypto` and a direct
dependency on `getrandom`, both of which are expensive to reverse once a
composition root and two caches are written against them. The user can
override it before the KMS providers land.

Amends nothing in [`ADR-0050`](0050-envelope-encryption-and-what-m8-verifies.md);
it answers a question that ADR left implicit. Point 1 there says *"the DEK is
generated by `oqueue-crypto`"* and point 2 says nonces are **constructed,
never random** — so the crate needs exactly one source of randomness, for
exactly one purpose, and the shape of that source is what is settled here.

## Context

`M8.5` builds the write-side DEK cache. Rotating a DEK means minting 32 bytes
of AES-256 key material, and the obvious way to get them is to call the
operating system's CSPRNG where they are needed.

That collides with three things at once:

- **Non-negotiable 5.** A read of the kernel's random pool is I/O: a syscall,
  in a library crate, outside any seam that exists to hold one.
  `check-sans-io.sh` does not grep for it today, which makes this a rule the
  gate would not have caught — the argument has to hold on its own.
- **Testability.** The cache's rotation logic *is* `NFR-33`. Asserting it
  means asserting which DEK the cache holds after a rotation, and a test cannot
  name a key the kernel chose. The clock seam exists for the identical reason
  and `ADR-0004` already made this argument for time.
- **`ADR-0050` point 2.** A random nonce is the one catastrophic mistake this
  milestone is built to make unwritable. Anything that puts a general source of
  random bytes in `oqueue-crypto`'s scope is a step back toward it.

## Decision

1. **`oqueue_crypto::Entropy` is a seam, and library logic never calls the OS
   RNG directly.** Same shape as `Clock`: a `pub trait`, a real implementation,
   and a fake beside it (`contracts.md` rule 9) so a downstream crate can test
   key-dependent logic without a testkit dependency.

2. **The seam is "fill these 32 bytes", not "give me a DEK".** ⚠️ **The narrow
   spelling is the point.** `fn fill(&self, out: &mut [u8; DEK_BYTES]) ->
   Result<()>` can serve exactly one caller — `mint_dek`, which wraps the bytes
   in a `Dek` and zeroizes the scratch buffer. The alternatives were both
   worse:
   - *"Give me `n` random bytes"* is a general randomness API in the crate that
     writes nonces. A future author needing twelve bytes would find it, and
     `ADR-0050` point 2 would be undone by an API that looked helpful.
   - *"Give me a `Dek`"* (`DekSource`) reads better but puts key construction
     behind the seam, so a fake could return a key that is not `DEK_BYTES`
     long, or one that is not zeroized on drop. Keeping construction on this
     side of the seam means every implementor, real or fake, is held to the
     same `Dek`.

3. **`OsEntropy` is the only caller of `getrandom`, and a composition root is
   the only place that constructs one.** A function taking `&dyn Entropy` is
   testable and a function that builds an `OsEntropy` is not, so the type is
   named in the crate and built in `bin/oqueue` or in a broker assembling its
   write path. ⚠️ **`getrandom` rather than `rand`**: `rand` is a PRNG
   framework with a distribution API and a thread-local generator, all of which
   is reachable once the dependency exists. What is wanted is the platform call
   — `getrandom(2)`, `arc4random_buf`, `ProcessPrng` — and nothing that could
   be reached for to make a nonce. No build script, no host tool, and already
   in `Cargo.lock` transitively, so `build.md` rules 3 and 4 are untouched.

   ⚠️ **What this costs is a claim the crate could previously make.**
   `oqueue-crypto`'s README said no random source was in scope at all. That is
   no longer true, and the README now says so: what keeps nonces constructed is
   `oqueue_core::Nonce` having no constructor from raw bytes, plus this seam
   being 32 bytes wide with one caller — not the absence of a dependency.

4. **`FakeEntropy` is a counter and is loudly not entropy.** It returns the
   call ordinal in the first eight bytes and a fixed filler in the rest, so a
   test can name the exact DEK the cache should be holding — which is how
   `rotation_replaces_the_live_dek` observes a retirement without reading
   freed memory. ⚠️ Its own documentation says constructing one outside a test
   writes guessable DEKs into object storage, the same warning
   `FakeKeyProvider` carries for the same reason. Nothing enforces that; it is
   a review question, as `WrappedKey::new`'s is.

5. **`Error::EntropyUnavailable` is `RetryClass::Never`.** A source that will
   not answer is refused, never degraded to weaker bytes: a DEK from a
   predictable source is one an attacker reconstructs without the KEK, and it
   would be written into object storage looking exactly like a good one — the
   silent, durable compromise `ADR-0006` refuses at the wrap seam.

   ⚠️ **The counter-argument, recorded rather than dismissed**: `getrandom` can
   legitimately fail *transiently*, before the kernel pool is initialised, and
   on that reading `Transient` is the honest class. It is rejected because the
   window is boot, not steady state — a broker that has accepted a connection
   is long past it — so a refusal on a running node means something is wrong
   with the host, and an automatic backoff would turn a loud failure into a
   slow one while the produce it is hiding must be refused anyway. ⚠️ If a
   platform is ever found where this fires in steady state, the class is the
   thing to revisit, not the refusal.

6. **`M13`'s FIPS build must route DEK generation to the approved DRBG.** This
   is the one place where `ADR-0050` point 7's *"the algorithm is a format, not
   a library"* does **not** fully apply: a nonce and a tag are bytes in the
   object and a DEK's *origin* is not, so nothing in the format constrains it
   and nothing in a cross-build read would notice a non-approved source. FIPS
   does constrain it. ⚠️ So `M13` adds an `Entropy` implementation over
   `aws-lc-rs`'s validated DRBG and wires it at the composition root — a
   different implementation of this trait, changing no bytes on either side.
   `M13.md` task 5 owns it. That the swap is a composition-root change rather
   than an edit inside the cache is the property this seam buys for FIPS.

## Consequences

- `oqueue-crypto` gains a `pub trait` and therefore this record
  (non-negotiable 6). There is one implementation pair today; the FIPS one is
  the second and is already named above rather than discovered later.
- A composition root that forgets to pass `OsEntropy` cannot silently fall back
  — there is no default — but it *can* pass `FakeEntropy`, which compiles. That
  is the same exposure `FakeKeyProvider` and `WrappedKey::new` already carry,
  and it is held by review rather than by the compiler.
- `check-sans-io.sh` still does not grep for an OS RNG call. A later milestone
  wanting this rule enforced rather than argued would add the pattern there;
  until then a direct `getrandom` call in a library crate is caught by review
  alone, and saying so is the same discipline as non-negotiable 3.
