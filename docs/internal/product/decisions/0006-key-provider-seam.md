# 0006. The `KeyProvider` seam

Status: accepted
Date: 2026-08-16
Requirements: NFR-51, FR-44

## Context

BYOK is configured per topic. Server-side encryption cannot express that — one
object carries many tenants' data and can carry only one SSE-KMS key — so
encryption is broker-side envelope encryption, and a seam is needed over the KMS
that holds the key-encryption key.

The seam has to work against AWS KMS and GCP Cloud KMS, and it must not let key
material reach a log (FR-44) or appear outside itself (NFR-51).

## Decision

Two methods, shaped as ADR-0002 decided:

```rust
pub trait KeyProvider: Send + Sync + fmt::Debug {
    fn wrap<'a>(&'a self, key_id: &'a KeyId, plaintext: &'a Redacted<Vec<u8>>)
        -> BoxFuture<'a, Result<WrappedKey>>;
    fn unwrap<'a>(&'a self, key_id: &'a KeyId, wrapped: &'a WrappedKey)
        -> BoxFuture<'a, Result<Redacted<Vec<u8>>>>;
}
```

⚠️ **Wrap and unwrap only. Deliberately no `generate_data_key`.** AWS KMS offers
one call that generates a DEK and returns it both plaintext and wrapped; **GCP
Cloud KMS has no equivalent** (doc 22 §4). A seam carrying it would be a seam
only one cloud can implement, and the portability this project promises would be
a wrapper faking the operation on GCP anyway. The DEK is generated by
`oqueue-crypto` and wrapped through here.

### What an implementor must guarantee

1. **`unwrap(wrap(k, id), id)` is `k`.**
2. ⚠️ **A `WrappedKey` produced under one `KeyId` does not unwrap under
   another.** This is what makes a cross-tenant key confusion a failure rather
   than a silent decryption with the wrong key.
3. ⚠️ **No error, log, panic message or `Debug` output it produces contains key
   material** — plaintext or wrapped. `Redacted` gives this for the types
   crossing the seam; an implementation that formats a KMS SDK error must check
   what that error carries.
4. ⚠️ **The plaintext DEK an `unwrap` returns is the caller's to zeroize.**
   `Redacted` is a formatting guarantee and does not zeroize (`security.md`
   rule 8 is "checked by review"), so the seam hands back live key material and
   the caller must not let it outlive its use. `M8` owns the zeroizing type;
   until then this is the obligation and there is no gate.
5. ⚠️ **A throttled or transient KMS failure is not `SecretRejected`.** That
   variant means *this key does not open this ciphertext*, which is permanent;
   a caller must be able to tell it from a 429. Today the enum has nowhere else
   to put one, so `M8` adds the retryable classification `error-handling.md`
   rules 7-8 require, and until then a real provider has no correct variant.
6. **`wrap` is not required to be deterministic.** A KMS may return a different
   ciphertext for the same DEK each call, and a caller must not compare wrapped
   keys for equality to decide whether two DEKs are the same.

### The unencrypted path refuses

`oqueue-crypto::NoOpKeyProvider` returns `Error::EncryptionDisabled` from both
methods.

⚠️ **It is production code, so it lives in `oqueue-crypto`, not beside the trait**
— `contracts.md` rule 9 puts *fakes* in `oqueue-core`, and this is the real
implementation of "no BYOK configured".

## Alternatives considered

**An identity no-op — return the plaintext DEK as its own wrapped form.** This
is what "no-op provider" most naturally suggests, and it is rejected. It would
make every call site succeed while writing a **plaintext data encryption key**
into object storage beside the data it protects, indistinguishable from a real
wrap. A misconfiguration would become a silent, durable compromise discovered by
whoever reads the objects. Refusing turns the same misconfiguration into an
error on the first call.

⚠️ **This reverses doc 22 §8 and `milestones/M0.md` item 6**, both of which ask
for a no-op that keeps the two paths uniform so they cannot diverge. The
reversal is deliberate: uniformity bought by a provider that writes a
plaintext DEK is uniformity around a vulnerability. The cost is real and
worth stating — the encrypted and unencrypted paths are no longer identical,
so a caller must branch.

**`generate_data_key` on the seam.** Rejected above.

**A `key_id` baked into the provider at construction** rather than passed per
call. Rejected: BYOK is *per topic*, so one broker serves many key ids at once,
and a provider per topic would put a KMS client per topic behind it.

**Returning the plaintext DEK as `Vec<u8>` rather than `Redacted<Vec<u8>>`.**
Rejected. `Redacted` is what makes FR-44 hold by construction rather than by
everyone remembering, and its cost is one `expose()` call at the point of use —
which is exactly where a reviewer should be looking anyway.

**Putting the fake in `oqueue-testkit`.** Rejected for the same reason as
ADR-0004 and ADR-0005: `contracts.md` rule 9.

## Consequences

**Easy.** `oqueue-crypto` can be written and tested with no KMS, no credentials
and no network. A cross-key-id confusion fails in a unit test.

**Hard.** Every call site handles `EncryptionDisabled`, and the branch between
encrypted and unencrypted is explicit rather than absorbed.

⚠️ **`FakeKeyProvider` performs no cryptography at all.** It prefixes the
plaintext with the key id and checks that prefix on the way back. It catches
key-id confusion and nothing else — not a weak cipher, not a reused nonce, not a
truncated ciphertext. A test passing against it says nothing about whether the
real envelope scheme is sound, and `M8` is where that is bought.

⚠️ **`Error::SecretRejected` carries a `KeyId`, not the material.** `M0.6`
created it holding the rejected bytes inside a `Redacted` — safe from formatting,
but still reading literally against FR-44 and `security.md` rule 6, both of
which say a secret must not reach an error variant *at all*. This commit
resolved that by removing the secret rather than by amending the standard, which
is the outcome that needed no exception. `security.md` rule 7's `Redacted`
carve-out stands unchanged; it is about `Debug` derivation, not about what an
error carries.

**What has no gate.** Guarantees 2 and 3 for a *real* provider. `check-secrets.sh`
is named by `security.md` rules 6-7, does not exist, and is deferred into `M8`
in `roadmap.md`'s table. Until then this is review's.
