# M7 — Metadata sharding and scale

**Kind:** non-functional ·
**Depends on:** M6, M9 ·
**Serves:** NFR-10, NFR-11, NFR-4

## Goal

The catalog reaches 1M–100M topics, up to ~1000 partitions each, with per-node
metadata cost proportional only to partitions active on that node — never to
the size of the whole cluster.

⚠️ **This milestone is where the corpus's central finding gets tested against
real numbers: the ceiling that binds first is the Kafka protocol and its
clients, not object storage.** librdkafka's per-partition fetch queues break
around ~10² partitions per consumer at default settings; the Java producer's
16 KB batch size against 32 MB buffer memory stalls around ~2,000 actively
produced partitions per producer. A Rust broker does not inherit the JVM/OS
ceilings a peer system hit at 600k partitions, but it does inherit the client
ceilings, because those live in the client.

## Depends on

**M6** — a rebalanceable shard is only revisable if failover already works,
and shard reassignment is itself a form of failover. **M9** — this milestone's
whole scale argument rests on the principal-indexed forward index M9 built;
without a principal there is nothing to index by.

## Decisions required first

None new. Doc 15 is a position paper and this milestone's job is to build to
it, not to re-decide it. Two things it settles that are easy to build against
the wrong way:

| What doc 15 already decided | Why it matters here | Background |
|---|---|---|
| Metadata shards are **internal and rebalanceable**, not client-visible Virtual Clusters | This reverses an earlier corpus recommendation (doc 14 §11.9). Building client-visible VCs here would be building the retracted design | doc 15 §3, §7 |
| Topic creation provisions **nothing** — no coordinator, no Raft group, no thread, no timer | If creating a topic provisions anything, 100M is unreachable. Existence is derived: the topic exists because an object exists at a derived key | doc 15 §2 |

## Provisional tasks

1. `MetadataShardId` + a shard-assignment function (topic → shard) written as a
   lookup, not a hash burned into a key — rebalance depends on this.
2. Shard routing table in the coordinator; `Metadata`/`FindCoordinator`
   resolution through it.
3. Shard rebalance: move a topic's routing with **no data migration and no
   client reconfiguration** — absorbed by ordinary metadata refresh. Test that
   a client survives it uneventfully.
4. Catalog store: topic entries (~100 bytes: name, UUID, config, partition
   count) disk-backed, per shard, sized toward ~500 MB/shard at 100 shards.
5. Partition entries (~40 bytes) in the same store. ⚠️ **Assert the catalog and
   the read-path index are separate structures** — conflating them makes the
   scale problem look far worse than it is.
6. Topic existence as a derived property: creation writes a prefix, a
   manifest, and a catalog row, and provisions nothing else. Test asserting
   create allocates no coordinator, task, or timer.
7. Metadata-role component boundary: its own task pool, its own memory
   ceiling, its own metric namespace. A gate asserting the data-plane hot path
   shares no mutable metadata state.
8. Node-class configuration: metadata-bearing vs. pure data plane from one
   binary. Assert a data-plane node holds zero durable state.
9. Per-shard replication and snapshot at RF 3 across metadata-bearing nodes.
10. Coordinator reconciliation watermark per partition — the boundary between
    the coordinator's hot tail and the compacted-history manifests.
11. Offline batch sweep for billing, metering, and reconciliation — a job from
    day one, never on a request path.
12. Admin-surface answer for `--list` at 100M topics: pagination, prefix
    scoping, or explicit refusal. ⚠️ Inherited from M9's deferral — the
    constraint was set there, the answer is due here.
13. KIP-951 leader hints inline in Produce/Fetch error responses. Leadership
    is cheap and mobile at this shape; clients need to be told where it went.
14. Opinionated client defaults documented: `queued.max.messages.kbytes`,
    `metadata.max.age.ms`, explicit topic lists preferred over pattern
    subscription.
15. Per-connection observable: does this client request all topics? Doc 14
    calls this the single measurement that determines whether the cluster
    scales to 10⁴ or 10⁶.
16. Scale test with a synthetic catalog, memory and metadata cost **measured,
    not extrapolated** (NFR-10), at two catalog sizes an order of magnitude
    apart (NFR-11).
17. Client-ceiling documentation: the librdkafka and Java-producer numbers
    above, published rather than discovered by a user.

17a. **A `SessionWatermark` carries its `MetadataShardId`**, and a version is
   never compared across shards. ⚠️ **Carries a deferral from `M3`**
   (`roadmap.md`'s deferred-into-a-later-milestone table, recorded by
   `M3.10`): `ADR-0020` point 1 asks two things of a watermark and `ADR-0023`
   settles one — it carries a `CoordinatorEpoch`, so a line carried across a
   *rebalance* is incomparable rather than falsely comparable. The other half
   waits for this milestone because it needs the shard identifier this
   milestone introduces. ⚠️ **It is a safety requirement, not a tidying
   pass**: `CoordinatorEpoch` is defined per *log* and a log is per shard, so
   two shards' first coordinators both sit at `CoordinatorEpoch::ZERO` — a
   watermark from shard A read against shard B's cache finds the epochs
   **equal** and falls through to a version comparison between two independent
   counters, admitting a read on a line that never saw the write. The moment a
   second shard exists this is reachable, so it lands with the sharding rather
   than after it.


17b. **A flush is refused if it would span metadata shards.** ⚠️ **Carries a
   deferral from `M3`** (`roadmap.md`'s deferred-into-a-later-milestone table,
   recorded by `M3.13`): `ADR-0020` requires that an object bundle topics
   *within one shard*, so that committing it stays a single append to one log
   rather than a non-atomic append to two — a crash between the two leaves the
   object committed for some partitions and not others. `M3.13`'s row said
   "enforced here, not assumed" and could not be: `MetadataShardId` is this
   milestone's, so `BundleBuilder` had nothing to check a topic's shard
   against. ⚠️ **The moment this milestone introduces a second shard the rule
   becomes reachable**, and the flush composer `M3.14` built has no shard
   parameter — so this lands *with* the sharding, not after it.

17c. **A parked fetch, and the requests behind it on one connection.**
   ⚠️ **Carries a deferral from `M3`** (`roadmap.md`'s table, recorded by
   `M3.25`): `MAX_PARK_MS` bounds how long one fetch parks and says nothing
   about what a *pipelined* connection sees, because a connection's requests
   are answered in order. ⚠️ **It may not be a defect at all** — Kafka's own
   broker orders responses per connection, and a client that cares uses a
   separate one — which is why it is a measurement rather than a patch: a real
   client's socket timeout and `max.in.flight` against a park held to its
   ceiling. This milestone is where that measurement is affordable, and where
   `MAX_PARK_MS`'s value stops being argued from `ConnectionLimits` alone.

17d. **A partition between an agent and the coordinator**, held past the
   bounded staleness limit. ⚠️ **Carries a deferral from `M10`**
   (`roadmap.md`'s table): `M10.md` asked for it and `M10.0` found no network
   between them to cut. M3's broker index *is* the coordinator's, folded before
   the ack by the only writer, so `Cluster::cache_state` hardcodes
   `silent_for_ms` to zero and `CacheState`'s silence breaker is unreachable —
   the same unreachability `M10.19` records for the newer-epoch check below it.
   ⚠️ **Here the follower's index is genuinely a cache**, so the limit
   `MAX_METADATA_STALENESS_MS` names becomes a thing a partition can exceed,
   and doc 12 §4.6's hazard H4 stops being asserted in prose. It lands beside
   17a's shard identity and the 404 refresh below, which are the other two
   pieces of the same follower.

⚠️ **And the index refresh a 404 is supposed to trigger** (`M3.22`). Doc 12
§4.6 asks a reader that finds an object the index named and the store does not
have to *refresh the index through a coordinator round trip* before answering
`OFFSET_OUT_OF_RANGE`. `M3.22` could not build it and said so: in a single-node
broker the index a fetch reads is the coordinator's own, and nothing removes an
entry from it, so a second read consults identical state. ⚠️ **Here it is real
work**: a follower's index *is* a cache, so its 404 may mean "my index is
behind" rather than "reaped", and answering out-of-range on the first miss
would tell a consumer that live records are gone. `IndexWatch` is the mechanism
that waits for a fold; `Cluster::read_or_refresh` is the function that has to
grow the round trip.

table, from M6's close.

every produce acknowledgement pays an object write until it lands), `M6.18`

opening commit re-derives each as an M7 row and marks the M6 row `dissolved`.

## Completion condition

```bash
scripts/gates/m7-complete.sh
```

Asserts: a synthetic catalog at 1M and at 10M topics shows per-node memory flat
against total cluster partition count (NFR-11); `Metadata` response size and

and NFR-4's produce-latency-independent-of-topic-count benchmark holds at two
topic counts an order of magnitude apart.

## Risks and open questions

- ⚠️ **The load-bearing assumption is Kafka's own `Metadata` authorization
  filtering, and M9 flagged it unverified.** If M9's ADR did not settle this
  against real Kafka source, do it before this milestone's scale test, not
  after — a wrong assumption here invalidates the whole forward-index design.
- **Median vs. max partitions per topic, and the active fraction, are
  unknown.** Doc 15 §1 refuses to guess either, and this milestone's sizing
  arithmetic depends on both.
- ⚠️ **Bootstrap and tenant routing at this scale is not researched** — you
  cannot enumerate endpoints in a load balancer, and the working hypothesis
  (shared bootstrap, tenant from SASL credentials) is untested. Doc 10 #21.
- **Consumer-group state at 100M tenants needs its own sizing**, deferred from
  M4 and still open here.
- **Topic deletion and reuse is unresolved.** Kafka clients carry topic-
  identity expectations (topic IDs, KIP-516) that complicate immediate reuse
  the way this milestone's derived-existence model would otherwise allow.
- **The one open question the corpus itself calls unresolved**: why Redpanda
  Cloud Topics chose an LSM metastore for compacted history despite already
  owning derivable manifests. It is the only evidence of a well-positioned
  team going the other way, and it deserves a look before this milestone's
  catalog design is treated as final.
