# M5 — Compaction and retention

**Kind:** functional ·
**Depends on:** M3, M10 ·
**Serves:** FR-33, FR-34, FR-35

## Goal

Historical reads stay bounded in cost, data ages out on schedule including on
partitions nobody is writing to, and an object is deleted only when no reader
can still reference it.

⚠️ **Compaction here is a metadata mechanism as much as an I/O one**, and that
is the part usually underestimated. At ~40 bytes per index entry and the
modelled rate the index grows ~14 GB/day and ~97 GB over a 7-day retention,
which does not fit in an agent's memory. Object *count* is a coordinator cost;
object *bytes* are a cloud-bill cost, and they want different mechanisms.

## Depends on

**M3** for the index compaction rewrites, **M10** because FR-35's acceptance
criterion is an invariant test on a race — a stale reader against a deleter —
and that is not testable by hand.

## Decisions required first

| Decision | Open question | Background |
|---|---|---|
| Compaction cadence at high partition counts | **#18** | Manifest PUT cost is linear in partitions × cadence and **fixed regardless of throughput**: at 100k partitions, a 60 s cadence is roughly $720/day against ~$24/day at 30 minutes. Interacts with M6's snapshot cadence |
| Retention on idle partitions | **#22** | Time-driven retention must fire on partitions nobody writes to — a per-partition cost. Candidates are lazy evaluation on next access or folding into a daily sweep; ⚠️ **neither is worked through** |
| `max_metadata_staleness` | **#11** | ⚠️ Set in M3, consumed here: it is the floor for `deletion_delay`, so the safety inequality cannot be parameterized until it has a value |

## Provisional tasks

1. `read_amp(partition, range)` computed from the index — the trigger input.
   ⚠️ **Never trigger on object count.**
2. Planner: select where read amplification exceeds a threshold (start at 8–16)
   **and** the range is older than the latency SLO, so tail data still served
   from cache is never rewritten.
3. Per-plan cost estimate and budget gate; refuse or defer plans over budget.
4. Streaming merge executor: exactly one additional GET per input regardless of
   its size, bounded memory, no random seeks.
5. Output layout regrouped by topic then partition into contiguous ranges, so
   one partition-fetch becomes one ranged GET.
6. Multipart output writer at the part size the cost model is built on.
7. Server-side range copy for whole-range moves — PUT-class cost, zero egress.
   ⚠️ Does not apply to every compaction type; do not budget zero egress for all.
   ⚠️ **Carries a deferral from `M1.18`** (ADR-0015; `roadmap.md`'s
   deferred-into-a-later-milestone table): `object_store` exposes server-side
   range copy for neither S3 (`UploadPartCopy` support is `pub(crate)`-only
   and whole-object-only even internally) nor GCS (`compose` does not exist
   in the crate at all — tracked upstream as
   `apache/arrow-rs-object-store#121`, open since 2023-10-20). This task
   inherits the actual decision: hand-roll signed requests now that a real
   caller and cost model exist, depend on `object_store` if #121 has closed
   by then, or accept a client-side copy for whichever compaction types this
   task's own warning above already says zero-egress does not have to cover.
8. **Composite objects**: an object holding pointers to live components and a
   copy of their index entries, collapsing N objects into one from the
   coordinator's view with zero data movement. The reference system bolted this
   on at 90% of an object-count ceiling; **build it from the start**.
9. **Range-coverage check before every commit** — verify every input offset
   range is covered by the outputs. Cheap insurance on the one operation that
   can silently lose data.
10. Atomic commit at the coordinator: one transaction swapping input refs for
    output refs. ⚠️ Compaction must never affect correctness, only efficiency.
11. `compaction_epoch` on `ObjectRef`. An older-epoch cached ref stays **valid**
    through the delay window — degradation, not a cliff.
12. Compaction-job claiming by CAS on object storage. ⚠️ A legitimate
    low-frequency control-plane use; explicitly not the offset stream.
13. Time-based retention driven from `ts_min`/`ts_max` in the index, so the
    decision needs no object-storage access.
14. Size-based retention: per-partition byte budget, oldest first, reconciled
    with time retention — the tighter wins.
15. **Retention on idle partitions**, per the ADR above (FR-33).
16. `trim(new_start_offset)` as the only partition-level retention primitive —
    advancing the logical start is metadata-only.
17. Object liveness: deletable only when **every** partition slice inside it is
    dead. ⚠️ Otherwise one slow-expiring partition pins a whole object
    indefinitely, which is what makes repacking a *retention* requirement.
18. Three-state lifecycle — live → logically deleted → deletion queue — with a
    TTL sweep, idempotent commit, and a per-round batch cap **plus
    backpressure**. An uncapped queue that grows once creation outruns deletion
    is a documented pathology in a peer system.
19. **The GC safety inequality**, in code and as an invariant test:
    `deletion_delay > max_metadata_staleness + max_in_flight_fetch_duration +
    clock_skew`, with its three enablers — non-reusable object IDs, an explicit
    **bounded** staleness that stops cache serving when exceeded, and
    404 ⇒ refresh ⇒ retry.
20. Orphan reconciliation: a daily mark-and-sweep driven by a storage inventory
    rather than by paginated listing. ⚠️ **The one legitimate use of listing.**

## Completion condition

```bash
scripts/gates/m5-complete.sh
```

Asserts: read amplification after compaction is within bound (FR-34); an idle
partition's data is deleted on schedule with no write to trigger it (FR-33); and
the GC safety inequality holds as an invariant test under M10's simulation, with
a stale reader racing a deleter (FR-35).

## Risks and open questions

- ⚠️ **Compaction does not always pay**, and the plan must not assume it does.
  Three named cases where it does not: pure tail consumption served from cache,
  retention shorter than one compaction interval, and data already contiguous.
- ⚠️ **A nonzero 404-on-read rate means the deletion delay is too short.** It
  must be a metric, not a swallowed retry. This is the single loudest signal
  that the inequality is mis-parameterized.
- **The break-even model and the 8–16 threshold are synthesis, not measurement.**
  Treat them as starting defaults that M14 replaces with numbers.
- **Lifecycle-policy expiry cannot deliver sub-day retention precision** —
  daily evaluation then queued asynchronous deletion. Anything with an SLA is
  application-driven deletion.
- ⚠️ **BYOK breaks compaction planning, and M8 depends on this being handled.**
  Compaction must plan **within a key domain**, workers need unwrap capability
  for every topic they touch, and a revoked KEK blocks compaction of that
  topic's data — which needs a defined behaviour rather than a stuck queue.
  Doc 10 #39, #37 (encryption). M5 must not close without either that path or an explicit,
  recorded deferral into M8.
- **Deferred:** key-based log compaction (two sequential passes per input) and
  Express→Standard tiering, if #7 resolves that way.
