# M8 — Encryption: BYOK and the FIPS build

**Kind:** feature ·
**Depends on:** M1, M5, M9 ·
**Serves:** FR-41, FR-42, FR-43, NFR-14, NFR-33

## Goal

Customer-supplied keys, portable across AWS and GCP KMS, configured per topic;
a separate FIPS 140-3 build; and neither degrades the default unencrypted path.

⚠️ **~10,000 BYOK topics out of 1M–100M is the number that decided this whole
design**, and it is worth restating rather than re-deriving: BYOK is rare, so
its data is segregated into its own objects by key domain rather than
complicating the object format for the >99% default path.

## Depends on

**M1**, whose region header carries the `alg` field this milestone finally
uses. **M5**, because compaction must re-seal within a key domain and this
milestone cannot close if that path was deferred rather than built. **M9**,
because `oqueue-crypto` sits in the same trust boundary as authentication and
the FIPS TLS backend is shared with it.

## Decisions required first

None new — doc 22 is a position paper, and the decisions below are already
made. Building against a *different* shape here needs an ADR that overturns
doc 22, not a quiet deviation.

| Already decided | Why it is easy to get wrong anyway | Background |
|---|---|---|
| Segregate by key domain, not per-region sealing on every object | The rejected alternative (seal every region everywhere) pays format complexity on 100% of traffic to serve <1% of it | doc 22 §2 |
| The seam is **wrap/unwrap**, not generate-data-key | GCP Cloud KMS has no `GenerateDataKey` equivalent. The trait is the *intersection* of AWS and GCP, not the union — using `GenerateDataKey` would produce an abstraction that leaks | doc 22 §4 |
| KMS is on the rotation path, never the per-batch path | Without caching, thousands of KMS ops/sec against a ~5,500/sec quota throttles at modest load, not at the target | doc 22 §5 |

## Provisional tasks

1. `KeyProvider` trait + `KeyId`, `Dek`, `WrappedDek`, `KeyError` in
   `oqueue-core`. `Debug` redacted by construction on the last two.
2. No-op `KeyProvider` + in-memory fake + static-key implementation in
   `oqueue-testkit` — present so the encrypted and unencrypted paths never
   diverge in what is tested.
3. `oqueue-crypto` crate: `#![forbid(unsafe_code)]`, no I/O, layering gate
   asserting it depends only on `oqueue-core`.
4. AEAD wrapper selecting its algorithm **at runtime from the region header**
   — the field M1 wrote and has carried as `none` ever since.
5. ⚠️ **Nonce construction as a type**, not a convention: writer epoch ‖
   object sequence ‖ region index, with no constructor able to produce a
   duplicate. Property test: no reuse reachable under any call sequence. This
   is the single highest-severity thing in this milestone to get wrong.
6. Zeroize-on-drop for `Dek`; a gate asserting key material cannot reach
   `Debug`, logs, spans, metric labels, or error variants.
7. Envelope seal/open for one region, producing `{key_id, wrapped_dek, nonce,
   alg}` in the footer.
8. DEK cache: one DEK per topic, rotated on **whichever comes first — a time
   bound or a bytes-encrypted bound**, both constants rather than settings.
9. Read-side unwrapped-DEK cache with a TTL, keyed by wrapped-blob identity.
10. AWS KMS `KeyProvider`: `Encrypt`/`Decrypt`, never `GenerateDataKey`.
11. GCP Cloud KMS `KeyProvider` — same seam, round-trip test proving the
    portability the trait shape exists for (FR-41).
12. Per-topic KEK reference in topic metadata, and the hierarchy: many topics
    may share a KEK, each still gets its own DEK.
13. Flush-planner key-domain routing: a topic with a KEK goes to a BYOK
    object, everything else to the default path. Test: no object contains
    regions from two key domains (FR-42).
14. Longer flush interval for BYOK topics, documented as the customer's trade
    to make — BYOK batches only within a key domain.
15. Compaction re-seal within a key domain preserving topic→key association,
    with a **defined** behaviour for a revoked KEK — never a stuck queue.
16. `fips` cargo feature flipping to `aws-lc-rs` FIPS + rustls `fips`; DEK
    generation routed to the approved DRBG.
17. `fips_mode_enabled()` runtime assertion, and a gate that checks it rather
    than the build feature flag.
18. FIPS↔non-FIPS differential test proving both read each other's data
    (FR-43) — the property the region header's `alg` field existed to buy.

## Completion condition

```bash
scripts/gates/m8-complete.sh
```

Asserts: a round trip against both AWS KMS and GCP Cloud KMS through the same
seam (FR-41); no object contains regions from two key domains (FR-42); a FIPS
build asserts `fips_mode_enabled()` at runtime and a differential test proves
FIPS and non-FIPS builds read each other's data (FR-43); default-path object
format and cost are unchanged when BYOK topics exist (NFR-14); and KMS call
count is a function of DEK rotation, never of produce volume (NFR-33).

## Risks and open questions

- **Key rotation semantics are undecided**: re-wrap eagerly, during
  compaction, or never. Decides how long old KEK versions must be retained.
- **Revocation behaviour is undefined.** Fail fetches with a specific error,
  stall compaction, or tombstone — must be defined before anyone relies on
  revocation, and M5's plan already made this M8's obligation to close.
- **DEK rotation constants have no value.** Derive them from the security
  argument — how much data may share one key — not from the KMS quota, which
  is not the binding constraint at this volume.
- **Segregation cost to a small BYOK customer is unquantified**: at what
  volume does the smaller-object penalty dominate, and is a longer flush
  interval adequate compensation?
- **Whether one-key-per-topic should be offered** is a product decision with a
  support cost, not a technical one; headroom exists at 10,000 topics.
- ⚠️ **KMS becomes a read-path dependency for cold BYOK data** once a DEK ages
  out of cache. A KMS outage degrades reads for BYOK topics specifically — this
  is inherent to BYOK, not a bug, but it must be monitored and reflected in the
  SLO rather than discovered in an incident.
