# M6 — Recovery and failover

**Kind:** non-functional ·
**Depends on:** M3, M10 ·
**Serves:** FR-51, NFR-20, NFR-22, NFR-44

## Goal

Losing a node costs time, never data. A coordinator restarts from a snapshot
plus a bounded replay tail, a standby is promoted rather than rebuilt, and a
data-plane node comes up clean with an empty disk and serves correctly.

⚠️ **This is a `non-functional` milestone, and it cannot be completed by writing
code.** Its completion condition names measurements. Until the failover timings
run, the milestone is not done however finished the implementation looks.

## Depends on

**M3** for the coordinator and its log, **M10** because the failure modes worth
designing against are reachable only under injected faults. ⚠️ **Not
"partitions"**, which this line said until `M10.34`: `M10` defers network
partitioning to `M7` (`roadmap.md`'s deferral table, `ADR-0028`'s `turmoil`
note), which this milestone does not depend on — a network-partition leg
below needs that dependency added, or its own mechanism, before it can be
more than prose.

## Provisional tasks

1. `SnapshotCommitted{end_offset, epoch, object_key}` as a record **in the
   metadata log**. ⚠️ This is what eliminates enumeration structurally — the
   pointer *is* a log position, so it cannot disagree with what it describes.
2. Reachability invariant enforced before advancing `log_start_offset`.
3. Non-blocking point-in-time snapshot via read-transaction MVCC — no
   state-machine pause, no `fork()`.
4. Write-to-temp-then-commit-the-record, with distinct in-progress, complete and
   tombstoned naming so a torn artifact is identifiable by name alone.
5. Snapshot GC and log pruning below the newest snapshot. **Cleanup defaults on.**
6. Cadence triggered on **accumulated journal bytes, not wall clock** — otherwise
   recovery time is load-dependent and worst exactly when the system is busiest.
7. Scheduled on **completion plus a minimum pause**, not a fixed period, to
   avoid continuous-checkpointing lock-up.
7a. **A durable `MetadataLog`**, and the engine benchmark doc 13 §6 asks for.
   ⚠️ **Carries a deferral from `M3`** (`roadmap.md`'s
   deferred-into-a-later-milestone table, recorded by `M3.19`): `ADR-0020`
   point 5 left doc 10 #12 open on purpose, and M3 shipped with
   `FakeMetadataLog` as the only implementation — so M3's coordinator is
   durable in object storage and **not in its own log**, and a restart
   re-bases every partition at `Offset::ZERO` over objects that already hold
   those offsets. ⚠️ **Nothing in M3 can be made to survive a restart before
   this lands**, which is why tasks 8 and 9 below are not merely faster with
   it: they have nothing to read without it. Fork `redb-bench` per doc 13 §6,
   run our ~40-byte layout and the `insert_sorted` sequential-apply number,
   choose with an ADR, and hold the result to `MetadataLog`'s five documented
   guarantees — guarantee 1 (durability) becomes checkable here for the first
   time, which `metadata_log.rs` already says in as many words.

7b. **Group commit: `CoordinatorLoop::run` drains N queued requests into one
   `append`.** ⚠️ **Carries a deferral from `M3`** (`roadmap.md`'s
   deferred-into-a-later-milestone table, recorded by `M3.25`): `MetadataLog`'s
   `append` already takes a slice, and without the drain a durable engine at
   single-digit-millisecond commits turns `COMMIT_QUEUE_DEPTH` into seconds of
   queueing against NFR-1's 500 ms p99. ⚠️ **The number that argument rests on
   does not exist until 7a lands** — `FakeMetadataLog`'s `append` is in-memory,
   so in M3 the drain would have optimized against nothing measurable, which is
   the same objection `ADR-0020` point 5 raised against picking the engine
   itself. It lands *after* 7a and is measured against the engine 7a chooses.

8. Cold start: read log → newest `SnapshotCommitted` → **one GET** → replay
   forward. Zero enumeration.
9. Warm restart: replay only `committed − applied_upto`.
9a. **The same snapshot, offered to a *follower*.** ⚠️ **Carries a deferral
   from `M3`** (`roadmap.md`'s deferred-into-a-later-milestone table, recorded
   by `M3.9`): `M3.9` built doc 12 §4.4's delta half — a push subscription, and
   a follower that re-bootstraps by paging the log — and not its snapshot half,
   *"fetch a compacted index snapshot at version V, then subscribe from V"*,
   which that section introduces to avoid *"a thundering herd of full-index
   queries on rolling restarts"*. Until this lands, N agents restarting
   together produce N full metadata-log replays. It belongs with tasks 8 and 9
   rather than in M3 because the mechanism is the same one: a
   `SnapshotCommitted` record and a compacted index that one GET retrieves. A
   follower-only snapshot format built in M3 would be a second of them.
10. Hot-standby materializers applying the log continuously, so failover is a
    **promotion, not a rebuild**. This is the path that handles routine kills.
11. Leader election and fencing, with a bounded detection-plus-election window.
12. The reads-survive/writes-pause asymmetry made explicit: agents keep serving
    from their cached index; only offset assignment blocks, and tail consumers
    see an ordinary empty fetch rather than an error.
13. ⚠️ **Lease self-fencing**: track your own TTL locally and **poll actively**.
    Never rely on a watch alone — a peer system's agents lost their lease
    without knowing it, and longer timeouts do not fix this.
13a. **Lease expiry as an injected fault**, and it is `M10`'s harness that
    injects it. ⚠️ **Carries a deferral from `M10`** (`roadmap.md`'s table):
    `M10.md` asked for "a node that has lost its lease and *does not know*" and
    `M10.0` found no lease to lose — `CoordinatorEpoch`'s doc names one and
    nothing implements it, because leases are task 13 above. ⚠️ **The shape is
    already built**: `M10.8`'s pause is a node that has lost something and does
    not know, which is the metastable case the peer-system audit found. What
    this task adds is the subject, so the fault becomes the specific one task
    13's self-fencing exists to survive — and the two land together or the
    fencing is asserted by nothing.
14. ⚠️ **Degraded startup**: no hard dependency in the boot path on the
    coordinator or on any specific object existing. Two independent systems hit
    this; under liveness probes and autoscaling it turns a transient blip into a
    fleet that can only shrink.
15. Chunked replay with bounded transaction size and periodic durable progress,
    so a crash mid-replay does not restart from zero.
   ⚠️ **Carries a deferral from `M3`** (`roadmap.md`'s table, recorded by
   `M3.25`): `CoordinatorLoop::rebuild` is an unbounded full-log replay awaited
   **inside `serve`** — before the ack and inside the single serialization
   point — so a dropped cache on a long log blocks every queued producer for
   the length of the replay, and a *failed* rebuild leaves `applied_upto` at
   `None`, so the next commit replays again until one succeeds. ⚠️ **M3 could
   not fix it without building half of this task**: `drop_cache` has no
   production caller there, because the eviction that would call it went to
   `M5` with `M3.11`'s quota. Taking the replay off the ack path is this task's
   bounded-progress mechanism applied at its first real caller.
16. RTO harness measuring hot-standby failover and cold rebuild as **separate
    published numbers**.

## Completion condition

```bash
scripts/gates/m6-complete.sh
```

Asserts: a chaos test kills nodes under load with no data loss and no manual
intervention (FR-51, NFR-20); ⚠️ **the same suite injects pauses long enough to
expire a lease, and asserts the affected node self-fences** — a clean kill
never produces an unnoticed lease expiry, so a kill-only gate cannot fail on
task 13, which exists for exactly that defect; a node starts with an empty
disk and serves correctly (NFR-44); a node whose coordinator is unreachable at
boot comes up degraded rather than refusing to start (task 14); a timed
failover test records hot-standby and cold-rebuild numbers **separately**; and
the local materialized store can be deleted and rebuilt to a **logically
equivalent** index. ⚠️ **Not "and partitions"**, per `Depends on` above
(`M10.34`) — a network-partition leg needs a dependency or mechanism this
milestone does not yet have.

⚠️ **"Logically equivalent", not byte-identical.** Every engine under decision
#12 produces different bytes on replay — page layout, SST naming, flush
boundaries — so a byte comparison fails on a perfectly correct rebuild. The
property that matters is that the offset→object index answers every query the
same way.

⚠️ **NFR-22 has no number, so this condition measures and records rather than
asserting a bound.** Writing an invented target here would make every later
capacity argument rest on it. Doc 10 #15.

## Risks and open questions

- ⚠️ **Metastable failure is the category to design against**, and it is defined
  by the outage outliving its cause. The documented shapes: a node unaware it
  lost its lease; caches amplifying a transient fault into silent wrongness; a
  hard startup dependency converting a blip into an unrecoverable fleet; a
  plausible offset on an error path turning availability into safety; and
  unenforced growth bounds whose recovery requires manual intervention.
- ⚠️ **Fault-inject pauses, not kills.** A killed coordinator is the easy case;
  every metastable finding in the peer audit came from pauses and partitions.
- **Snapshot, do not compact, the metadata log.** The state machine is
  event/delta shaped, tombstones are not guaranteed replicated before deletion,
  and compaction is O(data + tombstones) against a snapshot's O(data).
- **Almost every recovery figure in the corpus is an estimate.** No vendor
  publishes a cold-rebuild time, an interval→RTO formula, or a wall-clock
  recovery time for any candidate storage engine. The one rigorous statement is
  the identity: RPO ≈ checkpoint interval, RTO ≈ state reload + replay since.
- **An engine that opens instantly but then serves degraded reads has not
  recovered.** The nearest published proxy for that penalty is roughly 60×
  cold-versus-warm; budget for warmth, not just for `open()`.
- ⚠️ **Availability has a ceiling set by the coordinator**, and any design
  offering Kafka-rate sequencing on object storage owns it. Judge this milestone
  on how gracefully it degrades when the ceiling is hit, not on whether it is
  avoided.
