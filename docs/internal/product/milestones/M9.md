# M9 — Authentication, authorization, and tenant isolation

**Kind:** feature ·
**Depends on:** M2, M3 ·
**Serves:** FR-4, FR-40, FR-44, FR-45, NFR-12

## Goal

Every operation is scoped to an authenticated principal, and a `Metadata`
request costs O(topics this principal can see) rather than O(topics that exist).

⚠️ **The second half is the architectural one, and it is easy to under-read as
an optimization.** Doc 15 §4 calls principal-indexed metadata "a genuine
departure from how Kafka is built internally" and the single most important
requirement in that document. Kafka holds all topics in a metadata cache and
*filters per request* — the response is small, the work is O(all topics). At the
scale M7 targets that is fatal in CPU, not in bandwidth.

## Depends on

**M2** for a wire to authenticate over, and **M3** for `ListOffsets`, which
task 11 scopes and which does not exist before then. ⚠️ Without M3 the FR-40
assertion below silently narrows to M2's four APIs and `ListOffsets` ships
untested for cross-principal access. It sits before **M4** and **M7** in the
order because both need principals: M4's offsets are per-group-per-principal,
and M7's entire scale claim rests on the forward index built here.

## Provisional tasks

0. ⚠️ **Verify Kafka's `Metadata` authorization-filtering claim against Kafka
   source first** — the one item in the decisions table above that is
   investigation, not choice, and the one this milestone's own goal calls
   the architectural half. Everything from task 7 on assumes its answer.
1. `Principal` type in `oqueue-core`, and the rule that every request carries one.
2. `SaslHandshake` (17) and `SaslAuthenticate` (36). ⚠️ `SaslHandshake` is
   `flexibleVersions: none` forever — verify `M2`'s per-API table already
   encodes this (doc 02 §1.5 says it should have; confirm rather than assume).
3. `SASL/PLAIN` end to end (`ADR-0032`), with credentials from configuration,
   refused outright unless the connection is already TLS-terminated.
4. TLS termination, with the backend `ADR-0012` already chose (`ring`,
   default build) — no new choice, but see this file's own note above on
   what M9 inherits from it (the aarch64 cross-`cc` cost, and sharing
   `oqueue-store`'s process-global `rustls` provider install).
5. `ApiVersions` answerable **before** authentication, unchanged from M2.
6. Authorization decision point: one place every API passes through, so a new
   API cannot be added without a scoping decision.
7. **Principal → topic-set forward index**, maintained incrementally on topic
   create, delete, and ACL change.
8. `Metadata` served through the forward index.
9. ⚠️ The **null-topic-array** case resolved through the same index. Nominally it
   means "every topic in the system"; it must mean "every topic this principal
   can see", or the pathology returns through the one path nobody tested.
10. A gate asserting **no code path materializes the global topic list** to
    answer a client request. This is the requirement; a convention will not hold.
11. Per-principal scoping on produce, fetch, and `ListOffsets`.
12. Cross-principal refusal tested on **every** API, not a sample (FR-40).
13. Secret and key-material types that cannot reach `Debug`, logs, spans, metric
    labels, or error variants (FR-44).
14. A log scan in the end-to-end suite asserting the same, since a type rule
    catches construction and not interpolation.
15. Rate limiting and quotas per principal — the isolation half of multi-tenancy
    (FR-45, added by `M9.16`; this task's own backlog row previously cited
    `NFR-12` by mistake — `Metadata` response cost, an unrelated property).
    Server-side enforcement only for v1: doc 02 §1.7 lists `DescribeClientQuotas`/
    `AlterClientQuotas` (48-49) under requests "safely deferrable for an
    initial minimum-viable broker," so the wire-visible quota-management
    API is not this task's to build.
16. Cost test for NFR-12: `Metadata` response size **and CPU** independent of
    catalog size, measured at two catalog sizes an order of magnitude apart.

## Completion condition

```bash
scripts/gates/m9-complete.sh
```

Asserts: cross-principal access is refused on every implemented API (FR-40); a
principal sees only its own topics in `Metadata`, including for a null topic
array (FR-4); response size and CPU are independent of catalog size at two
catalog sizes an order of magnitude apart (NFR-12); and a log scan over the
end-to-end suite finds no credential, key, or token material (FR-44).

## Risks and open questions

- ⚠️ **Resolved by `M9.1`.** The claim this milestone's forward index rests
  on — that Kafka filters `Metadata` by authorization, at O(all topics) cost
  to produce a response of O(topics this principal can see) — holds against
  real Kafka source. See doc 15 §8.1's own updated entry. One nuance the
  original two-line claim did not carry: the *null-topic-array* case silently
  omits an unauthorized topic, but an *explicitly-named* one gets
  `TOPIC_AUTHORIZATION_FAILED` rather than being dropped — `M9.9`/`M9.10` and
  `M9.13` need to reproduce both shapes, not collapse them into one.
- ⚠️ **Bootstrap and tenant routing at 1M–100M tenants is not researched.** You
  cannot enumerate endpoints in a load balancer. The working hypothesis is a
  shared bootstrap endpoint with the tenant identified by SASL credentials —
  a hypothesis, not a design. Doc 10 #21.
- **Cross-tenant views must never go through `Metadata`.** Billing and metering
  are an offline batch sweep from day one; an admin `--list` across the whole
  catalog needs a deliberate answer — pagination, prefix scoping, or refusal —
  **before someone finds it**. That answer is M12's, but the constraint is set
  here. Doc 15 §4.
- **FR-44 has a gate that cannot be complete.** A static type rule catches key
  material reaching a formatter by construction; it does not catch a hand-rolled
  interpolation of the bytes. The log scan is the second net, and neither is
  proof.
