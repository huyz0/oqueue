# M12 — Admin API and operability

**Kind:** functional ·
**Depends on:** M4, M9 ·
**Serves:** FR-40, FR-44, FR-45, FR-50, FR-52, FR-53, NFR-12

## Goal

An operator manages topics and configuration through the real Kafka
`AdminClient`, and a stalled partition is diagnosable from metrics, logs, and
traces without reading source.

## Depends on

**M9**, whose plan explicitly deferred the cross-tenant admin surface here —
`--list` over a 1M–100M-topic catalog needs a deliberate answer, and this is
where it is due. **M4**, because group administration (`DescribeGroups`,
`ListGroups`) is part of a complete `AdminClient` surface and needs groups to
exist first.

## Decisions required first

| Decision | Why | Background |
|---|---|---|
| The cross-tenant `--list` answer | ⚠️ **Inherited obligation, not optional.** M9's plan states the constraint — cross-tenant views never go through `Metadata` — and says the answer is M12's, "before someone finds it" | roadmap.md deferral table; doc 15 §4 |
| What "diagnosable" means, concretely | FR-52's verification is "review against a written list of diagnosable scenarios" — that list does not exist yet and is this milestone's to write before it can be reviewed against | requirements.md |

### Opening decisions — ADR-0058

The proposed directions in the delivery handoff are accepted for M12 by
ADR-0058. Topic listing stays principal-scoped; mutation and group
authorization are separate from visibility; deletion is a durable,
non-reusable tombstone; unsupported config is refused; routine telemetry is
bounded; and the three binary roles must change actual responsibilities. A
topic-catalog contract change is planned in the deletion task and must use the
contract-change procedure.

## Provisional tasks

1. `CreateTopics` (19), `DeleteTopics` (20) — through the derived-existence
   model M7 built: creation still provisions nothing beyond a catalog row.
2. `DescribeConfigs` (32), `AlterConfigs` (33), `IncrementalAlterConfigs` (44).
3. `DescribeGroups` (15), `ListGroups` (16) — the admin-facing half of M4's
   consumer groups.

3a. **`GroupGrants`: FR-40 for the five group APIs.** ⚠️ **Carries a deferral
   from `M4`** (`roadmap.md`'s deferred-into-a-later-milestone table, recorded
   by `M4.23`): `M9`'s `TopicGrants` covers the two APIs `M4` adds that name a
   topic, and the other five — `FindCoordinator`, `JoinGroup`, `SyncGroup`,
   `Heartbeat`, `LeaveGroup` — scope on `GroupId`, which has no principal
   component. Principal A can join principal B's group, be elected leader,
   read every member's subscription metadata and hold partitions B's consumers
   are waiting for. ⚠️ **`M4.md`'s completion condition asks for all seven and
   `m4-complete.sh` reports the five as unmet rather than waiving them**, so
   this task is what lets that gate's leg become an assertion — it fails today
   if any of the five *gains* a principal check, which is the signal to
   promote it. ⚠️ **It lands beside tasks 3 and 5 on purpose**: `DescribeGroups`
   and `ListGroups` are the admin-facing half of the same resource and need
   the same grant to answer honestly, and the `AdminClient` conformance run is
   where a cross-principal refusal on a group can be driven end to end. A
   second grants type is a contract change in `oqueue-core` — `ADR` first,
   every fake and implementation in one commit (non-negotiable 6).
4. The cross-tenant `--list` implementation: pagination, prefix scoping, or
   explicit refusal, per the ADR above. ⚠️ Whichever is chosen, it must not
   route through the per-principal `Metadata` path M9 built.
5. `AdminClient` conformance: `kafka-topics.sh`, `kafka-configs.sh`, and the
   equivalent Java `AdminClient` calls, end to end.
6. Structured logging with a fixed schema, reusing FR-44's redaction rules so
   an admin log line cannot leak key material by construction.
7. Metrics: per-partition lag, per-partition write latency, coordinator
   health, DEK cache hit rate, index growth rate — the operational surface
   this milestone's own scenario list (task 9) needs to be answerable, not a
   set inherited from another plan's stated obligations.
8. Distributed tracing across the produce and fetch paths, with the object
   -storage round trip as a named span.
9. **The written list of diagnosable scenarios** FR-52 needs: a stalled
   partition, a lagging consumer group, a coordinator failover in progress, a
   compaction backlog, a KMS outage degrading BYOK reads.
10. A dashboard or query set answering each scenario in the list above, and a
    review against it — the actual verification FR-52 names.
11. Config validation on `AlterConfigs`, refusing values that would violate an
    invariant another milestone made load-bearing (e.g. a retention shorter
    than the GC safety inequality's deletion delay).
12. Topic deletion semantics resolved against doc 15 §9's open question:
    whether a deleted topic's name is immediately reusable, and what that does
    to a client holding a stale topic ID.
13. Rate limiting / quota administration surfaced through the admin path.
14. Health-check and readiness endpoints distinguishing "degraded, keep
    routing" from "down, stop routing" — the distinction M6's plan made
    load-bearing for graceful degradation.
15. Single-binary role selection exercised through the admin surface: starting
    each role (coordinator, data-plane, combined) from one artifact (FR-50).
16. Admin-path authorization: every admin operation scoped to a principal with
    the appropriate grant, reusing M9's authorization decision point rather
    than adding a second one.

## Completion condition

```bash
scripts/gates/m12-complete.sh
```

Asserts: a conformance test against the real Kafka `AdminClient` completes
topic lifecycle and configuration operations (FR-53); a smoke test starts each
role from one binary artifact (FR-50); a review against the written
diagnosable-scenarios list finds each scenario answerable from metrics, logs,
or traces alone (FR-52); and ⚠️ **FR-40 on the five group APIs M4 left unmet**,
which task 3a's `GroupGrants` is what makes satisfiable: principal A joining a
group and calling `JoinGroup`, `SyncGroup`, `Heartbeat`, `LeaveGroup` or
`FindCoordinator` against a group owned by principal B is refused. ⚠️ **The
tripwire is in the closed milestone's gate, so this leg is what stops the
repair being an edit to it**: `m4-complete.sh` reports those five as unmet and
fails the day any of them gains a principal check, so without a leg here FR-40
is covered on paper by `roadmap.md` and asserted by nothing. `M15.md`'s
inherited FR-31 is the precedent. `M4.39`.

## Risks and open questions

- **FR-52's verification is a review, not a test** — the softest completion
  condition in the plan. The list of scenarios is what makes it checkable at
  all; a milestone that skips writing the list has quietly weakened its own
  acceptance criterion.
- **The cross-tenant admin surface is a foot-gun if built casually.** An
  unscoped `--list` at 100M topics is either an operational incident or a
  tenant-isolation violation, and M9's plan named this explicitly as something
  to solve "before someone finds it" — which cuts against building it as an
  afterthought here.
- **Config validation against another milestone's invariant is coupling that
  needs a home.** If M5's GC safety inequality changes its constants, this
  milestone's validation logic needs to track it, and nothing currently
  enforces that the two stay in sync.
