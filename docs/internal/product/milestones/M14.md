# M14 — Performance and cost validation

**Kind:** non-functional ·
**Depends on:** M5, M13 ·
**Serves:** NFR-1, NFR-2, NFR-3, NFR-13, NFR-31, NFR-32

## Goal

Every latency and cost number the project has stated publicly is measured on
the release artifact, not asserted from a design document.

⚠️ **NFR-1 is the project's most consequential public claim** — mission.md
states the latency position plainly because it is roughly fifty times a
local-disk Kafka ack, and a claim that large has to be measured, not
asserted. This milestone is where it either holds or the mission statement
gets corrected.

## Depends on

**M5**, because a latency benchmark run before compaction exists measures an
unrealistic write amplification. **M13**, because these numbers are only
meaningful measured on the actual release artifact — CPU dispatch, allocator,
and build profile all affect them, and a debug build's numbers are not the
project's numbers.

## Provisional tasks

1. Produce latency benchmark on a fixed workload against S3 Standard,
   asserting p99 ≤ 500 ms and p50 ≤ 300 ms (NFR-1), gated in CI as a
   regression check once the first stable baseline exists.
2. Tail-read latency benchmark asserting zero object-storage round trips at
   the high watermark and p99 ≤ 10 ms (NFR-2).
3. Historical-read latency benchmark with a cold cache, asserting p99 within
   one GET plus index resolution (NFR-3).
4. **Re-run** M7's produce-latency-independent-of-topic-count benchmark at
   release-artifact fidelity. ⚠️ NFR-4 stays M7's to serve, per roadmap.md's
   coverage table — this is a re-measurement, not a second claim on it.
5. The API-cost model as a runnable test: count PUT-class and GET-class
   operations per GB ingested on the fixed workload, and assert the result
   stays within a bound (NFR-31) — once that bound exists. ⚠️ **Carries a
   deferral from `M1`**: `oqueue-core`'s `Operation`/`CountingObjectStore`
   (`M1.14`) count one call per `ObjectStore::put`/`get`/`delete`, which
   undercounts a multipart `put` (`M1.16`) — a `CreateMultipartUpload` plus N
   `UploadPart`s plus a `CompleteMultipartUpload`, all one counted `Put` from
   the decorator's vantage point around the trait. This task's runnable test
   needs the true per-request cost, which needs either a backend reporting
   it back through the trait (a contract change) or accounting living inside
   each backend rather than as a generic decorator — a design choice this
   task must make, not inherit unexamined from `M1`'s counter shape.
   `roadmap.md`'s deferred-into-a-later-milestone table.
6. Cross-AZ transfer assertion: the default write path incurs no cross-AZ
   egress charge (NFR-32).
6a. **The benchmark harness itself, and the eight hot paths waiting on it.**
   ⚠️ **Carries a deferral from `M2` and `M3`** (`roadmap.md`'s
   deferred-into-a-later-milestone table, recorded by `M3.25`).
   `performance.md` rule 18 says a hot path's benchmark arrives *with* the
   code; `check-hot-path-bench.sh` allowlists eight rows and `M3.35` fixed the
   gate — an allowlist reason now names the milestone that owes it and turns
   red when that milestone closes. ⚠️ **`M3.35` wrote none of the benchmarks,
   including the `find_batches` one that row first assigned it**: rule 2 puts
   the micro suite on gungraun, so writing one against an unchosen harness is
   choosing the harness, which is task 9's decision below.
   ⚠️ **Every one of them needs something that has never existed in this
   repository**: `crates/*/benches` is empty, no benchmark dependency is in the
   tree, and `scripts/bench.sh`'s own header records that its `cargo bench`
   invocation has never run against real code. Choosing the harness is a
   toolchain decision with `portability.md` and `build.md` consequences — a
   valgrind-based runner is a platform requirement, not a dev-dependency —
   which task 9 below already owns. ⚠️ **All eight rows**, which is more than
   `M3.25` first wrote here: RecordBatch encode/decode, CRC-32C over
   representative sizes, varint decode, the **offset→object index lookup**,
   **buffer allocation and pooling**, the produce path end to end, fetch
   tail-versus-cold, and **compaction throughput**. ⚠️ **The three in bold were
   added by `M3.35`'s review**, which found the gate pointing rows at a
   receiver whose own plan enumerated five and excluded them — a deferral that
   names a receiver the receiver does not accept is a row nobody owns.
   ⚠️ **Compaction throughput needs `M5`'s compaction as well**, and is here
   rather than in `M5` because `M5` closes six slots earlier: pointed there, it
   would fail `M5`'s own closing commit with no harness available to fix it.
   ⚠️ **Buffer pooling needs a second thing too** — nothing in `M0`-`M15` pools
   a buffer, so this task either schedules that or the row leaves rule 18's
   table. ⚠️ **They land with task 9, not before it**, and each one's allowlist
   entry in `check-hot-path-bench.sh` names `M14` as its receiver — ⚠️ **six
   of the eight name this task by number**, and the other two name what they
   are actually waiting on instead: the offset→object lookup names task 9's
   harness decision, and compaction throughput names `M5`'s compaction as well
   as this harness.
7. **Aggregate ingest throughput measured**, and the resulting number written
   into `requirements.md` to resolve NFR-13's UNDERIVED status — this is the
   milestone's most consequential deliverable, and it feeds back into product
   docs rather than only forward into a gate.
8. `crc-fast` and the compression codecs' actual AVX-512 dispatch verified
   empirically on real hardware — doc 10 #26 flags this as unverified and a
   silent-wrong-answer risk under the wrong benchmarking tool.
9. Benchmark harness chosen and wired per the CI-hardware ADR, with the PMU
   limitation of GitHub-hosted runners designed around rather than discovered.
10. Regression thresholds calibrated against the first month of real CI
    history, starting where doc 18 suggests and tightening from there.
11. A public latency/cost comparison table against the numbers this project's
    own mission and research corpus cite for peer systems, so a reader can
    check the claim rather than trust it.
12. Load test at the throughput number from task 7, sustained long enough to
    separate a real number from a burst artifact.
13. Cost model validated against at least one real cloud bill from the load
    test in task 12 — not only against the API-call-counting model.
14. A withdrawal path documented: what happens to mission.md and NFR-1 if the
    measured number does not hold. ⚠️ This is not hypothetical box-checking —
    doc 17 states single-digit-ms produce and object-storage-only durability
    are *structurally* mutually exclusive, so this milestone is expected to
    confirm a number in the hundreds of milliseconds, not to discover a
    surprise.
15. Fast-tier decision (#7) revisited with the now-known throughput number: is
    S3-Standard-only still the right default, or does the pluggable Express
    quorum path get exercised for the first time.
16. Every number this task list produces published in one place, superseding
    every `provisional` NFR status in `requirements.md` that this milestone
    was able to resolve.

Also carried here by ADR-0007 (`M0.13`): **measure the allocator.** Doc 10 #30
leaves snmalloc unbenchmarked while noting its message-passing free design

workspace's hot path settles both; without it M14 closes with doc 10 #30 still
open and ADR-0007 recording it as owned.

## Risks and open questions

- ⚠️ **NFR-1 is a claim about a fifty-times latency disadvantage relative to
  local-disk Kafka, made in `mission.md` before any code existed.** Confirming
  it here is not a formality — if the measured p99 exceeds 500 ms on the
  release artifact under realistic load, the honest response is correcting
  the mission statement, not adjusting the benchmark's workload until it
  passes. That is the same discipline non-negotiable 2 states for thresholds.
- **This is the first milestone whose own tasks feed back into
  `requirements.md`.** Every prior milestone read requirements; this one
  writes one (NFR-13). That reversal is deliberate and worth flagging at the
  boundary review as a check that the number was actually measured and not
  quietly chosen to make a downstream gate easier.
- **Peer-system numbers cited in the research corpus are vendor-reported**,
  not independently verified — the corpus says so of itself. Task 11's
  comparison table inherits that caveat and should carry it forward rather
  than presenting vendor numbers with the same confidence as this project's
  own measurements.
