# M15 — v1 hardening: chaos, soak, and the release gate

**Kind:** non-functional ·
**Depends on:** M14 ·
**Serves:** NFR-20, NFR-23, FR-10, FR-51, FR-31

## Goal

No acknowledged record is ever lost, under sustained load, over a soak long
enough to expose what only shows up slowly, with every prior milestone's
claims still holding in combination rather than only in isolation.

⚠️ **NFR-20 is "the requirement everything else yields to."** This milestone
is where that sentence is tested rather than trusted — every fault-injection
scenario across every failure point in the write path, run together, not one
at a time the way each earlier milestone necessarily tested it.

## Depends on

**M14**, entirely. Hardening a system whose own performance and cost claims
have not been measured tests a system that does not yet resemble what ships.
This is deliberately the last milestone: everything else is either a
prerequisite to this one or shipped alongside it.

## Provisional tasks

1. Chaos test harness combining every fault class from M10's simulation —
   kills, pauses, partitions, 503 storms — run **concurrently and under
   production-representative load**, not one fault at a time as each earlier
   milestone tested in isolation.
2. Fault injection across every point in the write path M-1's roadmap names:
   before PUT, between PUT and commit, after commit and before ack (FR-10).
3. A soak run long enough to expose what a short test cannot: memory growth
   from an uncapped cache, index growth outrunning compaction, a leak in
   connection or task pooling, DEK-cache growth beyond its designed bound.
4. Combined-milestone invariant sweep: every invariant test written in M3, M5,
   M6, M9 run together under the same chaos harness, not only individually in
   their own milestone's CI.
5. A full-fleet loss-and-recovery drill: not a single node, the failure mode
   FR-51 actually promises tolerance for.
6. Availability measured over the soak against the stakeholder figure from the
   ADR above (NFR-23).
7. A metastable-failure regression suite: each documented failure mode from
   M6's plan (lease expiry undetected, cache-amplified silent wrongness, a
   hard startup dependency, a plausible offset on an error path, an unenforced
   growth bound) exercised as a named test, not left to chance rediscovery.
8. Cross-tenant isolation re-verified under chaos: a fault affecting one
   principal's data path must not leak into or degrade another's, tested
   under load rather than only at rest as M9 originally tested it.
9. BYOK and FIPS paths included in the chaos and soak runs, not carved out —
   a KMS outage during the soak is exactly the read-path degradation M8's
   plan flagged and is exactly what this milestone exists to exercise.
10. A public incident-response runbook derived from what this milestone finds
    breaks, or nearly breaks — turning hardening findings into an operational
    document rather than only into fixed code.
11. The release gate itself: one script that runs every prior milestone's
    completion condition, plus this milestone's chaos and soak suites, and
    is the actual command that means "v1".
12. A go/no-go review against every UNDERIVED and `provisional` requirement
    still open at this point — if any remain, the honest response is either
    resolving them or explicitly deferring them into a stated post-v1 scope,
    not shipping silently against an unresolved requirement.
13. Public documentation of what v1 does *not* do — FR-15 (transactions),
    KIP-848 if deferred, and anything else this milestone's go/no-go review
    surfaces — matching the "what is not required" discipline
    `requirements.md` already states for the initial scope.
14. Load test at sustained peak (not burst) for a duration matching the soak,
    confirming M14's throughput number holds under combined chaos rather than
    only under clean conditions.


15. ⚠️ **The storage layer run against the storage it claims to support** —
    deferred here from `M1` by `M1.44` (`roadmap.md`'s cross-milestone table),
    and two obligations rather than one. **Real S3**: `M1`'s conformance suite
    runs against the fake and MinIO, so conditional-write behaviour is verified
    against doc 04 §6's *documented* semantics, not against S3 — if the fake
    and MinIO are both more permissive than S3, that is an architectural error
    and not a test gap (doc 10 #33). **GCS**: `GcsStore` has never executed
    against anything; `ADR-0014` measured two emulators and neither round-trips
    `object_store`'s actual request shape, so this needs an emulator fixed
    upstream, a third emulator, or real GCS. ⚠️ Sequence the GCS half
    emulator-first — real GCS with no fast-failing local target makes every
    iteration a cloud round-trip. ⚠️ The reason this cannot wait for someone to
    deploy on GCS: `s3.rs` and `gcs.rs` are ~90% duplicated, so the `s3` column
    being green makes GCS *look* covered while the 10% that differs
    (`ifGenerationMatch` preconditions and the resumable upload path) is
    exactly what is untested. ⚠️ Not `compose` — `ADR-0015` records that
    `object_store` does not expose it for GCS at all, so nothing here
    implements it; `M1.17`'s own row already retracted that mention once.
    Discharging this means `baselines/conformance-matrix.txt` gains `verified`
    for `s3-real` **and for at least one of `gcs` / `gcs-real`** — stated that
    way, not as "wherever it now reads `not-yet-run`", because the matrix has
    three such rows and this task deliberately permits the real-GCS route,
    which leaves the `gcs` emulator row honestly unrun. The completion
    condition below says the same thing; ⚠️ **an earlier version of each said
    something different from the other**, and the stricter one's only passing
    move was flipping a row to `verified` with nothing having run it.

    Either way the criterion is checkable by reading a file rather than by
    running a fleet, which is why the completion condition below states it.
    ⚠️ **Ordered ahead of
    the release tag deliberately.** A first version of `M1.44` appended this
    after task 15 and named it in no gate, which review pointed out is the same
    unchecked structure the row exists to condemn: an obligation scheduled
    after the thing it is supposed to gate cannot gate it, and `ADR-0014`'s
    deferral to a task that closed without discharging it is that failure one
    milestone earlier.

16. The v1 tag and release, cut only after the release gate passes clean.

## Completion condition

```bash
scripts/gates/m15-complete.sh
```

Asserts: the combined chaos-and-soak suite runs to completion with no
acknowledged record lost (NFR-20) and no data loss or manual intervention
required across a full-fleet failure (FR-51); the soak's measured availability
meets the stakeholder-set target (NFR-23); every metastable failure mode named
in M6's plan has a passing regression test; and the release gate — every prior
milestone's completion condition plus this one's — passes as a single command;
and `baselines/conformance-matrix.txt` records `verified` for `s3-real` **and
for at least one of `gcs` / `gcs-real`**, which is `M1.44`'s deferral
discharged (task 15) and the one assertion here checkable by reading a file
rather than by running a fleet.

⚠️ **"At least one", not both, and the disjunction is the point.** A first
version demanded `gcs` — the emulator row — while task 15 explicitly permits
discharging the GCS half against real GCS instead. Taking that route would
have left `gcs` honestly `not-yet-run`, failed this gate, and left one escape:
flipping a row to `verified` with nothing having run it, which is the single
thing `baselines/conformance-matrix.txt`'s header exists to prevent. A gate
whose only passing move is a false record is worse than no gate.

⚠️ **This is the roadmap's final completion condition.** A green result here
is the closest thing this project has to "v1 is done," and it is deliberately
built from every other milestone's condition rather than restating its own
independent claim.

## Risks and open questions

- ⚠️ **A chaos suite that only re-runs each milestone's own fault classes in
  isolation has not tested the thing this milestone exists for.** The
  interesting failures are combinations — a partition during a compaction
  job, a KMS outage during a coordinator failover — and the task list above is
  written to force combination, not repetition.
- **No stakeholder availability figure exists yet**, and this milestone's
  soak cannot honestly report pass/fail without one. Get it early; discovering
  it is missing during the soak itself is late.
- **FR-15 (transactions) ships deferred, and this is where that becomes
  official** rather than merely planned. The go/no-go review is where the
  project either accepts that gap publicly or decides it is not ready to ship
  without it — and if the latter, that is new work this plan did not
  schedule, and the roadmap needs to say so rather than silently absorbing it.
- **This milestone has no natural stopping point other than the gate
  passing.** Chaos and soak testing can always run longer and find more; the
  release gate is what converts "we could keep testing" into "this is v1."
