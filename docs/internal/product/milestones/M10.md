# M10 — Deterministic simulation and fault injection

**Kind:** AI-native development support ·
**Depends on:** M3 ·
**Serves:** NFR-20 (the method), FR-51 (the method), NFR-21

## Goal

Every milestone after this one makes a claim about behaviour under concurrency
and failure. M10 is what makes those claims testable rather than asserted: a
seeded, deterministic schedule in which a failing run can be replayed exactly.

⚠️ **It serves NFR-20 and FR-51 as a *method*, not directly**, and that is not
a defect in the plan: those are verified in M5, M6 and M15, and what M10
supplies is what makes verifying them possible. A milestone that mostly enables
other milestones is unusual and worth stating plainly rather than dressing up
with borrowed requirement IDs.

⚠️ **NFR-21 is the exception, and it is owned outright** (`M10.0`). This said
M10 "serves no requirement directly" until then, which the Serves line above
now contradicts on purpose: `requirements.md` gives NFR-21 the verification
method "invariant test: the cache is never ahead of durability", that test is
task 10 below and nothing else, and M3 — which owned the requirement — closed
with the substance asserted under FR-10's and FR-11's gate legs and nothing
connecting it to evidence. ⚠️ **So `m10-complete.sh` carries an NFR-21 leg**;
without one the move buys nothing, and the sentence above is the one that would
license omitting it.

⚠️ **Also receives six rows M3 opened after its own decomposition**
(`roadmap.md`'s cross-milestone table): `M3.41`-`M3.46`. ⚠️ **Because M10 is
next in execution order, not because they are simulation work** — that is
`M1`'s eleven, received by `M2.0`, and the rule it set: debt a milestone
discovers goes to whoever opens next, or it is a deferral in nobody's plan.
`M10.0` pulls them in as M10 rows and flips each M3 cell to `dissolved` with a
pointer, because closing an M10 row cannot flip an M3 cell.

⚠️ **Two are client-visible defects and should not be read as documentation
work**: `M3.43` — `RecordTooShort` reaches a producer as `CORRUPT_MESSAGE`,
which the Java client and librdkafka both retry, so a client re-sends
byte-identical bytes until `delivery.timeout.ms` expires — and `M3.45`, three
of whose seven sentences are in `docs/protocol-support.md`, the published FR-2
contract a client author plans against. `M3.41` is a type change, `M3.42` and
`M3.46` are gate mechanisms that pass for the wrong reason, and `M3.44` is two
files at the line limit. ⚠️ **`M10.0` must re-derive the set** rather than
trust this list: the set is M3's rows marked `deferred`, plus any `todo`.

## Depends on

**M3.** There is nothing worth simulating before the coordinator exists — the
interesting schedules are concurrent produce, commit, and cache propagation, and
none of those exist earlier.

## Why it sits here and not later

Doc 10 #32 calls this "the largest single testing investment the project needs".
Investments are made before the return, not after. M4, M5, M6, M11 and M15 all
assert failure behaviour, and a harness built afterwards can only retrofit tests
to code already written — which is how a system acquires tests that agree with
whatever it happens to do.

## Provisional tasks

1. ⚠️ **Not "wired behind the `cfg` seam" — `M1.22` found no such seam exists**
   for this project's object-store I/O (no madsim shim for `reqwest`/`hyper`).
   The task is a deterministic transport implementing `object_store`'s
   `HttpService`, answering from an in-process model, with the real transport
   staying the default. See `standards/testing.md`, "Deterministic simulation".
   ⚠️ Whether the *broker's* own socket I/O — a different stack from the object
   store's — can be simulated is a separate question this spike did not
   answer; `turmoil` is the candidate there.
2. Seeded scheduler: a run is reproducible from a single seed printed on
   failure. ⚠️ A failing seed that cannot be replayed is not a test.
3. Simulated clock driving the `Clock` seam — nothing reads real time.
4. Simulated `ObjectStore` driving latency distributions from doc 04 §2 rather
   than from round numbers.
5. Fault injection: 503 storms, conditional-write races, partial failures.
6. ⚠️ **Pauses and partitions, not only kills.** Every metastable finding in the
   peer-system audit came from pauses; a killed coordinator is the easy case.
7. Lease expiry as a first-class injected fault — the specific shape being a
   node that has lost its lease and *does not know*. ⚠️ **Deferred to `M6` by
   `M10.0`** — no lease exists to lose, and `M6` is where one is built; the
   *shape* stays here as `M10.8`'s pause (`roadmap.md`'s table; `M6.md` task
   13a).
8. Network partition between agent and coordinator, held long enough to exceed
   the bounded staleness limit M3 sets. ⚠️ **Deferred to `M7` by `M10.0`** —
   there is no network between them to cut while the broker's index *is* the
   coordinator's, which is why `Cluster::cache_state` hardcodes `silent_for_ms`
   to zero (`roadmap.md`'s table; `M7.md` task 17d).
9. Crash points enumerated on the write path: before PUT, between PUT and
   commit, after commit and before ack.
10. Invariant harness: the checks run continuously across a simulated run rather
    than at the end — offsets gap-free, cache never ahead of durability, high
    watermark never ahead of servability.
11. Seed corpus in CI, plus a nightly random-seed sweep that files a failing
    seed as an artifact.
12. Shrinking: reduce a failing schedule to a minimal interleaving.
13. `standards/testing.md` updated with what the harness actually made possible
    — the paragraph the M1 spike was deferred to inform.
14. A worked example: reproduce one already-known failure class end to end, to
    demonstrate the harness catches something rather than merely running.

## Completion condition

```bash
scripts/gates/m10-complete.sh
```

Asserts: a known-bad build fails under simulation and the failing seed replays
deterministically to the same failure; the invariant harness runs across a
seeded schedule with injected store failures and journal refusals; and the
simulated clock is the only clock — no test in the workspace reads real time.

⚠️ **This said "pauses, partitions and 503s" until `M10.0`**, which deferred the
only partition the plan enumerated to `M7` — see task 8. A leg asserting a
partition M10 cannot inject would run and constrain nothing, which is what
`M10.15`'s row is written to refuse. ⚠️ **`M10.34` scoped "pauses" the same
way**: the broker-level `Schedule` (`M10.12`) draws `StormStore` and
`RefuseJournal`, never a `Pause` step — `Fault::Pause` exists only in
`oqueue-store`'s simulated S3 (`M10.8`), one layer below where this harness
runs — so the sentence above names what actually runs rather than what the
layer beneath it can do.

⚠️ **Task 14 is what makes this condition meaningful.** A harness that runs and
finds nothing is indistinguishable from a harness that cannot find anything, so
completion requires demonstrating a real catch.

## Risks and open questions

- ⚠️ **Determinism is easy to lose and hard to notice losing.** A single
  `HashMap` iteration, a real clock read, or a thread pool that is not simulated
  makes replay unreliable — and a harness that is *usually* deterministic is
  worse than one that is honestly not, because failures get dismissed as flakes.
- **This milestone can expand without limit.** The completion condition is
  written to bound it: enough to verify the claims M4–M15 make, not a general
  simulation of the system.
- **The cost is real and recurring.** Doc 19 §9.2 notes the same tension for
  mutation testing — per-change cost is bounded by narrowing, but the full run
  grows linearly. Expect the nightly sweep to need sharding well before v1.
- **Unresolved:** whether the simulation composes with the sans-I/O split or
  partly subsumes it (#32). If it subsumes it, that is an argument about
  `architecture.md` and needs an ADR, not a quiet convergence.
