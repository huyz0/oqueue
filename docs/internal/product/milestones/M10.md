# M10 — Deterministic simulation and fault injection

**Kind:** AI-native development support ·
**Depends on:** M3 ·
**Serves:** NFR-20 (the method), FR-51 (the method)

## Goal

Every milestone after this one makes a claim about behaviour under concurrency
and failure. M10 is what makes those claims testable rather than asserted: a
seeded, deterministic schedule in which a failing run can be replayed exactly.

⚠️ **It serves no requirement directly, and that is not a defect in the plan.**
It supplies the *method* by which NFR-20 ("no acknowledged record is ever lost")
and FR-51 (tolerate the loss of any node) are verified in M5, M6 and M15. A
milestone that only enables other milestones is unusual and worth stating
plainly rather than dressing up with borrowed requirement IDs.

## Depends on

**M3.** There is nothing worth simulating before the coordinator exists — the
interesting schedules are concurrent produce, commit, and cache propagation, and
none of those exist earlier.

## Why it sits here and not later

Doc 10 #32 calls this "the largest single testing investment the project needs".
Investments are made before the return, not after. M4, M5, M6, M11 and M15 all
assert failure behaviour, and a harness built afterwards can only retrofit tests
to code already written — which is how a system acquires tests that agree with
whatever it happens to do.

## Provisional tasks

1. Simulation runtime selection wired behind the `cfg` seam, with a real-runtime
   build that stays the default.
2. Seeded scheduler: a run is reproducible from a single seed printed on
   failure. ⚠️ A failing seed that cannot be replayed is not a test.
3. Simulated clock driving the `Clock` seam — nothing reads real time.
4. Simulated `ObjectStore` driving latency distributions from doc 04 §2 rather
   than from round numbers.
5. Fault injection: 503 storms, conditional-write races, partial failures.
6. ⚠️ **Pauses and partitions, not only kills.** Every metastable finding in the
   peer-system audit came from pauses; a killed coordinator is the easy case.
7. Lease expiry as a first-class injected fault — the specific shape being a
   node that has lost its lease and *does not know*.
8. Network partition between agent and coordinator, held long enough to exceed
   the bounded staleness limit M3 sets.
9. Crash points enumerated on the write path: before PUT, between PUT and
   commit, after commit and before ack.
10. Invariant harness: the checks run continuously across a simulated run rather
    than at the end — offsets gap-free, cache never ahead of durability, high
    watermark never ahead of servability.
11. Seed corpus in CI, plus a nightly random-seed sweep that files a failing
    seed as an artifact.
12. Shrinking: reduce a failing schedule to a minimal interleaving.
13. `standards/testing.md` updated with what the harness actually made possible
    — the paragraph the M1 spike was deferred to inform.
14. A worked example: reproduce one already-known failure class end to end, to
    demonstrate the harness catches something rather than merely running.

## Completion condition

```bash
scripts/gates/m10-complete.sh
```

Asserts: a known-bad build fails under simulation and the failing seed replays
deterministically to the same failure; the invariant harness runs across a
seeded schedule with injected pauses, partitions and 503s; and the simulated
clock is the only clock — no test in the workspace reads real time.

⚠️ **Task 14 is what makes this condition meaningful.** A harness that runs and
finds nothing is indistinguishable from a harness that cannot find anything, so
completion requires demonstrating a real catch.

## Risks and open questions

- ⚠️ **Determinism is easy to lose and hard to notice losing.** A single
  `HashMap` iteration, a real clock read, or a thread pool that is not simulated
  makes replay unreliable — and a harness that is *usually* deterministic is
  worse than one that is honestly not, because failures get dismissed as flakes.
- **This milestone can expand without limit.** The completion condition is
  written to bound it: enough to verify the claims M4–M15 make, not a general
  simulation of the system.
- **The cost is real and recurring.** Doc 19 §9.2 notes the same tension for
  mutation testing — per-change cost is bounded by narrowing, but the full run
  grows linearly. Expect the nightly sweep to need sharding well before v1.
- **Unresolved:** whether the simulation composes with the sans-I/O split or
  partly subsumes it (#32). If it subsumes it, that is an argument about
  `architecture.md` and needs an ADR, not a quiet convergence.
