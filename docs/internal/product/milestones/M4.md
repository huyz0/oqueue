# M4 — Consumer groups

**Kind:** functional ·
**Depends on:** M3, M9 ·
**Serves:** FR-20, FR-21, FR-22

## Goal

Multiple consumers join a group, are assigned partitions, heartbeat, rebalance
when membership changes, and commit offsets that survive a full fleet restart.

## Depends on

**M3** for durable partitions and offsets to commit against, **M9** for the
principal that scopes a group. ⚠️ Consumer-group state is explicitly **not** on
the derived-manifest path — doc 14 §1 and §11.7 both carve it out — so it lives
in `oqueue-coordinator` with an authority, not in object-store manifests.

## Provisional tasks

1. `GroupId`, `MemberId`, `GenerationId`, and the group state machine as a type
   with only legal transitions: Empty → PreparingRebalance → CompletingRebalance
   → Stable → Dead.
2. `GroupCoordinator` seam in `oqueue-core` + fake in `oqueue-testkit`.
3. `FindCoordinator` v0–v3, single-key.
4. `FindCoordinator` v4+, batched (KIP-699), through the same resolver.
5. `JoinGroup` codec, carrying subscription-metadata blobs **opaquely**.
6. Group-leader election and protocol-name intersection — the one assignment
   protocol every current member advertises — including the empty-intersection
   error path.
7. `JoinGroup` handler: member-id assignment, generation bump, leader-only
   member list, and the rebalance-timeout join barrier.
8. `SyncGroup`: the leader submits the full assignment, followers submit empty,
   the coordinator slices and relays. ⚠️ **Assignment is computed client-side**
   in the classic protocol — the broker implements no assignor.
9. `Heartbeat` + session-timeout eviction, and `REBALANCE_IN_PROGRESS`.
10. `LeaveGroup`, including the batched-member form, triggering a rebalance.
11. Fencing errors as one audited path: `ILLEGAL_GENERATION`,
    `UNKNOWN_MEMBER_ID`, `NOT_COORDINATOR`, `COORDINATOR_NOT_AVAILABLE`,
    `COORDINATOR_LOAD_IN_PROGRESS`.
12. `OffsetCommit`, with generation, member **and principal** fencing on every
    commit.
13. `OffsetFetch`, including the all-partitions form, scoped by principal.
    ⚠️ The all-partitions form is the one that leaks if scoping is missed.
14. Durable offset storage plus replay on coordinator takeover.
15. Group-state durability and rebuild on shard reassignment — the
    `COORDINATOR_LOAD_IN_PROGRESS` window.
16. `ownedPartitions` round-tripped so `cooperative-sticky` clients work.
    ⚠️ The invariant is that a partition is revoked by its previous owner before
    being handed to a new one, which is why cooperative rebalancing takes two
    rounds. Mixed-protocol groups are unsafe.
17. Conformance: N consumers joining and leaving under librdkafka and the Java
    client, plus a full-fleet-restart offset-survival test.
18. **Wiring M9's authentication/authorization/quota mechanism into
    `bin/oqueue serve`'s real listener** (from M9, `roadmap.md`'s deferred
    table). `bin/oqueue`'s composition root still calls
    `Dispatcher::new(cluster)` with none of `.tls_terminated()`,
    `.with_credentials(...)`, `.with_topic_grants(...)`, or `.with_quota(...)`
    — every M9 mechanism exists and is tested, but nothing in the shipped
    binary reads a real TLS cert/key, a real credential source, real topic
    grants, or a real quota configuration and passes it to a connection's
    dispatcher. Reading that configuration was named "`bin/oqueue`'s job, the
    composition root" by `M9.3`, `M9.4`, `M9.5`, and `M9.16`'s own doc
    comments, and none of those milestones' own tasks were the composition
    root's to change. `M9`'s milestone-boundary review found this the day M9
    closed; `M4` receives it — the milestone next in execution order, `M1`'s
    eleven rows→`M2` and `M3`'s six rows→`M10`'s own precedent for "debt goes
    to whoever opens next, not to whichever milestone the work thematically
    resembles" — not because group membership needs it structurally (M4's
    own tests can drive `Dispatcher` directly, `cross_principal.rs`'s own
    pattern), but because a real client cannot reach an authenticated,
    quota-bounded connection at all until this lands, and M4 is the next
    milestone whose own conformance tasks (17, above) drive a real client
    against a real listener.

## Completion condition

```bash
scripts/gates/m4-complete.sh
```

Asserts: a conformance test with multiple consumers joining and leaving
completes rebalances against librdkafka and the Java client (FR-20); committed
offsets survive a full broker fleet restart (FR-21); every fencing error is
reachable in a test rather than merely defined; and ⚠️ **cross-principal access
is refused on each of the seven APIs this milestone adds** (FR-40).

⚠️ **That last clause is not M9's job, and assuming it is is the trap.** M9's
gate asserts FR-40 over "every implemented API" — implemented *as of M9*, which
predates every API here. Principal A joining a group and calling `OffsetFetch`
(all-partitions) or `OffsetCommit` against a topic owned by principal B leaks or
overwrites B's offsets if the resolver or the offset store keys on
`(group, topic)` without the principal — and both gates stay green while the
roadmap still shows FR-40 served. **Every milestone that adds an API re-asserts
FR-40 for it**; M11 and M12 inherit the same obligation.

⚠️ **FR-22 (KIP-848) is `deferred` and this condition does not assert it.**
`ADR-0033` settled it in `M4.0`, `M4.22` annotated `roadmap.md`'s coverage row
and added FR-22 to the "Deferred, with nothing scheduled" paragraph, and
`M4.24` moved the register itself from `provisional` to `deferred`. Nothing
here is outstanding — this paragraph used to say "if the ADR defers it, the
roadmap's coverage table must say so", and it does.

## Risks and open questions

- ⚠️ **Consumer-group state at this tenancy shape is unsized.** One group per
  tenant is the natural pattern, and the `__consumer_offsets` equivalent at that
  group count "needs its own sizing" — doc 15 §9, doc 10 #23. This milestone
  will make a sizing assumption; write it down.
- **The classic group-metadata record has a ~1 MB ceiling per group**, and
  KIP-848 converts that into ~1 MB per *member*. At one group per tenant this is
  survivable; at wide groups it is not. The threshold is not published.
- ⚠️ **Measured rebalance times above 1,000 partitions are not published for any
  protocol** — doc 14 §12. Anything this milestone claims above that is
  extrapolation.
- **`OffsetCommit`/`OffsetFetch` v9 carry topic IDs**, which interacts directly
  with the unresolved topic deletion-and-reuse question (doc 15 §9): Kafka
  clients have topic-identity expectations that complicate immediate reuse.
- **Deferred here:** `TxnOffsetCommit` and `AddOffsetsToTxn` belong with FR-15
  (transactions), which is post-v1 with nothing scheduled.
