# Object Storage Technical Characteristics for High-Throughput Log Systems (S3 & GCS)

*Research brief: consistency, latency, throughput limits, pricing, upload semantics, and coordination-free commit protocols relevant to building a WarpStream/AutoMQ/S2-style log-storage system directly on cloud object storage.*

> **How this fits the project:** every other design document in this knowledge base — the write path, read path, metadata approach, and cost model — is downstream of the facts in this file. Read this one first if you only read one "fundamentals" doc.

---

## 1. Consistency Model

**Amazon S3.** Since December 1, 2020, S3 provides **strong read-after-write consistency automatically, for all applications, at no additional cost and with no performance penalty** ([AWS S3 Consistency](https://aws.amazon.com/s3/consistency/), [AWS announcement, Dec 2020](https://aws.amazon.com/about-aws/whats-new/2020/12/amazon-s3-now-delivers-strong-read-after-write-consistency-automatically-for-all-applications)). Concretely:

- After a successful **PUT** of a new object, or an overwrite/delete of an existing object, any subsequent GET or HEAD "immediately receives the latest version."
- **LIST** operations are strongly consistent too — a listing performed right after a write reflects that write.
- Operations that change **object tags, ACLs, or metadata** are also strongly consistent.
- This applies uniformly across all AWS regions, including GovCloud and the China regions, and (since Nov 2021) S3 on Outposts.

Prior to Dec 2020, S3 offered read-after-write consistency only for new-object PUTs, with **eventual consistency for overwrite PUTs and DELETEs** — this was the source of the classic "wrote object, immediately read stale/old version" bug class and the reason many pre-2020 systems (e.g. early Kafka-on-S3 designs, Hadoop's S3Guard) bolted on an external consistency layer (DynamoDB-backed metadata, etc.). That workaround category is now obsolete for S3 itself, though it's worth noting AWS's public materials do not enumerate a residual edge case in normal operation — this is a genuinely global, no-caveat guarantee for standard S3 API calls. The consistency guarantee is about **object-level linearizability of the S3 namespace**, not about coordinating conflicting concurrent writers — two overwrite PUTs racing to the same key still resolve on a "last writer wins" basis (this is what the 2024 conditional-write feature, §6, was added to solve).

**Google Cloud Storage.** GCS also provides **strong global consistency** for the operations that matter to a log/metadata layer ([GCS Consistency docs](https://docs.cloud.google.com/storage/docs/consistency)):

- Read-after-create, read-after-metadata-update, and read-after-delete are all strongly consistent for objects.
- **Listing is strongly consistent** — this was a notable engineering investment: Google migrated all GCS metadata onto **Spanner**, its globally-distributed strongly-consistent database, specifically to make bucket listings strongly consistent even across dual-region and multi-region buckets ([Cloud Blog — Spanner and strong list consistency](https://cloud.google.com/blog/products/gcp/how-google-cloud-storage-offers-strongly-consistent-object-listing-thanks-to-spanner)).
- After a successful write response, the object is immediately available for read and metadata operations — no propagation delay, even across regions in a multi-region bucket.
- **Caveats:** (1) publicly-readable objects that are being served through caching may not be strongly consistent — a cached copy can be served until its cache lifetime (`Cache-Control`) expires, even after the underlying object changes; (2) **bucket-level configuration changes** (e.g., enabling versioning) are consistent for reads of the setting itself, but downstream effects can take time to fully propagate — Google explicitly recommends waiting ~30 seconds after enabling versioning before deleting/replacing objects; (3) **IAM/ACL permission changes and bucket recreation are eventually consistent**, typically ~1 minute, occasionally longer.

**Net comparison.** For the purposes of a log-storage system that treats object storage as its durability layer, S3 and GCS are functionally equivalent on the guarantees that matter: single-key read-after-write, and strongly consistent listing. GCS is slightly more precise/expansive in its public documentation about the read-after-delete and read-after-metadata-update cases; S3's docs are terser but the guarantee is the same in practice. Neither provider gives you multi-key transactional consistency or automatic conflict resolution between racing writers — that has to be built on top using conditional writes (§6) or an external metadata/commit log.

**Azure Blob Storage** (for completeness): Azure Storage was designed around a strong consistency model from the start — after an insert/update completes, subsequent reads or lists return the latest data, using snapshot isolation internally to let reads proceed concurrently with in-flight writes on the same partition ([Manage concurrency in Blob Storage](https://learn.microsoft.com/en-us/azure/storage/blobs/concurrency-manage), [Azure blog — Managing Concurrency](https://azure.microsoft.com/en-us/blog/managing-concurrency-in-microsoft-azure-storage-2/)). Azure never had the S3-style "eventual consistency on overwrite" historical gap that AWS closed in 2020, but it also historically had weaker per-account/per-partition throughput scaling than S3/GCS, which matters more for a log system than the consistency model does at this point (all three providers are strongly consistent today).

## 2. Latency Characteristics

Latency, not throughput, is the binding constraint for produce/fetch paths in an object-storage-backed log system, because every "flush" or "fetch" round-trip to the object store adds tail latency to the client-visible produce/consume latency.

**S3 Standard — typical figures.** AWS does not publish an official per-storage-class SLA in milliseconds, but independent benchmarks converge on:
- **GET**: median (p50) roughly 15–45ms for small-to-medium objects in the same region, p90 ~60ms, p99 in the 85–300ms range depending on object size and measurement methodology ([AutoMQ — Kafka on S3 challenges](https://www.automq.com/blog/deep-dive-into-the-challenges-of-building-kafka-on-top-of-s3), community S3 latency benchmarks).
- **PUT**: median commonly 60–70ms, p99 in the 130–250ms range for small objects, increasing for larger multi-MB objects.
- These numbers are **1000x slower** than local NVMe (tens to low-hundreds of microseconds), which is the central engineering problem every object-storage-native log system has to design around ([AutoMQ blog](https://www.automq.com/blog/deep-dive-into-the-challenges-of-building-kafka-on-top-of-s3)).

**Factors affecting S3 latency:**
- **Object size**: sub-request-overhead dominates for small objects; large objects benefit from parallel byte-range GETs and multipart PUTs to maximize throughput per NIC ([S3 performance design patterns](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-design-patterns.html)).
- **Request rate / "newness" of a key range**: S3 auto-scales per-prefix capacity but does so gradually; a burst against a cold prefix produces transient `503 Slow Down` and higher tail latency until S3 internally repartitions.
- **Same-region vs cross-region**: cross-region calls add real network RTT (tens to 100+ms depending on geography) on top of the base object-store latency, plus egress cost (§4) — virtually all log-on-object-storage systems pin writers and object-store bucket to the same region/AZ.
- **Connection reuse / DNS**: AWS explicitly recommends connection pooling and spreading requests across S3's IP pool; cold TCP/TLS handshakes materially affect small-request p99s ([S3 performance design patterns](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-design-patterns.html)).
- **S3 Express One Zone**: purpose-built low-latency tier storing data in a single AZ (in "directory buckets"), advertised and benchmarked at **single-digit-millisecond** typical latency and up to **10x lower latency / 50% lower request cost** than S3 Standard ([S3 Express One Zone launch](https://aws.amazon.com/about-aws/whats-new/2023/11/amazon-s3-express-one-zone-storage-class), [Optimizing S3 Express One Zone performance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-express-performance.html)). AWS added CloudWatch P50/P95/P99 latency metrics for it in 2026 for SLA monitoring. Real-world benchmarks (see §8) put p50 GET around 3ms and p99 around 15ms for small objects.

**GCS.** Google's own guidance frames latency mostly through the request-rate/ramp-up lens (§3) rather than publishing explicit percentile tables, but GCS is broadly comparable to S3 Standard for same-region small-object GET/PUT (tens of ms median, low hundreds of ms p99), and GCS's **Anywhere Cache / Rapid Cache** (renamed 2026) exists specifically to shave GET latency for bursty/hot-read workloads by co-locating cached copies with compute zones, offering aggregate read throughput up to 2.5 TB/s for a bucket without code changes ([Anywhere Cache docs](https://cloud.google.com/storage/docs/anywhere-cache), [Blocks & Files coverage](https://www.blocksandfiles.com/public-cloud/2026/04/22/googles-cloud-storage-gets-faster-and-smarter-for-ai/5218551)).

**Implication for produce/fetch latency in a log system.** This is the load-bearing constraint that shapes every object-storage-native log design:
- **WarpStream** measured **~400–600ms p99 write latency** and **<1.5s p99 end-to-end (produce→consume)** latency using S3 Standard, and cut that roughly **4x with S3 Express One Zone**, reporting **p99 ≈169ms / median ≈105ms** produce latency on Express, and as low as **33ms median** with "Lightning Topics" using delayed/batched sequencing tricks ([AWS Storage Blog — WarpStream on S3 Express](https://aws.amazon.com/blogs/storage/how-warpstream-enables-cost-effective-low-latency-streaming-with-amazon-s3-express-one-zone/), [WarpStream benchmark/TCO post](https://medium.com/@warpstream/warpstream-s3-express-one-zone-benchmark-and-total-cost-of-ownership-458791998677)).
- **S2.dev** reports **p99 end-to-end under 500ms** on its S3-Standard-backed "Standard" tier and **under 50ms** on its "Express" tier (a quorum of three S3 Express One Zone buckets), the latter being latency-competitive with disk-based streaming systems ([S2.dev — Introducing S2](https://s2.dev/blog/intro)).
- **AutoMQ** avoids the raw object-store latency on the write critical path entirely by fronting S3 with a low-latency **Write-Ahead Log** on block storage (EBS: sub-10ms; NFS/FSx: ~6ms avg, ~13ms p99) and flushing to S3 asynchronously in the background, since direct S3 writes (200–500ms, ~150ms even on Express) are too slow for a synchronous produce ack ([AutoMQ WAL blog](https://www.automq.com/blog/deep-dive-into-the-challenges-of-building-kafka-on-top-of-s3), [AWS Storage Blog — AutoMQ + FSx](https://aws.amazon.com/blogs/storage/achieving-sub-10ms-latency-and-94-cost-savings-with-diskless-kafka-using-automq-and-amazon-fsx-for-netapp-ontap/)).

The consistent pattern: raw synchronous object-store round trips (hundreds of ms on Standard tiers, tens of ms on Express) are too slow to be the sole mechanism for low-latency produce acks, so every serious system either (a) batches many producer records per object and amortizes the fixed per-request latency, (b) fronts object storage with a fast WAL and flushes asynchronously, or (c) uses S3 Express One Zone / quorum writes across multiple Express buckets to shrink the tail directly.

## 3. Throughput & Request-Rate Limits

**S3.** Since July 2018, S3 guarantees **at least 3,500 PUT/COPY/POST/DELETE requests/sec** and **5,500 GET/HEAD requests/sec**, *per partitioned prefix*, with **no limit on the number of prefixes per bucket** — so parallelizing across 10 prefixes can reach 55,000 read req/s, etc. ([S3 request-rate increase announcement, 2018](https://aws.amazon.com/about-aws/whats-new/2018/07/amazon-s3-announces-increased-request-rate-performance), [S3 Performance design patterns](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-design-patterns.html)). Above those figures, S3 auto-scales its internal partitioning of the keyspace to absorb more load, but scaling is **gradual** (minutes, not instant): a sudden burst can produce transient `503 Slow Down` responses until S3 finishes repartitioning; AWS recommends exponential backoff (its SDKs do this automatically) and, for planned high-rate launches, ramping traffic up gradually rather than jumping straight to peak.

Key practical nuance for key/prefix design: **randomized-prefix hashing (the old "add hex entropy at the front of the key" advice) is now obsolete** for pure throughput purposes — since the 2018 change, S3 partitions automatically based on request patterns regardless of lexical structure, and sequential/logical prefixes (e.g., date-based) work fine at moderate rates. Hash-prefixing is only still relevant if a single logical prefix will **sustainably** exceed ~3,500 write-req/s or ~5,500 read-req/s, in which case spreading writes across several prefixes (e.g., `shard-00/`, `shard-01/`, …) lets S3 allocate separate partitions instead of hot-spotting one ([S3 key design best practices](https://hidekazu-konishi.com/entry/amazon_s3_object_key_design_best_practices.html), [Earthmover — S3 prefix scalability](https://www.earthmover.io/blog/exploring-icechunk-scalability/)). For a log system, this maps directly to the WarpStream/AutoMQ pattern of spreading topic-partition object writes across multiple prefixes and batching many logical partitions into a single physical PUT to keep steady-state request rate well under these ceilings. S3 Express One Zone directory buckets separately support up to **2,000,000 reads/s and 200,000 writes/s by default** (with quota increases available), reflecting its design for far higher steady-state request rates ([S3 Express One Zone launch notes](https://aws.amazon.com/about-aws/whats-new/2023/11/amazon-s3-express-one-zone-storage-class)).

**GCS.** Buckets start with roughly **1,000 object-write requests/s** and **5,000 object-read requests/s** of "free" IO capacity; beyond that, GCS auto-scales by distributing load across more backend servers, but — like S3 — this **takes on the order of minutes** ([GCS request-rate and access-distribution guidelines](https://docs.cloud.google.com/storage/docs/request-rate)). Google's explicit guidance: if you expect to exceed these thresholds, **ramp up gradually, doubling request rate roughly every 20 minutes**, and this applies whenever accessing a **new key range** (e.g., a freshly-created prefix), since GCS's index-range hotspot detection needs time to redistribute load; failing to ramp gradually causes temporary elevated latency/error rates rather than hard failures. Functionally this is the same operating model as S3: near-unbounded aggregate throughput, achieved through automatic index/keyspace partitioning, but requiring gradual ramp and prefix diversity to reach it — a log system writing to GCS should apply the same multi-prefix sharding discipline as for S3.

## 4. Pricing Model Detail

*(US region reference pricing, subject to change; see cited pricing pages for current/regional rates.)*

**S3 Standard, us-east-1** ([AWS S3 Pricing](https://aws.amazon.com/s3/pricing/), [CloudZero S3 pricing guide](https://www.cloudzero.com/blog/s3-pricing/)):
- Storage: **$0.023/GB-month**.
- **PUT/COPY/POST/LIST**: **$0.005 per 1,000 requests**.
- **GET/SELECT**: **$0.0004 per 1,000 requests** (~12.5x cheaper per-request than PUT).
- DELETE and CANCEL: free.
- Same-region intra-AWS transfer (e.g. S3→EC2 same AZ): free; cross-AZ within region ~$0.01/GB; cross-region (bucket-to-bucket replication or cross-region reads): ~$0.02/GB.
- Internet egress: first 100GB/month free (aggregated across AWS services on an account), then roughly **$0.09/GB** for the first 10TB, stepping down at higher volume tiers (~$0.085/GB, ~$0.07/GB).

**S3 Express One Zone** ([Express One Zone price cut, April 2025](https://aws.amazon.com/blogs/aws/up-to-85-price-reductions-for-amazon-s3-express-one-zone/)): storage **~$0.11/GB-month** (roughly **5x** Standard's per-GB cost, following an 85%/31% price cut in April 2025), but **request pricing was slashed** — reads now **$0.00003 per 1,000 requests** (an 85% cut) and writes cut 55%, plus per-GB data-transfer charges for uploads/retrievals reduced 60% and now applied uniformly (not just to bytes over 512KB). Net effect: Express One Zone is much more expensive per GB stored but dramatically cheaper per request and far lower latency — the intended pattern (used by WarpStream and S2, §8) is to land freshly-produced data in Express One Zone for a short retention window, then **compact/tier it down into S3 Standard** for long-term storage, capturing low latency on the "hot" write path while keeping steady-state storage cost low.

**GCS Standard** ([Google Cloud Storage pricing](https://cloud.google.com/storage/pricing), [CloudZero GCS pricing guide](https://www.cloudzero.com/blog/gcp-storage-pricing/)):
- Storage: **$0.020/GB-month** (Iowa/South Carolina/Ohio/Oregon/Dallas) to **$0.0253/GB-month** (N. Virginia, LA, and a few other regions); Nearline ~$0.010, Coldline ~$0.004, Archive ~$0.0012/GB-month.
- Operations are billed as **Class A** (writes, list — the expensive tier) and **Class B** (reads, gets — the cheap tier), roughly analogous to S3's PUT/GET split; 2026 pricing changes raised Class A/B rates in several tiers (e.g., Coldline Class B doubled from $0.05→$0.10 per 10,000 ops, Class A from $0.10→$0.20 per 10,000 ops) ([GCS pricing-change announcement](https://cloud.google.com/storage/pricing-announce)).
- Reads within the same region/multi-region are free; egress follows tiers similar to S3: **Premium Tier internet egress ≈$0.12/GB** for the first 1TB, ≈$0.11/GB for 1–10TB, ≈$0.08/GB above 10TB (only the first 1 GiB/month free); same-continent inter-region ≈$0.01/GB; intercontinental up to ≈$0.08/GB; a cheaper **Standard Tier** network path exists at ≈$0.085/GB with a larger (200GiB) free egress allowance, trading some latency/routing quality for cost ([GCP egress pricing overview](https://www.cloudbolt.io/gcp-cost-optimization/gcp-egress-pricing/), [EgressCost.com GCP breakdown](https://egresscost.com/gcp/)).
- **Anywhere Cache / Rapid Cache**: billed as a **per-GB, per-hour, pro-rated-to-the-second** storage fee on top of normal storage, but reads served from cache are priced **below** Class B and incur **no retrieval fee**, giving a way to absorb bursty hot-read fan-out cheaply ([Anywhere Cache docs](https://cloud.google.com/storage/docs/anywhere-cache)).

**The economic case for large batch sizes.** This is the single most important cost lever for a log system: **PUT-class requests are ~12x the price of GET-class requests on S3** (and similarly skewed on GCS's Class A vs Class B), so systems that flush small, frequent batches pay disproportionately in request costs, not storage. AutoMQ's own numbers make this concrete: **S3 Standard PUT at $0.005/1,000 requests means a naive service issuing 10,000 writes/sec would cost ~$130,000/month in PUT requests alone** ([AutoMQ — Deep dive into building Kafka on S3](https://www.automq.com/blog/deep-dive-into-the-challenges-of-building-kafka-on-top-of-s3)). This is precisely why every production object-storage-native log system (WarpStream, AutoMQ, S2) **batches many producer records — often across many distinct topic-partitions — into a single larger object per PUT**, trading (a) a few hundred ms of added buffering latency and (b) background compaction complexity, for (c) 1–2 orders of magnitude lower request cost. The same logic applies to LIST avoidance: AutoMQ explicitly notes that LIST-based metadata discovery "performs poorly" and cost-scales badly, which is why these systems maintain their own metadata/commit log (either external, like WarpStream's control plane, or embedded via meta-object convention, like AutoMQ's meta streams) rather than relying on bucket listing to discover committed segments.

## 5. Multipart / Resumable Upload Semantics

**S3 multipart upload** ([S3 multipart upload limits doc](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html)):
- Minimum part size: **5 MiB** for all parts except the **last part**, which has no minimum (can be any size, including a few bytes).
- Maximum part size: 5 GiB; maximum object size via multipart: 5 TiB; maximum **10,000 parts** per upload.
- AWS recommends switching from single-shot PutObject to multipart once an object exceeds ~100MB.
- Parts can be uploaded in parallel and in any order, and the upload can span hours (up to the configured abort/lifecycle policy); this is the natural mechanism for **streaming writers of unknown final size** — a log-storage layer accumulating a segment can open a multipart upload, flush accumulated buffer chunks as parts as they fill (each ≥5MiB except the trailing part), and only "seal" the object (`CompleteMultipartUpload`) once the segment is closed, without ever needing to know the final size up front. Since Aug/Nov 2024, `CompleteMultipartUpload` also supports **conditional-write preconditions** (see §6), letting a segment-sealing commit be atomic and safe against concurrent sealers.

**GCS resumable and streaming uploads** ([GCS resumable uploads](https://docs.cloud.google.com/storage/docs/resumable-uploads), [GCS streaming uploads](https://docs.cloud.google.com/storage/docs/streaming-uploads)):
- **Resumable uploads** split a transfer into chunks (chunk size should be a multiple of **256 KiB**, except the final chunk) and support **unknown total size at start** — clients send `Content-Range: bytes 0-524287/*` (using `*` in place of total size) for interim chunks and only supply the final size on the last chunk. This is functionally the GCS analogue of S3's multipart-upload-for-unknown-size pattern, and is what a GCS-backed log writer would use to stream a growing segment without pre-committing to its final byte count.
- **Parallel composite uploads** let a client upload several component objects in parallel and then have GCS `compose` them server-side into one final object — useful when segment content can be produced out of order or from multiple workers, though composed objects have their own constraints (max 32 source components per compose call, and CRC32C-based composition rather than a true streaming multipart API like S3's).
- GCS also supports plain HTTP chunked-transfer-encoding uploads for simpler unknown-length streaming without the resumable-session bookkeeping, at the cost of losing the resumability (restart) property.

For a log system, both mechanisms serve the same architectural role: **decouple "write bytes as they arrive" from "seal object at unknown final size,"** letting the storage layer accumulate a segment/batch object incrementally rather than buffering the entire segment in memory before a single atomic PUT.

## 6. Retention, Compaction & Coordination-Free Commit Protocols

Because a log system built on object storage cannot rely on a filesystem or a coordination service (ZooKeeper/Raft-over-disk) for metadata by default, three object-store primitives become load-bearing for implementing compaction/retention/commit safely:

**Lifecycle policies (auto-expiry).** Both providers support **rule-based automatic expiration** of objects by age/prefix, which is the natural mechanism for enforcing log retention (e.g., "delete segment objects older than 7 days") without the application having to issue explicit DELETEs. On S3, lifecycle rules run on a **daily schedule (00:00 UTC)** and, once an object qualifies, it's queued for async backend deletion rather than removed instantly — relevant if a retention SLA needs sub-day precision, since the actual delete has queueing latency on top of the daily evaluation cadence ([S3 NoncurrentVersionExpiration doc](https://docs.aws.amazon.com/AmazonS3/latest/API/API_NoncurrentVersionExpiration.html)). Both S3 and GCS lifecycle engines support transitioning objects between storage classes (e.g., Standard → Standard-IA/Nearline → Glacier/Archive) on the same schedule, which maps naturally onto tiered retention (hot Express/Standard for recent segments, cold/archive class for long-tail compliance retention).

**Versioning.** S3 bucket versioning keeps prior object versions around after an overwrite/delete; combined with `NoncurrentVersionExpiration` lifecycle rules, a system can retain a bounded number of prior versions (up to 100) for a bounded number of days before permanent deletion — useful as a safety net for accidental overwrite/corruption during compaction, though it adds storage cost if not actively pruned ("if you never clean up noncurrent versions, storage costs accumulate silently"). GCS has an equivalent object-versioning feature with the same noncurrent-version-cleanup pattern.

**Conditional writes — the key primitive for coordination-free commits.**
- **GCS** has supported **generation-based preconditions** (`ifGenerationMatch` / `x-goog-if-generation-match`) since essentially its inception: a write (or delete) can be conditioned on the target object's current generation number matching an expected value, returning `412 Precondition Failed` on mismatch. Setting `ifGenerationMatch=0` is the canonical GCS idiom for **"create only if the object doesn't already exist"** (compare-and-swap semantics) — exactly the primitive needed to implement an append-only commit log or a leader-election/fencing token directly as GCS objects, with zero external coordination service ([GCS request preconditions doc](https://docs.cloud.google.com/storage/docs/request-preconditions)).
- **S3** lacked this entirely until **August 2024**, when AWS added conditional writes via the `If-None-Match` header on `PutObject`/`CompleteMultipartUpload` (supporting "create if absent"), and then in **November 2024** added `If-Match` (ETag-based "update only if unmodified") ([S3 conditional writes announcement, Aug 2024](https://aws.amazon.com/about-aws/whats-new/2024/08/amazon-s3-conditional-writes), [If-Match addition, Nov 2024](https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-s3-functionality-conditional-writes)). This closed a long-standing gap that had forced S3-based systems (WarpStream, Delta Lake, Iceberg, etc.) to run an **external transactional metadata store** (DynamoDB conditional-writes, or a proprietary control plane) purely to get compare-and-swap semantics for commit pointers — pre-2024, S3 alone could not safely implement "commit segment N only if no one else already committed segment N." AWS extended this further in 2025 with **conditional writes on copy operations (Oct 2025)** and **conditional deletes in general-purpose buckets (Sep 2025)**, rounding out the primitive set. Notably, this is available **at no additional charge**.

Practically: this means a **2024+ S3-based log system can implement metadata/commit protocols (e.g., "the next segment index is N, write object `segment-N` only if it doesn't exist yet") directly against S3 using `If-None-Match: *`**, without a separate coordination service — GCS has offered this since day one via generation preconditions. This is a meaningful design-space convergence: it's now plausible to build a Raft-free, ZooKeeper-free "single source of truth" commit log purely out of object-store conditional PUTs on both providers, though most production systems (WarpStream) still layer a purpose-built metadata service on top for query performance and richer transactional semantics beyond single-key CAS.

> Cross-reference: see [06-distributed-systems-design-challenges.md](06-distributed-systems-design-challenges.md) §1 for how this primitive plugs into (or replaces) an external metadata store.

## 7. Durability Guarantees

Both S3 Standard and GCS Standard/multi-region classes advertise **"eleven nines" (99.999999999%) annual durability** — meaning, per AWS's own framing, that if you store 10 million objects, you should expect to lose on average **one object every 10,000 years**, or equivalently, storing a billion objects you'd expect to lose roughly one every 10 years ([S3 Storage Classes page](https://aws.amazon.com/s3/storage-classes/), [durability explainer](https://medium.com/@ayogun/how-much-durable-aws-s3-is-a3b2ce789c29)). This is achieved through erasure coding / redundant storage across a minimum of 3 Availability Zones (for multi-AZ classes) plus continuous integrity checking and self-healing against silent bit-rot and drive failure — it is a statement about **data loss**, distinct from **availability** (uptime SLA, typically "only" 99.9–99.99%, i.e., the object might be briefly unreachable but is not lost).

This durability figure is the foundation of the entire "object storage as sole source of truth" architecture pattern used by WarpStream, AutoMQ, and S2: rather than replicating each record across N broker disks (the classic Kafka ISR model), these systems write once to object storage and treat that single durable copy as sufficient, because the provider's internal replication already exceeds what a 3-broker Kafka cluster achieves, at a fraction of the cost (no cross-AZ replication traffic, no broker-disk provisioning). The important caveat is that **S3 Express One Zone is explicitly single-AZ** and therefore does **not** carry the same multi-AZ durability profile as S3 Standard — this is exactly why WarpStream and S2 both write to **a quorum across multiple Express One Zone directory buckets in different AZs** rather than trusting a single Express bucket, manually reconstructing multi-AZ durability at the application layer to get Express's latency without accepting single-AZ risk ([WarpStream S3 Express blog](https://aws.amazon.com/blogs/storage/how-warpstream-enables-cost-effective-low-latency-streaming-with-amazon-s3-express-one-zone/), [S2.dev intro](https://s2.dev/blog/intro)).

## 8. Published Benchmarks & Engineering War Stories

- **WarpStream** (Kafka-compatible, built with **zero local disks**, all data in object storage): benchmarked **~400–600ms p99 write latency** and **<1.5s p99 end-to-end** on S3 Standard; migrating hot data to **S3 Express One Zone** cut end-to-end latency roughly **4x** (p99 produce ≈169ms, median ≈105ms), and its "Lightning Topics" delayed-sequencing technique pushed median latency down to **33ms**. Because Express One Zone storage is **~8x more expensive per GB** than Standard, WarpStream's Agents **write new data to Express, then background-compact it into S3 Standard** for long-term storage — capturing low latency on the hot path while controlling storage cost. For durability despite Express's single-AZ nature, WarpStream writes to **multiple directory buckets and acknowledges only after quorum**, tolerating loss of a whole AZ ([AWS Storage Blog — WarpStream + S3 Express](https://aws.amazon.com/blogs/storage/how-warpstream-enables-cost-effective-low-latency-streaming-with-amazon-s3-express-one-zone/), [WarpStream benchmark/TCO Medium post](https://medium.com/@warpstream/warpstream-s3-express-one-zone-benchmark-and-total-cost-of-ownership-458791998677), [WarpStream architecture docs](https://docs.warpstream.com/warpstream/overview/architecture)). Architecturally, WarpStream **separates data (object storage) from metadata** (a purpose-built external metadata store), and never acknowledges a produce request until the data is durably in object storage *and* committed in the metadata store — deliberately not relying on S3 alone as the commit authority, despite S3's own durability being sufficient for the bytes themselves. See [01-warpstream-architecture.md](01-warpstream-architecture.md) for the full architecture writeup.

- **AutoMQ** (also Kafka-protocol-compatible, "diskless" architecture): quantified the core tension directly — **S3 GetObject median latency ~15ms, P90 ~60ms**, versus **20–100μs for local NVMe (roughly 1000x faster)**, and calculated that a naive **10,000 writes/sec workload issuing one PUT per write would cost ~$130,000/month** just in S3 PUT request fees at $0.005/1,000 requests. Their answer is a pluggable **Write-Ahead Log** in front of object storage: an EBS-backed WAL gives sub-10ms write latency, an FSx/NFS-backed WAL gives ~6ms average / ~13ms p99, and pure S3-as-WAL trades latency for zero-disk simplicity. They batch writes into two object types — **Stream Set Objects** (multi-partition, WAL-style) and **Stream Objects** (single-partition, post-compaction) — specifically to keep S3 request rates low, and explicitly flag that **LIST-based metadata discovery performs poorly at scale**, hence their own meta-stream indexing layer instead of relying on bucket listings ([AutoMQ — Deep dive into Kafka-on-S3 challenges](https://www.automq.com/blog/deep-dive-into-the-challenges-of-building-kafka-on-top-of-s3), [AutoMQ WAL storage docs](https://docs.automq.com/automq/architecture/s3stream-shared-streaming-storage/wal-storage), [AWS Storage Blog — AutoMQ+FSx sub-10ms](https://aws.amazon.com/blogs/storage/achieving-sub-10ms-latency-and-94-cost-savings-with-diskless-kafka-using-automq-and-amazon-fsx-for-netapp-ontap/)). See [03-competitive-landscape.md](03-competitive-landscape.md) for more on AutoMQ.

- **S2.dev** ("the Stream Store," purpose-built log-as-a-service on object storage): reports **p99 <500ms end-to-end** on its S3-Standard-backed **Standard** class and **p99 <50ms** on its **Express** class, the latter built as **a quorum of three S3 Express One Zone buckets**, explicitly targeting latency competitive with disk-based cloud streaming systems. S2 multiplexes records from many logical streams into shared chunks specifically to hit an optimal object write size, and uses a verifiable quorum-write protocol across the three Express buckets for durability without waiting on S3 Standard's slower replication path ([S2.dev — Introducing S2](https://s2.dev/blog/intro)).

**Common thread across all three:** raw synchronous object-store latency (hundreds of ms on Standard tiers) is fundamentally incompatible with sub-second produce-ack SLAs unless mitigated by (1) an intermediate low-latency WAL, (2) S3 Express One Zone / equivalent low-latency tiers with application-level multi-AZ quorum reconstruction, and/or (3) aggressive batching of many logical partitions into few physical objects — and that same batching is *also* the dominant lever for controlling S3/GCS request-pricing cost, making latency-optimization and cost-optimization point in the same direction (larger, less frequent object writes) for this workload class.
