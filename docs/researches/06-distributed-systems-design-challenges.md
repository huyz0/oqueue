# Building a Kafka-Compatible Log on Object Storage: Core Distributed-Systems Design Problems

> **⚠️ CORRECTION (2026-08-13) — AutoMQ claims in this document.** Statements here about AutoMQ's **EBS-backed WAL** (sub-10ms produce latency) and **EBS Multi-Attach failover** ("within milliseconds") were taken from AutoMQ's blog and **do not match their shipping code**. ## Introduction

Kafka's original design assumes storage primitives that object stores fundamentally do not provide: low-latency sequential append, atomic compare-and-swap on a byte range, and cheap random reads from many small files. Object stores (S3, GCS, Azure Blob) instead offer high-latency (tens to hundreds of milliseconds), high-throughput, immutable, whole-object PUT/GET operations, with durability and internal replication opaque to the client. Every system that has attempted to put Kafka's core log semantics — ordered offsets, low produce latency, log compaction, exactly-once delivery, and fast consumer-group rebalancing — on top of object storage has had to re-derive these semantics from a fundamentally different set of primitives. This report surveys the resulting design space, drawing on the concrete architectures of WarpStream, AutoMQ, and Redpanda, the in-progress KIP-1150 "Diskless Topics" effort in Apache Kafka, and general distributed-systems theory (conditional writes as compare-and-swap, virtualized shared logs such as Meta's Delos).

## 1. The Metadata Problem: Who Assigns the Next Offset?

Kafka's offset is a strictly monotonic per-partition sequence number, traditionally assigned by the single partition leader as records are appended to its local log. Object storage provides no such mechanism — a PUT is not an append, there is no partition-scoped atomic counter, and per-object PUT latency (tens to hundreds of ms) is orders of magnitude too slow to serialize every record individually. Every diskless design therefore separates "durably storing bytes" from "deciding what offset those bytes occupy," and the central architectural question becomes *where the ordering decision is made and how it is made consistent across concurrent writers*.

**Option A — External strongly-consistent metadata store.** The dominant pattern is to keep an external, replicated, linearizable metadata service that maps `(topic-partition, offset-range) → object location`, and to treat *committing this mapping* as the actual "commit point" of the write, distinct from the object-storage PUT. WarpStream's Agents write a batch of records (spanning many topic-partitions) into a single file, then commit the file's metadata to WarpStream's **Cloud Metadata Store**, a replicated state machine where "every metadata operation is journaled to a strongly-consistent log storage system before being executed... and acknowledged back to the Agent." Only after both the object-storage write *and* the metadata commit succeed does the Agent ack the producer — this is the actual linearization point for offset assignment ([WarpStream Architecture](https://docs.warpstream.com/warpstream/overview/architecture); [WarpStream Write Path](https://docs.warpstream.com/warpstream/overview/architecture/write-path)). Critically, offset order is decided **retroactively, at metadata-commit time**, not at flush time — this lets many Agents write to the same partition concurrently while a single serialization point (the metadata store) assigns the final order ([WarpStream retroactive tombstones](https://www.warpstream.com/blog/unlocking-idempotency-with-retroactive-tombstones)). For multi-region durability, WarpStream backs this metadata layer with globally-consistent, multi-region databases — AWS DynamoDB Global Tables or GCP Spanner — with active-active regional control planes and automatic leader election to decide which region owns writes at any moment ([No record left behind](https://www.warpstream.com/blog/no-record-left-behind-how-warpstream-can-withstand-cloud-provider-regional-outages)).

KIP-1150's emerging design (elaborated in the follow-on KIPs 1163/1164) converges on the same shape under the name **Batch Coordinator**: a pluggable, centralized order-preserving sequencer that brokers report file-and-offset-range coordinates to after an object write completes. The default reference implementation journals through an internal Kafka topic (`__diskless-metadata`) backed by SQLite for compact, queryable local state; Aiven's production prototype instead backs the coordinator with PostgreSQL and layers an Infinispan distributed cache across availability zones so read replicas don't all have to hit the write leader ([2minutestreaming: Diskless Kafka Topics](https://blog.2minutestreaming.com/p/diskless-kafka-topics-kip-1150); [Aiven: Hitchhiker's Guide to Diskless Kafka](https://aiven.io/blog/guide-diskless-apache-kafka-kip-1150)). This is architecturally the same pattern as Meta's **Delos** virtual-log design, where a `MetaStore` — "a single versioned register supporting a conditional write" — is the one piece of strongly-consistent state that decides how the logical log address space maps onto physical storage segments ("Loglets"), while the segments themselves can be served by disaggregated, higher-throughput storage ([Virtual Consensus in Delos, OSDI'20](https://www.usenix.org/conference/osdi20/presentation/balakrishnan); [morning paper summary](https://blog.acolyer.org/2020/11/09/delos/)). In both Delos and the Kafka-on-object-storage systems, the metadata/ordering plane is deliberately kept small and centralized (or quorum-replicated) because it is the only component that truly needs consensus; bulk data movement is pushed off to storage that need not be consistent in the same way.

**Option B — Object-storage-native conditional writes as the CAS primitive.** A second, structurally different pattern dispenses with an external metadata service and uses the object store's own conditional-write support as the sequencing primitive. Since November 2024, S3 supports `If-Match`/`If-None-Match` conditional PUTs, and GCS has long supported generation-match preconditions (`x-goog-if-generation-match`); both let a client attempt to write only if an object does or does not already exist at a given key, which is a genuine compare-and-swap ([Amazon S3 conditional writes announcement](https://simonwillison.net/2024/Nov/26/s3-conditional-writes/); [AWS: building multi-writer applications with native controls](https://aws.amazon.com/blogs/storage/building-multi-writer-applications-on-amazon-s3-using-native-controls/)). A minimal distributed log can then be built by naming each record (or batch) object by its intended offset and writing with `IfNoneMatch: "*"`: only the first writer for a given offset succeeds, and concurrent writers for the same slot are naturally rejected, serializing the log without any external coordinator ([Building a distributed log using S3 in <150 lines of Go](https://avi.im/blag/2024/s3-log/)). This pattern is also used for **leader election** in object-storage-based systems generally — using conditional PUT/If-Match on a "lease" object to elect a single writer for a bounded period ([Leader Election with S3 Conditional Writes](https://www.morling.dev/blog/leader-election-with-s3-conditional-writes/); [Leader election with S3 and If-Match](https://quanttype.net/p/leader-election-with-s3-and-if-match/)). The tradeoff is throughput and latency: every offset assignment now costs a full object-storage round trip (tens to hundreds of ms) and, at high contention, a storm of failed conditional PUTs that must retry, plus no efficient way to recover "the last committed offset" other than a linear scan unless the design layers on additional indexing — the demo implementation above explicitly defers this ("recovery works via `LastRecord()`, which scans all objects... a linear operation lacking optimization") ([avi.im: S3-backed log](https://avi.im/blag/2024/s3-log/)). In practice, no production system reviewed here uses *pure* conditional-write sequencing for the hot path at scale — it is used either as a building block for leader election/fencing, or in low-throughput/cold-path roles, because the latency and contention costs make it unsuitable for assigning offsets to a high-QPS partition directly. See [04-object-storage-s3-gcs.md](04-object-storage-s3-gcs.md) §6 for the conditional-write primitives themselves.

**Option C — Hybrid: consensus stays local, only bulk bytes go remote.** Redpanda's **Cloud Topics** takes the opposite tack from WarpStream/KIP-1150: it keeps the "brains" — Raft-based consensus, partition metadata, and offset bookkeeping — on local, high-performance NVMe disks attached to a stateful broker (exactly Kafka's classical replicated-log architecture), and only streams the message *payload* bytes directly to object storage in a "write pass-through model." Because ordering is still decided by an in-process Raft leader with disk-speed writes, Redpanda's design preserves exactly-once semantics, transactions, and idempotent producers "with the same guarantees as standard topics," at the cost of retaining a leader-per-partition and local disks as a piece of required state ([Redpanda Cloud Topics](https://www.redpanda.com/data-streaming/cloud-topics-write-to-object-storage)). This sits at the opposite end of the spectrum from WarpStream's fully leaderless design, illustrating a core axis of the design space: how much consensus state you are willing to keep local (fast, but requiring replicated disks and broker affinity) versus how much you push into a shared external metadata service (enables statelessness, but adds a network hop and a new component that must itself be highly available).

**AutoMQ's take** sits closer to Option A but reuses Kafka's own metadata plane: it keeps Kafka's KRaft (Raft-based) controller quorum for cluster/partition metadata and layers "object metadata and scheduling logic" for its S3Stream storage engine on top, rather than inventing a new external store — brokers retain Kafka-style partition ownership (a single broker is authoritative for a given partition's offset assignment at a time) but the underlying bytes live in a WAL and then S3 ([AutoMQ vs WarpStream comparison](https://www.automq.com/blog/warpstream-vs-automq-object-storage-backed-kafka); [AutoMQ S3Stream overview](https://docs.automq.com/automq/architecture/s3stream-shared-streaming-storage/overview)). This means AutoMQ still has a leader-assigns-offsets model per partition (like classic Kafka), just with the physical log replaced by S3Stream; it trades away the fully leaderless elasticity that WarpStream and KIP-1150 pursue in exchange for reusing much more of Kafka's existing consistency logic.

## 2. The Write-Latency/Batching Problem

Object-storage PUT latency (roughly 50–400ms depending on provider, region, and object class) is one to two orders of magnitude higher than Kafka's typical produce-ack latency (single-digit to low-double-digit ms). No diskless design can hide this without either (a) batching many records into fewer, larger PUTs and accepting the batch-formation delay as added latency, or (b) introducing a local low-latency durability layer ("fast path") that decouples the client-visible ack from the object-storage write.

**Batching strategy.** Every system studied uses the same dual-trigger flush policy: flush on a **time threshold** or a **size threshold**, whichever comes first. WarpStream's Agents buffer in memory for a configurable `batchTimeout` (default 250ms, tunable down to 25ms) or until 8 MiB accumulates ([WarpStream Write Path](https://docs.warpstream.com/warpstream/overview/architecture/write-path); [WarpStream Low Latency Clusters](https://docs.warpstream.com/warpstream/kafka/advanced-agent-deployment-options/low-latency-clusters)). KIP-1150's reference design uses the identical 250ms/8MiB defaults ([2minutestreaming](https://blog.2minutestreaming.com/p/diskless-kafka-topics-kip-1150)). This is not a coincidence: at these batch sizes, the number of PUT operations per second stays low enough to keep object-storage request costs manageable (S3 PUTs are billed per-request, roughly $0.005/1,000 ops), while the batch window bounds the worst-case added latency a producer experiences.

**Multi-tenant / cross-partition batching.** The key efficiency lever these systems share — and a genuine departure from how tiered-storage systems traditionally structure objects — is writing **one object per flush interval containing interleaved records from many different topic-partitions and many different producers**, rather than one object per partition. WarpStream explicitly avoids "a naive one-file-per-partition approach": "individual files contain data from many different topic-partitions simultaneously," which amortizes the fixed per-PUT cost and latency across all tenants sharing an Agent ([WarpStream Architecture](https://docs.warpstream.com/warpstream/overview/architecture); [WarpStream noisy neighbors](https://www.warpstream.com/blog/getting-rid-of-kafka-noisy-neighbors-without-having-to-buy-a-mansion)). This is the direct object-storage analogue of "group commit" in traditional databases, generalized across tenants instead of just across transactions on one connection. The resulting objects are then fragmented across many logical partitions, which pushes complexity into the metadata layer (tracking many small offset-ranges per object) and into background compaction (see §4) to later consolidate per-partition data into contiguous, efficiently-readable ranges. AutoMQ's `deep-dive` post on building Kafka on S3 frames this as an unavoidable **fragmentation-vs-cost tradeoff**: batching to control PUT cost/latency necessarily fragments a partition's logical byte stream across objects, and a background compaction process must "asynchronously consolidate data from the same partition onto the least possible number of objects" ([AutoMQ: challenges of building Kafka on S3](https://www.automq.com/blog/deep-dive-into-the-challenges-of-building-kafka-on-top-of-s3)).

**Latency/cost/durability curve.** The batch-timeout knob is a direct, tunable dial on this tradeoff: shorter timeouts reduce produce latency but increase PUT-operation count and cost (and, on some tiers, transfer cost when objects fall below the free per-request byte allowance); longer timeouts amortize cost across more data but add latency and increase blast radius per lost/delayed object. WarpStream's S3 Express One Zone benchmarks show this concretely: end-to-end p99 latency drops roughly 4x versus S3 Standard (from ~400–600ms p99 write / <1.5s p99 end-to-end, down substantially with Express One Zone), at roughly 8x higher per-GB storage cost, which WarpStream mitigates by tiering data out to S3 Standard shortly after ingest ([WarpStream + S3 Express One Zone](https://aws.amazon.com/blogs/storage/how-warpstream-enables-cost-effective-low-latency-streaming-with-amazon-s3-express-one-zone/)). WarpStream is explicit that this whole architecture accepts p99 latency "in the hundreds of milliseconds" versus Kafka's classic single-digit-ms in exchange for eliminating partition-pinned broker capacity limits and enabling trivial autoscaling ([The Case for Shared Storage](https://www.warpstream.com/blog/the-case-for-shared-storage)).

**Decoupling durability from sequencing ("lazy log").** WarpStream's **Lightning Topics** feature is the most concrete example of a further optimization within the "no local fast path" family: rather than adding a WAL, it decouples *durability* (bytes safely in object storage) from *sequencing* (offset assigned in the metadata store), based on the observation — attributed to the "LazyLog" line of research — that "durability needs to be ensured upfront, sequencing rarely does." In the classic flow, the Agent writes the file, commits offset metadata, *then* acks the client. In Lightning Topics, the Agent writes the file and acks the client immediately, deferring the metadata commit (and therefore true offset assignment) to an asynchronous background step; this "cuts the latency of writing data... in half," reaching median 33ms / p99 50ms when combined with S3 Express One Zone. The tradeoff is a loss of *external consistency* (records can be sequenced out of order relative to submission order), producers get offset 0 back in the produce response, and idempotent/transactional producers are explicitly rejected, since the true offset isn't known at ack time. A background "slow path" scans object storage for uncommitted files and replays them into the metadata store to guarantee eventual sequencing and zero data loss even if the async commit fails, and an even more aggressive "Ripcord Mode" lets producers keep accepting writes durably even during a full control-plane outage, at the cost of blocking consumers until the control plane recovers ([WarpStream: The Art of Being Lazy(log)](https://www.warpstream.com/blog/the-art-of-being-lazy-log-lower-latency-and-higher-availability-with-delayed-sequencing)).

**Local WAL fast path.** AutoMQ takes the opposite approach: instead of accepting object-storage latency on the ack path (with or without lazy sequencing), it interposes a **local write-ahead log** that the produce ack depends on, and treats the S3 upload as a fully asynchronous background step. "The broker receives the message [and] returns an 'I got your message' response only when it persists in the WAL," after which "data is then later written to object storage asynchronously." Production deployments choose among EBS WAL, Regional EBS WAL, or NFS WAL as the durable medium ([AutoMQ WAL Storage](https://www.automq.com/docs/automq/architecture/s3stream-shared-streaming-storage/wal-storage); [AutoMQ: Kafka on S3 in 100 lines of code](https://www.automq.com/blog/automq-s3-wal-integration)). This buys single-digit-ms produce latency (AutoMQ advertises sub-10ms) but reintroduces exactly the kind of local, per-broker durable state that fully diskless designs try to eliminate — it must be solved with block-storage features like EBS Multi-Attach so a healthy broker can take over another's WAL volume within milliseconds on failure, upload the (typically ~500MB, fixed-size) unflushed WAL contents to S3, then release the volume ([AutoMQ + AWS FSx blog](https://aws.amazon.com/blogs/storage/achieving-sub-10ms-latency-and-94-cost-savings-with-diskless-kafka-using-automq-and-amazon-fsx-for-netapp-ontap/)). This is the clearest instance of the "fast path adds complexity/local state" tradeoff named in the task: AutoMQ recovers Kafka-classic ack latency but must re-solve broker-affinity and failover problems that a purely stateless-agent design (WarpStream, KIP-1150) avoids by construction. Redpanda Cloud Topics makes essentially the same choice at the consensus layer, keeping Raft on local NVMe for the same reason.

## 3. The Read/Caching Problem

Since produce paths already accept batch-timeout latency, read paths must avoid re-paying object-storage GET latency (tens to hundreds of ms, e.g. "GetObject median ~15ms, p90 ~60ms" per AutoMQ's own numbers) on every consumer fetch, or streaming consumption becomes unusably slow ([AutoMQ: challenges of Kafka on S3](https://www.automq.com/blog/deep-dive-into-the-challenges-of-building-kafka-on-top-of-s3)).

**Local caching on stateless nodes.** Because Agents/brokers in these architectures are meant to be interchangeable and horizontally scalable, caches cannot rely on sticky partition ownership the way classic Kafka's page cache does; any node might serve any partition's read. AutoMQ's S3Stream layer addresses this with a hybrid cache that stores "both hot data and prefetched cold data... to accelerate reads," with separate handling of two distinct access patterns:
- **Tailing reads** — recently-produced data still resident in the write buffer/cache (equivalent to reading Kafka's page cache), served with minimal latency.
- **Catch-up reads** — historical data pulled from object storage and prefetched ahead of the consumer's read cursor to hide GET latency for sequential scans ([AutoMQ S3Stream overview](https://docs.automq.com/automq/architecture/s3stream-shared-streaming-storage/overview)).

KIP-1150's design uses a similar **per-rack (per-AZ) shared cache** rather than a per-broker cache, motivated directly by the cost of cross-AZ data transfer and the stateless-node requirement: "the first uncached look-back... naturally pays the object-store round-trip (about 100ms)... the second and third scans of neighbouring offsets... are satisfied from RAM and come in <20ms" ([Aiven: Hitchhiker's Guide to Diskless Kafka](https://aiven.io/blog/guide-diskless-apache-kafka-kip-1150)). Aiven's prototype implements this with **Infinispan**, a distributed cache library, replicating segment copies per availability zone so reads don't have to cross AZ boundaries or hit a single node — this doubles as both a read-latency optimization and a cross-AZ-egress cost optimization, since AZ-crossing traffic is separately billed on major clouds ([2minutestreaming: Diskless Kafka Topics](https://blog.2minutestreaming.com/p/diskless-kafka-topics-kip-1150)).

**Cache coherence with stateless/interchangeable nodes.** None of these systems need classic cache-invalidation protocols, because the underlying objects are immutable once written — a cached copy of an object is valid forever until the object is deleted (post-compaction or post-retention), at which point the cache entry simply becomes stale/unused rather than incorrect. This is a meaningful simplification versus mutable-backend caching: correctness only requires that the cache never serves a *file that has been logically superseded* as if it were current, which is handled by the metadata layer (the coordinator/metadata store, not the cache, decides which objects are authoritative for a given offset range) rather than by cache invalidation messages between nodes.

**Distributed mmap / cost-aware caching.** WarpStream has a dedicated engineering effort ("Minimizing S3 API Costs with Distributed mmap") aimed specifically at reducing the number of GET requests issued against object storage for hot reads by memory-mapping cached ranges across the Agent fleet rather than re-fetching per request — evidence that GET-request *count* (not just latency) is itself a first-class cost concern that caching must manage on top of latency ([WarpStream blog listing](https://www.warpstream.com/blog)).

**Sequential prefetching.** Both AutoMQ and the KIP-1150 designs explicitly lean on the fact that Kafka consumption is overwhelmingly sequential (consumers advance monotonically through a partition) to justify readahead/prefetch: once a consumer's fetch offset is known, the system speculatively fetches subsequent byte ranges (or whole objects) before they're requested, converting a chain of latency-bound single GETs into a background-pipelined stream. This mirrors how tiered-storage read-ahead works in Kafka's own tiered storage and in Redpanda's `remote_partition`/`cache_service` read path, which likewise separates "recent, local" reads from "remote, tiered" reads and applies caching mainly to the batch/streaming read pattern rather than random access ([Redpanda Tiered Storage architecture deep dive](https://www.redpanda.com/blog/tiered-storage-architecture-deep-dive)).

## 4. Compaction and Retention on Immutable Object Storage

Kafka has two retention models that must both be reprojected onto immutable, whole-object storage: **time/size-based retention** (delete whole log segments once they age out or the partition exceeds its size budget) and **key-based compaction** (retain only the latest record per key, garbage-collecting superseded values while preserving offset order for the records that remain).

**Time/size retention** maps relatively cleanly: once every offset in an object is older than the retention window (or a partition's total live data exceeds its budget), the object is dropped from the metadata mapping and physically deleted. The complication is that objects are multi-tenant and multi-partition (per §2), so a single object may contain some records eligible for deletion and others not — pure per-object deletion isn't available until *every* partition's data in that object has aged out, incentivizing periodic compaction/repacking so that objects age out uniformly rather than being pinned indefinitely by one slow-expiring partition's slice.

**Key-based compaction** is structurally harder on object storage because Kafka's classic compactor relies on cheap random-access seeks within a local file to build its offset map and then rewrite a compacted segment — an access pattern that is prohibitively expensive against remote storage, since every seek is a separate network GET. WarpStream's solution, described for its "Kafka as a KV store" compacted-topic support, avoids seeking entirely by using **two independent sequential read streams over each input file**: a first pass streams the whole file to build an in-memory map of `key-hash → latest offset` (storing 16-byte MD5 key hashes and 8-byte offsets rather than full keys/values, so millions of keys fit in ~128 MiB of RAM, mirroring Kafka's own compaction memory trick), and a second sequential pass streams the file again, consulting the map to decide which records survive into the compacted output. This costs exactly **two GET requests per input file regardless of the number of partitions or keys involved**, versus the "thousands or tens of thousands" of GETs a naive backward-seeking approach would need — and it composes naturally with WarpStream's multi-partition file layout, since a structural property normally seen as a complication (many partitions interleaved in one object) instead lets compaction amortize its two-pass cost across many partitions at once ([WarpStream: Kafka as a KV Store](https://www.warpstream.com/blog/kafka-kv-store)).

**Read amplification and background compaction as a first-class subsystem.** Because ingest-time batching deliberately fragments each partition's logical stream across many small, multi-tenant objects (§2), every diskless design needs an *always-on background compaction/consolidation job*, distinct from key-based log compaction, whose purpose is purely to reduce the number of objects a sequential partition read has to touch — i.e., to control read amplification. AutoMQ names this explicitly as a background process that "asynchronously consolidates data from the same partition onto the least possible number of objects" to improve fetch efficiency and lower per-fetch object count/cost ([AutoMQ: challenges of Kafka on S3](https://www.automq.com/blog/deep-dive-into-the-challenges-of-building-kafka-on-top-of-s3)). WarpStream's docs describe the same mechanism: Agents "compact files in object storage, which enables merging batches for the same topic-partition in different files together, improving IO access patterns for historical replays" ([WarpStream Write Path](https://docs.warpstream.com/warpstream/overview/architecture/write-path)). KIP-1150's design similarly plans "periodic merging of the small SLS [Shared Log Segment] files into larger ones," although the KIP explicitly flags this piece as still underspecified ("the KIP is still very unclear" on implementation) ([2minutestreaming](https://blog.2minutestreaming.com/p/diskless-kafka-topics-kip-1150)).

**Deletion is a distinct, delicate sub-problem.** Logically removing a file from the metadata map (via retention, compaction, or topic deletion) cannot be safely followed by immediate physical deletion from object storage, because in-flight reads may already hold a reference to that file, and because synchronous coupling between metadata deletion and object deletion creates a class of orphan-file bugs if one succeeds and the other fails. WarpStream's solution is an "optimistic deletion queue": logically-deleted file IDs are enqueued and only physically deleted after a configurable delay (which doubles as a bound on how far back in time backups/point-in-time-recovery can reach), backstopped by an asynchronous mark-and-sweep reconciliation job that periodically scans object storage for files absent from the metadata store and reclaims anything older than the deletion delay — a safety net against Agents crashing mid-deletion ([Taking out the Trash](https://www.warpstream.com/blog/taking-out-the-trash-garbage-collection-of-object-storage-at-massive-scale)). This two-phase (soft-delete-then-reap) pattern is a recurring one across log-structured storage systems generally, but the specifics of what "safe delay" means and how compaction cooperates with in-flight consumer offsets are bespoke to each implementation.

## 5. Consumer Group and Offset Management at Scale

Classic Kafka stores committed offsets in the internal `__consumer_offsets` topic, itself a regular (compacted) Kafka topic; the **group coordinator** for a given consumer group is the broker leading the specific `__consumer_offsets` partition that the group ID hashes to, and rebalances (partition reassignment on membership change) are driven through that coordinator.

In a diskless/object-storage-primary design, this internal-topic mechanism is largely displaced by the same metadata store used for offset sequencing, rather than being reimplemented as a regular topic written through the same batching/flush pipeline as user data. WarpStream stores committed consumer-group offsets directly in its **Cloud Metadata Store** rather than in an offsets topic, and because "any Agent can act as the leader for any topic, commit offsets for any consumer group, or act as the coordinator for the cluster," coordinator selection is not tied to a specific broker owning a specific partition the way it is in classic Kafka ([WarpStream Architecture search summary](https://docs.warpstream.com/warpstream/overview/architecture)). This has a direct, favorable effect on **rebalance speed**: because there is no broker-affinity state to hand off (no partition leadership to transfer, no local segment files a new leader must catch up on), reassigning which node services which partition/group is a metadata-only operation against an already-consistent store, rather than a multi-step protocol involving log-end-offset reconciliation between a new leader and its followers. This is one of the more unambiguous latency wins the shared-storage model provides over classic Kafka, where broker restarts/rebalances can take seconds to minutes while ISR catch-up and leader election complete.

The tradeoff is that offset-commit traffic, which in classic Kafka is just ordinary produce load against a special topic (and therefore automatically inherits Kafka's own scaling/partitioning), becomes instead a dependency on the metadata store's write throughput — the same store handling data-offset sequencing. WarpStream's scaling argument for this is that data-to-metadata ratio stays high enough in practice (metadata write volume is a small fraction of data write volume) that the shared metadata store doesn't become the bottleneck even at multi-GiB/s cluster throughput, reporting real customer metadata stores running at 10–30% utilization at 4.5 GiB/s of data throughput ([The Case for Shared Storage](https://www.warpstream.com/blog/the-case-for-shared-storage)). KIP-1150's design is less specific on this point in public materials reviewed, beyond committing that Diskless topics will "support all existing APIs with the same external semantics as non-Diskless topics, including... Consumer Groups/Offsets" — leaving open, as of the KIP's acceptance, whether offset storage will reuse the Batch Coordinator's store or remain a conventional (possibly still-diskless) `__consumer_offsets` topic ([KIP-1150 wiki](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1150:+Diskless+Topics)). AutoMQ, having preserved Kafka's KRaft-based broker/partition model, is closer to classic Kafka's own offset-topic mechanics, layering its S3Stream storage engine underneath rather than replacing the coordinator protocol itself ([AutoMQ vs WarpStream](https://www.automq.com/blog/warpstream-vs-automq-object-storage-backed-kafka)).

## 6. Exactly-Once and Idempotency Guarantees

Kafka's idempotent producer relies on the broker tracking, **per `(producer_id, partition)`**, the last accepted sequence number, so that retried batches (from producer-side retries after an ack timeout) can be deduplicated deterministically; transactions additionally require atomic, all-or-nothing visibility of writes spanning multiple partitions, coordinated through the transaction coordinator and marker records. Both mechanisms implicitly assume a small amount of durable, consistently-visible per-partition state co-located with whichever broker is currently the partition leader — exactly the kind of state a stateless, leaderless Agent fleet does not have by default.

**WarpStream's retroactive-tombstone approach.** Rather than blocking duplicate batches from ever reaching object storage, WarpStream lets Agents write batches without knowing in advance whether they are duplicates, then uses the metadata store to make the deduplication decision after the fact: the metadata store retains "the sequence IDs of the last 5 batches... for each tuple of `<producer_id, partition>`," and if a batch is identified as a replay, the metadata store simply never returns metadata pointing at that batch's records to consumers, even though the bytes physically remain on disk in object storage until compaction removes them. This creates "mutable views over immutable files" — logical deletion via metadata, without needing to rewrite the object ([Unlocking Idempotency with Retroactive Tombstones](https://www.warpstream.com/blog/unlocking-idempotency-with-retroactive-tombstones)). The documented costs of this approach are real: batch merging across producers is disabled when idempotency is on (since merging would break the sequence-number bookkeeping), duplicate "dead" batches consume storage and read bandwidth until compaction reclaims them, and — as of WarpStream's published known-issues — full **transactions remain unimplemented** ("supporting Kafka transactions in the future"). There are also concrete client-compatibility gaps stemming directly from the leaderless design: because any Agent can service any partition and WarpStream's dynamic load-balancing reshuffles partition "ownership" frequently to keep Agents evenly loaded, idempotent-producer clients (particularly librdkafka) see far more leadership-change signals than they expect, causing spurious `KAFKA_STORAGE_ERROR` retries, out-of-order-batch rejections, and (because WarpStream returns a constant leader epoch of 0) incompatibility with librdkafka ≥2.4's monotonic-epoch requirement — documented workarounds include disabling idempotence, using null record keys, or switching to a stickier partition-assignment strategy ([WarpStream Known Issues](https://docs.warpstream.com/warpstream/kafka/configure-kafka-client/known-issues)). This is a clear, sourced example of a "known gap in clone systems": idempotency in a fully leaderless design is achievable, but it strains protocol assumptions (stable leader epochs, one leader per partition) baked into official Kafka clients, not just into the broker/server contract.

**Lightning Topics forfeit idempotency entirely.** As noted in §2, WarpStream's low-latency Lightning Topics mode explicitly rejects idempotent-producer and transactional requests outright, because true offset assignment (needed to detect duplicate sequence numbers against a stable offset) is deferred past the point where the client is acked — illustrating a direct tension between the latency optimizations in §2 and the correctness machinery in this section ([WarpStream: Lazy(log)](https://www.warpstream.com/blog/the-art-of-being-lazy-log-lower-latency-and-higher-availability-with-delayed-sequencing)).

**Redpanda Cloud Topics's opposite tradeoff.** Because Cloud Topics keeps Raft consensus and partition state local (§1), it claims to support "exactly-once semantics, transactions, and idempotent producers" with "the same guarantees as standard topics" — trading away full statelessness specifically to avoid the idempotency/transaction complications that leaderless designs run into ([Redpanda Cloud Topics](https://www.redpanda.com/data-streaming/cloud-topics-write-to-object-storage)).

**KIP-1150's stance.** The KIP commits, at the requirements level, to preserving ordering, idempotency, transactions, and consumer groups/offsets as external-facing guarantees identical to classic topics, but defers the actual mechanism to KIP-1163/1164; independent commentary on the proposal notes that "exactly-once will stay in preview until the follow-up KIP lands," i.e., the community itself does not yet consider the EOS story solved even at the design-document stage ([KIP-1150 wiki](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1150:+Diskless+Topics); [2minutestreaming](https://blog.2minutestreaming.com/p/diskless-kafka-topics-kip-1150)). The general pattern across the field, then, is: idempotent-producer deduplication is tractable via a metadata-store-backed sequence-number table (whether centralized as in WarpStream or Raft-backed as in Redpanda/AutoMQ), but full multi-partition transactional atomicity is either not yet implemented (WarpStream), preserved only by *not* going fully leaderless (Redpanda), or still an open design question (KIP-1150).

## 7. Multi-Tenancy and Isolation

Sharing one object-storage bucket and one batching/flush pipeline across many tenants/partitions is precisely what makes the cost and latency amortization in §2 work — but it creates the classic noisy-neighbor exposure at two distinct layers: the **shared metadata store** (every tenant's offset commits compete for the same linearizable write path) and the **shared batching window** (a burst from one tenant can force early/oversized flushes, or a slow/large producer can hold up the batch that many other tenants' records are waiting in).

WarpStream's own framing of the problem describes exactly this: in a shared cluster, "high-throughput real-time analytics running alongside resource-heavy batch jobs" compete for CPU, memory, network, and disk I/O, and traditional Kafka-style static quotas (broker-level bandwidth/request-rate caps) require "upfront global planning" and don't adapt to bursty, unpredictable demand; the alternative of physically separate clusters per tenant avoids contention but reintroduces cost overhead, loses the ability to share topics across tenants, and creates offset-alignment headaches for downstream consumers like Flink/Spark that expect one coherent offset space ([Getting Rid of Kafka Noisy Neighbors](https://www.warpstream.com/blog/getting-rid-of-kafka-noisy-neighbors-without-having-to-buy-a-mansion)).

WarpStream's mitigation is **Agent Groups** — a purely service-discovery-layer partitioning of the Agent fleet into isolated pools that all still point at the same underlying object-storage buckets and the same logical Virtual Cluster/metadata store. Because Agents in different groups never need to talk to each other directly (all coordination flows through shared object storage plus the metadata store), a noisy tenant can be pinned to its own dedicated Agent Group — insulating other tenants' compute path — while still sharing the same logical cluster, topics, and consistent offset space; this also incidentally enables multi-VPC and multi-cloud-account deployments under one logical cluster ([Agent Groups / noisy neighbors](https://www.warpstream.com/blog/getting-rid-of-kafka-noisy-neighbors-without-having-to-buy-a-mansion)). Note, however, that this only isolates the **compute** layer (Agents); it does *not* fully isolate the shared metadata store's write path, which remains a single point every tenant's offset-sequencing and offset-commit traffic passes through — WarpStream's separate argument that metadata volume stays a small, low-utilization fraction of data volume (§5) is effectively the load-bearing claim that keeps this from being a bottleneck, rather than any per-tenant metadata partitioning scheme.

The multi-partition, multi-tenant object layout described in §2 (many topic-partitions interleaved in one flushed object) is itself a second, more structural form of shared fate: a single slow or throttled object-storage PUT/GET on a shared object delays every tenant whose data happens to be co-located in that object, and a single hot-partition burst that forces an early flush (hitting the size threshold before the time threshold) effectively truncates the batch window for every other tenant's data riding along in the same flush cycle. None of the sources reviewed describe a mechanism for *selectively* excluding a bursty tenant's records from a shared flush while still amortizing cost across the rest — the isolation primitives available (Agent Groups, per-topic batch-timeout tuning) operate at a coarser granularity than per-flush tenant fairness. This is a design tension inherent to the batching-for-cost-efficiency model in §2 that none of the surveyed public materials claim to have fully solved, as distinct from compute-level isolation, which is solved by physically segregating Agent pools.

## 8. Failure Modes Unique to This Architecture

Classic Kafka's durability contract — "a record is committed once it is written to the in-sync replica set (ISR)" — is defined entirely in terms of broker-local disks and a broker-to-broker replication protocol (ISR) the operator fully controls and observes. Once storage moves to object storage, durability is redefined in terms of two components neither of which is fully observable or controllable by the operator: the object store's own (opaque) internal replication, and an external metadata store that must itself be highly available. This introduces failure classes that don't exist, or look very different, in classic Kafka.

**Object-storage regional outages / throttling.** A regional object-storage outage is existential in a design where object storage *is* the log, unless durability is explicitly engineered across regions. WarpStream's answer is to write each batch to **a quorum of three object-storage buckets across regions** before acknowledging, explicitly rejecting reliance on the cloud provider's own asynchronous cross-region replication, which they note completes "99.99% of objects... within 15 minutes" — far too slow to be a durability guarantee for an ack that must be given within the produce request's lifetime. On a full regional loss, WarpStream reports "a small latency spike of around 10 seconds" while automatic failover elects a new leader region, with "no data lost between the time the leader region was lost and the new leader region was elected," backed by a 99.999% multi-region-cluster uptime SLA (≈26s/month) ([No record left behind](https://www.warpstream.com/blog/no-record-left-behind-how-warpstream-can-withstand-cloud-provider-regional-outages)). Object storage **throttling** (e.g., S3 `503 SlowDown` responses under high per-prefix request rates) is a related, lower-severity but higher-frequency failure mode that the batching-for-fewer-larger-objects strategy (§2) also happens to mitigate structurally, since it reduces the raw PUT/GET request rate against the bucket compared to a naive per-record or per-partition object scheme.

**Metadata-store unavailability.** Because the metadata store is the actual linearization point for offset assignment (§1), its unavailability is more severe than an individual broker failing in classic Kafka — it can stall *all* writes cluster-wide rather than just the partitions one broker leads. WarpStream's mitigations layer three responses: (1) automatic, transparent replacement of failed metadata-store replicas without operator intervention, backed by multi-region strongly-consistent databases (DynamoDB Global Tables / GCP Spanner) so no single region's outage removes metadata durability ([WarpStream Architecture](https://docs.warpstream.com/warpstream/overview/architecture); [No record left behind](https://www.warpstream.com/blog/no-record-left-behind-how-warpstream-can-withstand-cloud-provider-regional-outages)); and (2) for the most extreme case, **Ripcord Mode**, which degrades gracefully rather than stopping — producers keep durably writing to object storage even while the control plane/metadata store is fully down, at the cost of consumers being blocked until the metadata store recovers and catches up on deferred sequencing ([WarpStream: Lazy(log)](https://www.warpstream.com/blog/the-art-of-being-lazy-log-lower-latency-and-higher-availability-with-delayed-sequencing)). This produces a durability model that is subtly different from Kafka's ISR contract: instead of "committed once replicated to N brokers," the effective contract becomes "durable once written to a quorum of object-storage regions" *plus* "visible/consumable once sequenced in the metadata store" — two separate commit points that can diverge in time under failure, whereas classic Kafka conflates durability and visibility into a single ISR-commit event.

**Partial batch failures.** Because a single flushed object interleaves records from many partitions/tenants (§2/§7), a failure partway through the write-then-commit sequence (object PUT succeeds but metadata commit fails, or vice versa) risks orphaned data (bytes durably in object storage but never referenced by any offset, effectively invisible and eventually garbage-collected) or, worse, a metadata entry pointing at an object that was never actually durably written. The systems reviewed handle this by making the **metadata commit the sole source of truth for visibility**: an object is not "real" from a consumer's perspective until its metadata entry is committed, so a failure after the object PUT but before the metadata commit simply results in an orphaned, never-referenced object that the garbage-collection/reconciliation sweep (§4) eventually reclaims — never in ordering or duplicate-visibility corruption ([Taking out the Trash](https://www.warpstream.com/blog/taking-out-the-trash-garbage-collection-of-object-storage-at-massive-scale)). The harder partial-failure case — an Agent crashing after a PUT succeeds but before it even attempts the metadata commit — is exactly what WarpStream's Lightning Topics "slow path" background scanner is designed to catch: it periodically scans object storage for files that were durably written but never got sequenced, and replays them into the metadata store, guaranteeing eventual sequencing without ever needing the original Agent to survive ([WarpStream: Lazy(log)](https://www.warpstream.com/blog/the-art-of-being-lazy-log-lower-latency-and-higher-availability-with-delayed-sequencing)).

**Opaque internal replication as a durability abstraction.** All of these systems ultimately delegate "how many physical copies, on how many physical disks, in how many failure domains" to the cloud provider's own internal replication for a *single* object-storage region/bucket, which is not configurable or observable by the Kafka-compatible layer above it. This is a genuine trust boundary shift versus classic Kafka, where the operator explicitly configures `min.insync.replicas` and directly observes ISR membership. The systems reviewed compensate for this loss of direct observability in different ways: WarpStream by adding its *own* explicit cross-region quorum on top of (rather than trusting solely) any single bucket's internal replication; Redpanda Cloud Topics by keeping the traditionally-observable Raft/ISR machinery local and only delegating the payload bytes to object storage, thereby limiting how much of the durability contract is actually delegated to the opaque layer; and AutoMQ similarly by requiring the WAL write (on an operator-visible, provider-SLA'd medium like EBS) to complete before acking, treating the eventual S3 upload as a secondary, already-durable copy rather than the primary durability event.
