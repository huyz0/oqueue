This file is a living tracker, not a finished research document. It exists because the research in `01`–`08` covers the general problem space (what WarpStream/AutoMQ/Redpanda/turbopuffer do, what Kafka-protocol-compatibility requires, what object storage guarantees, what Rust crates are available) — but several decisions can't be made until the user shares project-specific requirements, goals, and architectural preferences. This file is where those decisions land once made, and where the gaps are tracked until then.

## Not yet provided by the user (as of 2026-08-12)

- **Target workload / use case.** General-purpose Kafka replacement? Log/event ingestion specifically? Latency sensitivity requirements (is WarpStream-class p99 ~400ms–1s acceptable, or does this need AutoMQ/Redpanda-class single-digit-ms)?
- **Scale targets.** Expected throughput (MB/s or GB/s), partition count, tenant count, retention window.
- **Deployment model.** Self-hosted only? BYOC like WarpStream? Managed SaaS? Single-binary/single-node mode for small deployments (à la Tansu/s2-lite)?
- **Cloud provider scope.** S3 only, or S3+GCS+Azure from day one? (Affects whether to build on `object_store`/`opendal` vs. a provider-specific SDK — see [05-rust-ecosystem.md](05-rust-ecosystem.md) §1.)
- **Kafka compatibility bar.** Full protocol compatibility including transactions/EOS, or a pragmatic subset (produce/fetch/consumer-groups, defer transactions)? See [02-kafka-protocol-compatibility.md](02-kafka-protocol-compatibility.md) §1.6–1.7 for the minimum-viable-vs-full split.
- **License choice.** [07-licensing-strategy.md](07-licensing-strategy.md) lays out four strategies (Apache-2.0, open-core, BSL, AGPLv3) but makes no recommendation binding — this is the user's call given it's explicitly framed as "open source it."
- **Team size / velocity assumptions.** Solo project vs. planning for outside contributors from day one (affects CLA/DCO decision, [07](07-licensing-strategy.md) §6).
- **Metadata store preference.** External managed dependency (Postgres/DynamoDB/etcd) acceptable, or a strong preference for zero external dependencies (favoring the turbopuffer-style CAS-only approach, [08](08-turbopuffer-lessons.md) §4, accepting its throughput ceiling)?

## Architecture decisions this research sets up but does not make

These are the concrete decision points the next design doc (likely `11-architecture-decisions.md`, not yet written) needs to resolve, each with the relevant background already researched:

1. **Metadata/offset-sequencing approach** — external strongly-consistent store (WarpStream-style) vs. object-storage-native CAS (turbopuffer-style) vs. hybrid-local-consensus (Redpanda Cloud Topics-style). See [06-distributed-systems-design-challenges.md](06-distributed-systems-design-challenges.md) §1.
2. **Fast-path vs. no-fast-path for produce latency** — accept ~250ms–1s batching latency (WarpStream/KIP-1150 default) vs. add a local/attached-disk WAL for single-digit-ms acks (AutoMQ-style), with the attendant broker-affinity/failover complexity. See [06](06-distributed-systems-design-challenges.md) §2.
3. ~~**Storage-abstraction crate** — `object_store` vs. `opendal` vs. provider SDKs.~~ — **resolved 2026-08-16, `ADR-0008`: `object_store`.** `M1.15`-`M1.18` then built S3 and GCS on it and found the two limits the ADR did not predict, both recorded as their own ADRs: no public way to condition a `CompleteMultipartUpload` (`ADR-0013`) and no `copy_range` for either backend (`ADR-0015`). Original tradeoff table: See [05-rust-ecosystem.md](05-rust-ecosystem.md) §1 for the tradeoff table; current lean is `object_store` given its ecosystem gravity and native `PutMode` CAS support.
4. **Protocol layer** — build on the `kafka-protocol` crate vs. hand-roll. See [05](05-rust-ecosystem.md) §2 and [02](02-kafka-protocol-compatibility.md) §6.
5. **Idempotency/transactions strategy** — WarpStream's retroactive-tombstone approach (with its documented librdkafka compatibility gaps) vs. Redpanda's local-consensus approach vs. deferring transactions entirely for v1. See [06](06-distributed-systems-design-challenges.md) §6.
6. **License.** See above.
7. **Low-latency tier usage** — write straight to regional S3 Standard/GCS Standard (cheapest, ~400ms–1s p99, zero cross-AZ cost) vs. quorum-write across 2–3 S3 Express One Zone buckets for ~4x lower latency at the cost of reintroducing bounded cross-AZ transfer charges (`(RF−1) × cross-AZ-rate × ingested-bytes`) plus the Express storage premium on a transient buffer window. See [11](11-low-latency-tiers-and-interaz-costs.md) §6 and the four-option comparison in [17](17-latency-budget.md) §5. Note this decision is AWS/GCP-specific — Azure has no inter-AZ transfer fee at all, so the calculus changes there. **Working lean** ([17](17-latency-budget.md) §5): start S3-Standard-only and treat ~300–500ms p99 as the honest position, but make the tier pluggable so Express quorum is a config change rather than a rewrite. Blocked on the throughput target (#25).
25. **Aggregate throughput target** — still unspecified, and it gates #7 (whether the Express fast path is warranted), the shared-WAL sizing, and the active-working-set math in [15](15-scale-architecture-position.md) §1.
8. **Index granularity in the coordinator** — store full byte ranges centrally (fat index, 1 GET per fetch, WarpStream/KIP-1163 style) vs. object refs only with an in-object footer index resolving the range (lean index, 1–3 GETs cold, AutoMQ style) vs. the hybrid (fat for the tail window, lean for compacted history). This is bounded by index-size math (~14 GB/day uncompacted at the modeled workload), so it interacts with the compaction policy. See [12](12-object-discovery-and-api-cost.md) §6.3.
9. **Metadata distribution to readers** — push tail deltas to every agent via long-poll subscription (wiring into Kafka's existing `fetch.max.wait.ms`, so freshness costs zero added latency) vs. pull-per-fetch (WarpStream). Push-for-tail/pull-for-history is the working answer (see [12](12-object-discovery-and-api-cost.md) §4.4–4.5); what remains unmodeled is the **crossover point** — at what index size / partition count / agent-fleet size does broadcasting the tail delta to every agent stop being cheaper than per-fetch coordinator queries?
10. **Tail-path affinity policy** — soft partition→agent affinity is recommended in [12](12-object-discovery-and-api-cost.md) §4.5, but the concrete policy is open: what hash function, how sticky, how it interacts with Kafka's own consumer-group assignment and with zone alignment, and what triggers re-affinity after a failover.
11. **Bounded staleness limit** — the concrete value for `max_metadata_staleness`, which in turn sets the floor for `deletion_delay` in the GC safety inequality (`deletion_delay > bounded_staleness + max_fetch_duration + skew`). See [12](12-object-discovery-and-api-cost.md) §4.6 (hazard H4).
12. **Materialized-state engine** — SQLite (KIP-1164's choice; restore is `open()` not deserialization) vs. redb vs. RocksDB vs. fjall vs. SlateDB (object-storage LSM; near-instant open but 50–100ms cache-miss reads). **[13](13-coordinator-recovery.md) §6 recommends resolving this empirically**: fork `crates/redb-bench`, set key/value to our ~40-byte layout, fix its SQLite adapter to use WAL mode, and run the existing `insert_sorted` benchmark — the sequential-apply number that decides cold-start budget does not exist publicly for any of these engines.
13. **Snapshot cadence and trigger** — [13](13-coordinator-recovery.md) §5 argues for journal-volume-based (not wall-clock) triggering so RTO is load-independent, and for scheduling on completion+pause to avoid continuous-checkpointing lock-up. The concrete threshold is open; revealed preference across KRaft/etcd/openraft suggests a replay tail in the tens of MB.
14. **The enumeration fork** — WarpStream-style prefix-bounded recovery scanner (survives total coordinator outage, à la Ripcord, but does enumerate object storage) vs. AutoMQ-style `PREPARED`→`COMMITTED` controller state with expiry GC (zero enumeration, but coordinator is on the write critical path always, precluding a Ripcord mode). See [13](13-coordinator-recovery.md) §7. This decision is coupled to #7 (lazy sequencing): adopting Lightning-Topics-style ack-before-sequencing *requires* the scanner.
15. **Target RTOs** — [13](13-coordinator-recovery.md) §2 argues hot-standby failover and cold rebuild are separate numbers that should be designed and measured separately. Neither target has been set, and no peer system publishes a cold-rebuild figure to anchor against.
16. ~~**Active working set, not catalog size**~~ — **partially resolved 2026-08-13**, see [15](15-scale-architecture-position.md) §1. Target shape stated: tenant ≈ topic, 1M–100M topics, ≤1000 partitions each. Still needed: **the active fraction** (what proportion of topics are written to in a given window) and **median vs. max partitions per topic** — [15](15-scale-architecture-position.md) §5's sizing is sensitive to both.
17. **Tiered metadata — the design is validated, the open risk is named.** [14](14-metadata-scale-and-tiering.md) §1 finds both halves ship in production separately (Redpanda has derivable per-partition manifests; Kafka Diskless bounds coordinator state to the uncompacted window) but the combination is unbuilt. The one thing to probe: **why Redpanda Cloud Topics chose an LSM metastore for compacted L1 despite already owning derivable manifests** — undocumented, and the only evidence of someone well-positioned going the other way.
18. **Compaction cadence at high partition counts** — manifest PUT cost is linear in partitions × cadence and *fixed regardless of throughput* ([14](14-metadata-scale-and-tiering.md) §7): at 100k partitions, 60s cadence ≈ $720/day vs 30min ≈ $24/day. Interacts with #13 (snapshot cadence) and with read amplification. Also note GCS's ~1 CAS/s per object (vs S3's ~15) is a portability hazard for manifest updates.
19. ~~**Metadata-namespace sharding as the tenancy unit**~~ — **resolved 2026-08-13**, see [15](15-scale-architecture-position.md) §3. Metadata shards are **internal and rebalanceable**, not client-visible Virtual Clusters. The rebalanceability is what makes shard granularity an operational knob rather than a one-way door, and it removes the isolation-vs-batching tension.
20. ~~**Client-side protocol posture**~~ — **reframed 2026-08-13**, see [15](15-scale-architecture-position.md) §4. The answer is **principal-indexed metadata** (a `Metadata` request must cost O(topics this principal can see), never O(topics that exist)), not throttling `allTopics()`. With that in place the regex-subscription pathology stops mattering. **⚠️ This rests on an unverified claim about Kafka's authorization-filtering implementation — see [15](15-scale-architecture-position.md) §8.1.**
21. **Bootstrap and tenant routing at 1M–100M tenants** — you cannot enumerate endpoints in a load balancer. Working hypothesis in [15](15-scale-architecture-position.md) §9: shared bootstrap, tenant identified by SASL credentials, `Metadata` scoped to the authenticated principal. Not yet researched.
22. **Retention on idle partitions at scale** — time-driven retention must fire on partitions nobody writes to, a per-partition cost turbopuffer never pays ([14](14-metadata-scale-and-tiering.md) §9.2f). Candidates: lazy evaluation on next access, or folding into the daily reconciliation sweep. Neither worked through.
23. **Consumer-group state at 100M tenants** — one group per tenant is the natural pattern; the `__consumer_offsets` equivalent at that group count needs its own sizing.
24. **Topic deletion and name reuse** — turbopuffer allows immediate reuse because existence is just object presence; Kafka clients have topic-identity expectations (topic IDs, KIP-516) that may complicate it.
26. **Do our actual dependencies dispatch to AVX-512?** Unverified for `crc-fast`, `zstd`, and `lz4`. This decides whether the silent-wrong-answer failure mode in [18](18-rust-performance-methodology.md) §2.2 applies to us — under Valgrind, `is_x86_feature_detected!` returns false, so a dispatching dependency quietly benchmarks its fallback path. **Must be settled empirically before any gungraun number on a CRC or compression path is trusted.**
27. **CI hardware posture** — CodSpeed (free for public repos, instruction counts + bare-metal wall time, but vendor lock-in on performance history) vs. one self-hosted runner (eliminates the runner-heterogeneity class in [18](18-rust-performance-methodology.md) §2.4 entirely) vs. GitHub-hosted with pinned `target-cpu` and a pinned glibc container. Note GitHub-hosted runners have **no PMU** at all, so `perf`-based measurement is off the table there regardless.
28. **Regression thresholds** — [18](18-rust-performance-methodology.md) §7 suggests starting at `ir=1%` hard-fail with `@all=5%` warn and tightening toward 0.5% once the suite is stably green. Below ~0.5% you are detecting allocator and glibc drift rather than your own code. Needs calibration against real history.
29. ~~**`x86-64-v2` vs `v3` baseline**~~ — **resolved 2026-08-13**, see [20](20-build-and-release-portability.md) §5. **Ship one binary per `(os, arch)` at `x86-64-v2` / aarch64 `+lse,+crc`, everything above the baseline behind runtime dispatch.** It was never answerable alone: the baseline is a function of the artifact strategy. Since runtime dispatch is required anyway for CRC-32C (12 GB/s → 97 GB/s spread), raising the *static* baseline buys little and excludes users; v4 SIGILLs on modern consumer Intel.
30. **Allocator choice** — [18](18-rust-performance-methodology.md) §3.5 leans mimalloc with jemalloc feature-gated for heap profiling, but **snmalloc is unbenchmarked and its message-passing free design matches our allocation shape exactly** (network thread allocates a buffer, flush thread frees it). Worth one measurement. Secondary to buffer pooling either way.
36. **(encryption)** **Key rotation semantics** — when a customer rotates a KEK, existing wrapped DEKs stay valid under the old version. Re-wrap eagerly, during compaction, or never? Decides how long old KEK versions must be retained. See [22](22-encryption-byok-and-fips.md) §9.
37. **(encryption)** **Revocation behaviour** — a revoked KEK makes that topic's data unreadable *by design*. Fail fetches with a specific error, stall compaction, or tombstone? Must be defined before anyone relies on revocation.
38. **(encryption)** **DEK rotation constants** — [22](22-encryption-byok-and-fips.md) §5 requires both a time bound and a bytes-encrypted bound; neither has a value. ⚠️ The KMS budget is *not* the binding constraint at this volume, so derive them from the security argument — how much data may share one key — rather than from the quota.
39. **Does BYOK compose with cross-tenant compaction?** Compaction plans across objects; with key-domain segregation it must plan within a domain, and a revoked KEK blocks compaction of that topic's data.
41. **How much does segregation cost a small BYOK customer?** BYOK topics batch only within a key domain, so a customer with one low-volume topic produces small objects and pays more PUTs per byte. Unquantified: at what volume do PUT costs dominate, and is a longer flush interval adequate compensation?
42. **Should one-key-per-topic be offered?** At 10,000 BYOK topics the KMS headroom exists ([22](22-encryption-byok-and-fips.md) §3). Whether to expose it or require the KEK-per-customer hierarchy is a product decision with a support cost.
40. **Is a FIPS/non-FIPS differential suite worth two toolchains in CI?** The builds must agree byte-for-byte on anything both produce. ⚠️ Related and cheaper: the region header must name its AEAD algorithm **from its first commit**, or the two builds become mutually unreadable — a field now, a migration later. ⚠️ **CORRECTION (2026-08-16)** — this entry originally said "from M1". `M1` turned out to build only the object-storage seam (`put`/`get`/`delete` of opaque bytes); `oqueue-store` is architecturally unaware bytes are encrypted or structured at all (`architecture.md`'s Encryption section), so no region header exists for `M1` to add a field to. The object's internal structure — where a region header actually lives — is `M3`'s (multi-topic flush batching, FR-32), the first milestone that assembles a bundled object. The timing constraint this entry states is unchanged: whichever commit first defines that structure must include the field, or the migration this entry warns about happens anyway, just one milestone later than originally planned.
36. **(build)** ~~**Which TLS backend?**~~ — **resolved 2026-08-17, `ADR-0012`: `ring`** for the default build, with `aws-lc-rs` behind a `fips` feature for `M8`'s artifact only. ⚠️ **The reasoning below was considered and rejected**, so do not act on it: the ADR declines "match the FIPS build rather than diverge" precisely because `aws-lc-rs` needs CMake and Go, which NFR-42's "cargo and a C compiler" budget does not cover, for a compliance property doc 22 §8 puts at under 1% of deployments. ⚠️ `M1.42` then found the cost the ADR itself missed — `ring` still needs a **cross** `cc`, which broke the aarch64 check. Original tradeoff, superseded: `rustls` + `aws-lc-rs` (needs cmake) vs `ring` vs a pure-Rust provider; **partly resolved by the FIPS requirement**: `aws-lc-rs` is the only FIPS-140-3-validated path in Rust, so the FIPS build forces it and the default build should match rather than diverge. A **build-portability** decision as much as a crypto one — see [20](20-build-and-release-portability.md) §1, §9 and [22](22-encryption-byok-and-fips.md) §7 — and it belongs with [05](05-rust-ecosystem.md)'s crate selection.
37. **(build)** **Does `object_store`'s dependency tree cross-compile cleanly to aarch64-musl?** The four-way artifact matrix in [20](20-build-and-release-portability.md) §7 is asserted, not verified. ⚠️ ~~One CI run settles it; do it before the matrix is promised.~~ — **reframed by `M1.42`, and the answer for aarch64-gnu is already no.** That half was being checked by `m0-complete.sh` on every run, and `ADR-0012`'s `ring` broke it the day it landed: `ring`'s build script runs `cc` for the *target*, so `oqueue-store` needs `aarch64-linux-gnu-gcc`. Bisected — passes at `a961ae7~1`, fails at `a961ae7`, eighteen commits red before anyone read the gate. musl is strictly harder (no cross libc either). So the question is not "does it compile" but "which crates need a cross toolchain, and does the release path avoid needing one" — today's answer being that `portability.md` rule 9 builds natively. 38. **(build)** **glibc floor: 2.28 or 2.34?** 2.28 covers RHEL 8 (EOL 2029); 2.34 is freer if we don't intend to support it. A product decision. See [20](20-build-and-release-portability.md) §2.
31. **PGO in CI** — 14–36% measured on comparable workloads, but requires a representative produce/consume training load and real pipeline complexity. Open: what the training workload is, and whether profiles are regenerated per release or pinned. See [18](18-rust-performance-methodology.md) §3.3.
32. **Where DST sits in the crate graph** — `madsim` substitutes the async runtime at compile time (`--cfg madsim`), touching every crate that does async. Whether that composes with the sans-I/O split in [19](19-workspace-engineering.md) §4.1 — or partly subsumes it — needs a spike before committing. See [19](19-workspace-engineering.md) §11.
35. **Mutation-testing budget as the codebase grows** — diff narrowing bounds per-PR cost, but the nightly full run grows linearly (a workspace of this size reaches several thousand mutants, typically sharded four ways). At what point is the answer more shards versus a tighter crate list? See [19](19-workspace-engineering.md) §9.2.

## Log of resolved decisions

**2026-08-13 — Scale architecture working position.** Recorded in [15-scale-architecture-position.md](15-scale-architecture-position.md), the first document in this corpus stating our own design rather than surveying others. Reached through design discussion grounded in [12](12-object-discovery-and-api-cost.md), [13](13-coordinator-recovery.md), and [14](14-metadata-scale-and-tiering.md):

- **Target shape**: tenant ≈ topic; 1M–100M topics; ≤1000 partitions each. (resolves #16 partially)
- **Three-level structure**: internal metadata shard → topic (= tenant) → partition. Only the lower two are client-visible.
- **Metadata shards are internal and rebalanceable**, not client-visible Virtual Clusters — making shard granularity an operational knob rather than a one-way door. (resolves #19)
- **Principal-indexed metadata** is the load-bearing protocol requirement: a `Metadata` request must cost O(topics this principal can see), not O(topics that exist). (reframes #20)
- **Index granularity**: coarse coordinator index + in-object footer index, forced by the state arithmetic. (resolves #8)
- **Deployment**: co-located roles, no dedicated metadata tier; a subset of nodes carry metadata shards while the majority stay purely stateless. Single binary, roles by config.

**Status: working position, not a commitment.** Six items still need verification before any of it is settled — most importantly the assumption about Kafka's `Metadata` authorization-filtering implementation, which the whole design rests on. See [15](15-scale-architecture-position.md) §8.

**2026-08-13 — Rust performance methodology.** Recorded in [18-rust-performance-methodology.md](18-rust-performance-methodology.md). Four findings are settled enough to act on now, ahead of any code:

- **`crc32fast` is the wrong polynomial.** It implements CRC-32/IEEE; Kafka's v2 RecordBatch mandates CRC-32C (Castagnoli). No compile error, no runtime error — just batches every client rejects. Use `crc-fast` or `crc32c`, and design around `crc32c_combine` (deriving the CRC of `A‖B` in O(log n)) from the start, since re-batching for object-storage segments is intrinsic to the architecture.
- **Crate boundaries are optimization barriers**, so `lto = "thin"` is mandatory rather than marginal in a multi-crate workspace, and the true hot path (record-batch codec, CRC, varint, index lookup, buffers) should live in one crate. Two traps: `lto = false` + `codegen-units = 1` performs *no* LTO at all, and `cargo bench` inherits `release`, so the default setup benchmarks codegen that is never shipped. Five-profile `Cargo.toml` in §3.6.
- **Three benchmark suites, only one of which gates merges.** Valgrind cannot execute AVX-512 or SVE *and* misreports CPUID, so instruction counts and SIMD are structurally incompatible: gungraun `Ir` limits gate pure-CPU leaves on every PR; end-to-end and SIMD-dispatching paths are wall-time-on-quiet-hardware, report-only. Gating on a metric that cannot see the bottleneck trains people to ignore alerts.
- **The unsafe budget is three crates** (`oqueue-buf`, `oqueue-codec-core`, `oqueue-checksum`), everything else `#![forbid(unsafe_code)]`, and **never in the async/concurrency layer**. Grounded in a source study of Polars: bounds-check elimination is worth only 1–3%, and their 2026 soundness bugs cluster in **safe APIs failing to validate input**, not in unsafe blocks. Also falsifies 2 of the 5 claims in the widely-circulated video on the topic (§5.1).

Deferred to implementation time: allocator (#30), PGO (#31), `target-cpu` baseline (#29), CI hardware (#27). Also settled: **skip BOLT** (0.8–3%, aarch64 instrumentation broken) and **skip `build-std`**.

**2026-08-13 — Test infrastructure scoping: fakes and containers first, real cloud deferred.** Constraint: one WSL2 development machine (20 cores, 31 GB, 945 GB free) plus GitHub Actions. Decision:

- **T0/T1 (pure + hermetic fakes) and T2 (containerized MinIO/LocalStack) are in scope now.** T2 is *not* blocked — Docker Desktop is installed and needs only WSL integration enabled; it is also free on GitHub-hosted runners. The earlier framing of "limited to mocks" understated available capability.
- **T3 (real S3/GCS) is deferred**, pending cloud credentials. Cost is not the blocker; account setup is.
- **The conformance suite is written now, not deferred**, as backend-agnostic assertions with "which backends has this been run against" tracked as an explicit property. Deferring T3 then means *the suite has not been pointed at S3 yet*, not *tests do not exist*. Promoting it later is a config change.
- **macOS is dropped from the CI matrix for now** — [20](20-build-and-release-portability.md) §6 already scopes macOS as a development platform rather than a release target, and with no Mac available a macOS-only failure would have to be debugged blind through CI pushes. Revisit when a Mac-using contributor appears. **`ubuntu-24.04-arm` stays**: free, a real deployment target, and the only place aarch64 `+lse` codegen is exercised.

⚠️ **The risk this decision carries, and where it is tracked.** Conditional writes (`If-Match`/`If-None-Match`) are load-bearing for the CAS-based design in [08](08-turbopuffer-lessons.md), [12](12-object-discovery-and-api-cost.md), and [15](15-scale-architecture-position.md). If the in-memory fake and MinIO are both more permissive than real S3, the consequence is an architectural error rather than a test gap. Assertions are written to the documented semantics in [04](04-object-storage-s3-gcs.md) §6, which narrows residual risk to "does the implementation match its own documentation" — but **conditional-write behaviour stays marked unverified-against-real-S3 until T3 runs.** Tracked as #33.

**Consequence for #32:** deterministic simulation testing rises in priority. Without real-cloud testing, injected faults in a simulated store become the primary correctness mechanism rather than a supplement to it.

**2026-08-13 — Development methodology: spec-driven, fully AI-authored, direct-to-main.** Stated by the user; recorded here because it constrains the engineering practice in [19](19-workspace-engineering.md) and [20](20-build-and-release-portability.md).

- **Spec-driven development (SDD)**, sole developer, **no manually written code** — every line authored by an AI agent.
- **Commit directly to `main`** until the first release. Branching only on explicit request.
- **Build the development system in-repo rather than installing [Agent OS](https://buildermethods.com/agent-os/v2) or a comparable framework.** Agent OS v2's structure (Standards + Product + Specs) is a subset of what is needed, because it is a documentation and prompting system: nothing in it fails a build. The layer it lacks is enforcement, and the governing principle here is that *a rule with no gate is a preference*. Three further elements have no equivalent in the published frameworks — **executable milestone completion conditions** (a milestone's "done" must be a command, not a judgement, or it cannot be driven autonomously), the **decomposition rule** (only the current milestone is decomposed, because early decomposition produces tasks that are wrong by the time they are reached), and a **roadmap that records corrected beliefs** rather than mere completion. External maintenance, Agent OS's one advantage, is a liability here: updates would overwrite conventions deliberately chosen.

**Four adaptations the constraints force:**

1. **PR-triggered gates must become push-triggered.** Diff-narrowed mutation testing is conventionally run on pull requests; with direct-to-main it would never fire. Anything keyed to `origin/main...` needs rebasing onto the previous commit.
2. **Pre-commit is the gate; CI is the backstop.** With no branch protection and no review, a bad commit on `main` is immediately the state of the world. Non-negotiable #1 (*one task = one commit = one change that leaves the tree green*) already encodes this workflow, and small green commits make `git bisect` the sole developer's substitute for a reviewer.
3. **Claims must become artifacts.** Non-negotiable #3 — *"never claim a test passes without having run it… no script enforces this"* — is the acknowledged single point of failure, and a fully-AI-authored project leans on it harder than a human-written one. Mitigation follows the existing pattern (`mutants-baseline.txt`, `wired.txt`, coverage constants): **every claim that matters leaves an artifact a later run re-checks.** ⚠️ This supersedes **[18](18-rust-performance-methodology.md) §5.7**'s assumption of a human second reviewer for unsafe-block safety arguments (that document now carries a banner) — the role is filled by the isolated reviewer subagent in [21](21-ai-development-loop.md) §4–5.
4. **This research corpus is upstream of the product docs, not parallel to them.** [15](15-scale-architecture-position.md) → `mission.md` + `architecture.md`; [18](18-rust-performance-methodology.md)/[19](19-workspace-engineering.md)/[20](20-build-and-release-portability.md) → `standards/`; [10](10-open-questions.md) + [17](17-latency-budget.md) → `roadmap.md`.

**Design for the loop itself is now in [21](21-ai-development-loop.md)** — author/reviewer separation, the review artifact gate, gate allocation, and the anti-slop taxonomy.

**2026-08-13 — Encryption requirements: per-topic BYOK and a FIPS build.** Both optional; neither may burden deployments that do not use them. Design derived in [22](22-encryption-byok-and-fips.md).

- **Server-side encryption (SSE-KMS / CMEK) cannot satisfy this.** One object carries many tenants' data — that batching is what makes the cost model work — and an object can carry exactly one SSE-KMS key. The choice would be one key for every tenant in the object (not BYOK) or one object per topic (destroys batching). **Broker-side envelope encryption is therefore forced, not chosen**, and it has the side benefit of being identical on S3 and GCS.
- **Per-topic keys and multi-topic batching are reconciled by segregation, not by universal per-region sealing.** ⚠️ Also revised by the 10,000 figure. Sealing every region of every object independently works — the read path already issues ranged GETs — but pays object-format complexity on **100% of traffic to serve under 1% of it**. Instead an object is *either* a default-key object (the >99% path, unchanged) *or* a BYOK object holding only regions whose topics share one KEK. Regions inside a BYOK object are still sealed per topic, so a customer's topics stay isolated from each other. **Accepted cost: BYOK topics get worse batching efficiency**, since they can only batch within a key domain — the customer's trade to make, and one to state rather than absorb.
- **BYOK volume is ~10,000 topics out of 1M–100M**, clarified 2026-08-13 after the first draft. ⚠️ **This corrected a conclusion.** The initial analysis assumed BYOK might apply catalog-wide and concluded that AWS KMS's **100,000 customer-managed keys per region** made one key per topic impossible. At 10,000 topics the ceiling is **not binding** — and BYOK keys live in the customer's account anyway, so the quota applies per customer. The hierarchy (a topic names its KEK, several topics may share one, each topic keeps its own DEK) is still the recommendation, but it is now a **choice rather than a forced move**.
- **The portable seam is `wrap`/`unwrap`, not `generate_data_key`.** GCP Cloud KMS has no `GenerateDataKey` equivalent and documents generating DEKs locally. Building on AWS's richer API would produce an abstraction that leaks on GCP, so the seam is the intersection.
- ⚠️ **KMS must never sit on the per-batch path.** Crypto operations share a **5,500–10,000/sec per-account, per-region** quota. With cached DEKs and hourly rotation, 10,000 BYOK topics need ~3 KMS ops/sec — about 0.05% of the quota. Uncached, a call per flush per BYOK topic reaches the quota long before the topic count does, so it throttles at modest load rather than at scale. DEKs are cached per topic and rotated on time-or-bytes, mirroring S3 Bucket Keys, which cut KMS calls by up to 99%. **KMS availability consequently becomes a read-path dependency for cold BYOK data** — inherent to BYOK, but it belongs in the SLO rather than being discovered.
- **FIPS is a separate build** using `aws-lc-rs`'s validated module (AWS-LC-FIPS 4.x, certificate #4816). It requires **CMake, Go, and a C compiler** at build time, which independently justifies separation: [20](20-build-and-release-portability.md) §1 requires that `cargo build` need only cargo and a C compiler. FIPS also restricts the AEAD to AES-256-GCM (ChaCha20-Poly1305 is not approved) and mandates the validated DRBG for local DEK generation — the one place the two requirements interact.
- **New milestone M8** covers both, sequenced after the object format stabilizes. ⚠️ One thing must land earlier: the **region header names its AEAD algorithm from its first commit**, or FIPS and non-FIPS builds become mutually unable to read each other's data. ⚠️ **CORRECTION (2026-08-16)**: originally said "from M1"; item #40 above carries the full correction — the field's first commit is `M3`'s, not `M1`'s, since `M1` turned out to have no object format to carry it.
