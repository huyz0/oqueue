# turbopuffer: Engineering Lessons for Object-Storage-Native Log/Queue Systems

*Research compiled 2026-08-12 for engineers building a Kafka-compatible, S3-backed streaming/queue system in Rust.*

> **How this fits the project:** turbopuffer isn't a queue and isn't Kafka-compatible — it's included because its engineering writing is unusually candid and its coordination-without-consensus design (§4) is the single most directly transferable idea in this whole knowledge base. Read alongside [06-distributed-systems-design-challenges.md](06-distributed-systems-design-challenges.md) §1 (the metadata problem) and [04-object-storage-s3-gcs.md](04-object-storage-s3-gcs.md) §6 (conditional writes).

## Overview

turbopuffer is a serverless vector and full-text search database built "from first principles on object storage," founded by Simon Hørup Eskildsen (ex-Shopify Director of Engineering/Principal Engineer) in 2023 [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer). It stores all durable data in S3/GCS as the system of record, layering NVMe SSD and DRAM caches on top, and is written in Rust [Rust zero-cost abstractions vs. SIMD](https://turbopuffer.com/blog/zero-cost). It is directly relevant to a Kafka-on-object-storage design (in the WarpStream mold) because it solved a structurally similar problem — durable, cheap, multi-tenant storage of large, mostly-append data with strict cost targets — using conditional-write coordination on object storage instead of a consensus system, and it has documented this reasoning unusually explicitly on its blog. Notably, turbopuffer's engineers themselves draw the WarpStream/Kafka analogy on Hacker News: combining cheap object storage with hot local caches "mirrors successful patterns like Warpstream (using S3 instead of Kafka)" [HN discussion](https://news.ycombinator.com/item?id=40916786), and turbopuffer has published its own post on building a distributed queue on object storage, discussed in depth below.

## 1. Core Architecture: Compute/Storage Separation

turbopuffer's compute nodes are entirely stateless: "The API routes to a cluster of Rust binaries that access your database on object storage" [Architecture docs](https://turbopuffer.com/docs/architecture). All durable state lives in S3/GCS; any compute node can serve any tenant's data, since nothing but caches is pinned to a machine. The company's guiding design principle, attributed to painful on-call experience at Shopify, is explicit: "the fewer stateful dependencies, the more nines of uptime" [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer). This is described as "not tiering, where cold data is eventually replicated to object storage: it is an object-storage-first storage engine" — i.e., object storage isn't a cold archive bolted onto a hot database, it *is* the database, structured as an LSM tree [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer).

The caching hierarchy spans the full memory pyramid: "CPU registers → L3 cache → DRAM → NVMe SSD → S3 object storage" [ANN v3: 200ms p99 query latency over 100 billion vectors](https://turbopuffer.com/blog/ann-v3). Concretely: cluster centroids for vector search (tens of MB per active namespace) are kept resident in DRAM; a much larger working set is memory-mapped/cached on local NVMe SSD as a ring buffer; anything not cached falls back to a direct S3 read [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa). The NVMe cache is deliberately simple: described as "about 200 lines of code. No eviction heuristics. No LRU complexity" — implemented as a circular/ring buffer rather than a sophisticated cache-replacement policy [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa). Requests for a given namespace are consistently routed (via consistent hashing on the namespace key) to the same compute node to maximize cache locality — "subsequent queries are routed to the same query node for cache locality, but any query node can serve queries from any namespace" [Architecture docs](https://turbopuffer.com/docs/architecture). At their scale this consistent-hash routing operates across "200+ million namespaces in production" [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa).

Underlying storage economics: object storage costs roughly $0.02/GB versus $2–5+/GB for RAM and ~$0.60/GB for 3x-replicated SSD, which the company frames as "up to 100x cheaper than memory for cold storage, and 6–20x cheaper for warm storage" [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer); a separate podcast cites disk-based storage at ~$0.60/GB "accounting for replication and utilization" versus $0.02/GB for object storage, a 30x baseline improvement [How to build 10x cheaper with object storage](https://turbopuffer.com/blog/podcast-barrchives-podcast-how-build-10x-cheaper-object-storage). Simon Eskildsen has framed the enabling conditions historically: this architecture was only recently possible because "S3 became consistent in December 2020" (strong read-after-write consistency) and "NVMe SSDs weren't in the cloud until 2017" [Latent Space podcast](https://www.latent.space/p/turbopuffer) — i.e., turbopuffer is explicitly a bet on infrastructure primitives that didn't exist a decade earlier.

## 2. Write Path: Batching, WAL, and the Durable-vs-Queryable Gap

Writes do not go through an in-memory buffer that's later flushed lazily; every write is committed directly and durably to an object-storage-resident write-ahead log before being acknowledged: "Every write adds a new file to the WAL directory inside the namespace's prefix. If a write returns successfully, data is guaranteed to be durably written to object storage" [Architecture docs](https://turbopuffer.com/docs/architecture). The write path is described end to end as: API call → load balancer → group-commit buffer → WAL commit to S3 → cache update → enqueue indexing work [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa).

Because each S3 PUT costs on the order of 100–250ms, turbopuffer batches many logical writes into a single physical object-storage write via **group commit**: "whenever a write is in flight, we buffer incoming requests in memory. As soon as the write finishes, we flush the buffer as the next CAS write," explicitly compared to how "traditional databases also use this technique to coalesce `fsync(2)` calls to maximize the committed throughput to disk" [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue). Docs quantify the per-namespace throughput ceiling this creates: "each namespace can currently write 1 WAL entry per second. Concurrent writes to the same namespace are batched into the same entry" [Architecture docs](https://turbopuffer.com/docs/architecture). This is an explicit, accepted tradeoff: high per-write latency (100–250ms) in exchange for effectively unbounded aggregate throughput and much lower cost, because "writes take up to 200ms to commit" but the system supports "thousands of writes per second per namespace" [Tradeoffs docs](https://turbopuffer.com/docs/tradeoffs). One interview account put individual write latency at "200x slower than Postgres (~100 microseconds)," framing the system explicitly as "not an OLTP database. It's built for search workloads where writes are batched and reads are the bottleneck" [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa). Aggregate write throughput is claimed at "10M+ writes/s" platform-wide [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer), and one account cites "10+ million vectors per second write performance" [TurboPuffer: Object Storage-First Vector Database Architecture](https://jxnl.co/writing/2025/09/11/turbopuffer-object-storage-first-vector-database-architecture/).

**Durable ≠ indexed.** After the WAL commit succeeds (durability), the data still needs to be merged into the searchable index structures asynchronously: "After data is committed to the log, it is asynchronously indexed to enable efficient retrieval" [Architecture docs](https://turbopuffer.com/docs/architecture). To bridge this gap without giving up correctness, turbopuffer defaults to **strong consistency**: "if you perform a write, a subsequent query will immediately see the write" — achieved by having queries check for and linearly scan any not-yet-indexed WAL tail before returning, at a latency cost around p50=10ms / p90=17ms [Tradeoffs docs](https://turbopuffer.com/docs/tradeoffs). Applications that don't need this can opt into **eventual consistency**, which searches only "up to 128 MiB of unindexed data and tolerates staleness up to approximately one hour in worst cases," while noting that "over 99.8% of queries return consistent data even with eventual consistency" in practice [Concepts docs](https://turbopuffer.com/docs/concepts). This is a clean, explicit design lever for the durable-vs-queryable gap: correctness (scan the WAL tail) is preserved as the default, and a bounded staleness window is offered as an opt-in for lower latency, rather than either being forced globally.

## 3. Indexing Strategy: Building Indexes on Immutable Object Storage

turbopuffer runs two index types, both built as LSM trees rooted in object storage rather than as monolithic files that get rewritten wholesale.

**Vector search (ANN).** The vector index is centroid-based, based on Microsoft's SPFresh algorithm, described as maintaining "dynamic cluster balancing through incremental updates" so the index "avoid[s] periodic rebuilding" [Native filtering for high-recall vector search](https://turbopuffer.com/blog/native-filtering). New vectors are assigned to the nearest existing cluster, with clusters automatically split or merged to stay balanced, and updated cluster data is written back to S3 under CAS [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa). This was itself a hard-won architectural pivot: "the most critical optimization involved incremental index maintenance. The original approach required periodic full re-clustering, which became untenable at scale (tens of millions of vectors with high write throughput). V2 implemented an LSM-tree architecture on object storage with the SPFresh algorithm for continuous cluster optimization" [How to build 10x cheaper with object storage](https://turbopuffer.com/blog/podcast-barrchives-podcast-how-build-10x-cheaper-object-storage) — i.e., their first design didn't survive contact with real write volumes and had to be rebuilt around incremental, not full, index rebuilds.

The most recent iteration, ANN v3, scales this to 100 billion vectors (200TiB) at "200ms p99 latency" and "1,000+ QPS," using a wide (100x branching factor), shallow centroid tree so upper levels fit in DRAM by temporal locality while lower levels retain spatial locality on disk, bounding cold-query latency even on an S3 miss [ANN v3: 200ms p99 query latency over 100 billion vectors](https://turbopuffer.com/blog/ann-v3). It also applies binary quantization via the RaBitQ method for "16–32x compression," storing 1-bit-per-dimension vectors in the hot tiers and only fetching full-precision vectors for the top <1% of candidates [ANN v3: 200ms p99 query latency over 100 billion vectors](https://turbopuffer.com/blog/ann-v3). Engineers found their first bottleneck was disk bandwidth (~100 QPS), and only after quantization increased arithmetic intensity 64x did the bottleneck shift to CPU, at which point switching kernels to AVX-512 popcount gave a further ~5% throughput gain [ANN v3: 200ms p99 query latency over 100 billion vectors](https://turbopuffer.com/blog/ann-v3). Their stated meta-lesson from this work: "maximize the efficiency of a single machine before turning to distribution," to avoid overbuilding an unnecessarily expensive distributed system [ANN v3: 200ms p99 query latency over 100 billion vectors](https://turbopuffer.com/blog/ann-v3).

**Full-text search (BM25).** The inverted index is stored as key-value pairs mapping terms to posting-list *blocks* of a fixed target size (~256 postings), independent of document clustering, because block size has to simultaneously satisfy compression alignment (underlying bitpacking operates on 128-posting frames, so blocks are kept between 128–512 postings), query-time skippability with their vectorized MAXSCORE algorithm, and amortization of per-KV metadata overhead [Designing inverted indexes in a KV-store on object storage](https://turbopuffer.com/blog/fts-v2-postings). Posting lists are split/merged continuously as documents are upserted to keep blocks near target size, and "the LSM-tree naturally groups adjacent blocks into the same physical objects (files in S3), so queries can fetch multiple blocks in a single read operation" [Designing inverted indexes in a KV-store on object storage](https://turbopuffer.com/blog/fts-v2-postings). Compression uses a Rust port of Daniel Lemire's simdcomp bitpacking library (via Quickwit's crate), decoding roughly 741 million postings/sec on one core [Designing inverted indexes in a KV-store on object storage](https://turbopuffer.com/blog/fts-v2-postings). The FTS v2 rewrite, drawing architectural inspiration from Tantivy and Apache Lucene, cut on-disk index size by up to 10x and improved query latency up to 20x by letting queries "skip large chunks of unrelevant postings" [FTS v2: up to 20x faster full-text search](https://turbopuffer.com/blog/fts-v2). They also ported Lucene's MAXSCORE dynamic-pruning algorithm (over WAND) specifically because "agent-generated queries tend to be longer than typical human searches," and MAXSCORE "scales better than alternatives for long queries" [Vectorized MAXSCORE over WAND, especially for long LLM-generated queries](https://turbopuffer.com/blog/fts-v2-maxscore) — a workload-shape lesson: LLM/agent-driven traffic patterns (many more, longer queries) forced an algorithm change that pure human-search traffic wouldn't have.

**Compaction and background indexing as the log-compaction analogue.** Both index types are maintained via ongoing background split/merge/compaction jobs operating over LSM-structured object-storage files, functionally very close to log compaction in Kafka: old, small, or overlapping segments are periodically read, merged, and rewritten into fewer, larger, better-organized objects, while the system continues serving reads/writes against the pre-compaction state. Crucially, "any node can compact data" — compaction work is not pinned to an owner node, it's claimed via the CAS-based job queue described below, so a compactor dying mid-job doesn't require special failover logic, just re-claiming [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer) [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa).

## 4. Metadata/Consistency Layer: CAS Instead of Consensus

This is arguably turbopuffer's most transferable idea for a queue system, and they've written it up as a dedicated post, ["How to build a distributed queue in a single JSON file on object storage"](https://turbopuffer.com/blog/object-storage-queue).

The core primitive is **compare-and-set (CAS)** on a single object: a client GETs the object with its current ETag, mutates it locally, and PUTs it back with an `If-Match` condition on that ETag; if the object changed in between, the PUT fails with a 412 and the client retries [Amazon S3 adds new functionality for conditional writes](https://simonwillison.net/2024/Nov/26/s3-conditional-writes/) [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa). turbopuffer uses this to implement, among other things: a per-namespace indexing job queue (a `queue.json` file that pushers append jobs to and workers claim jobs from via CAS), leader/broker election (the current broker's address is itself stored inside `queue.json`, and a dead broker is detected via timeout and replaced by any node that wins the next CAS), and worker liveness (workers heartbeat a timestamp into the job record in `queue.json`; if it goes stale, another worker takes over) [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue).

Because CAS objects have a natural throughput ceiling — a single JSON blob can only be rewritten so many times a second (roughly "1 / ~200ms ≈ 5 writes/second," further capped by "the 1 RPS limit on GCS") — turbopuffer layers the same group-commit technique described in §2 on top of the metadata path itself: a stateless broker collects concurrent client requests in memory and performs a single CAS write per commit cycle "on behalf of *all* clients, so no one contends for the queue object" [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue). The redesign delivered "10x lower tail latency versus our prior implementation" [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue). The stated design philosophy is worth quoting directly, as it's a strong statement of engineering taste: "Because it's simple, predictable, easy to be on-call for, and extremely scalable. We know how it behaves, and as long as we design within those boundaries, we know it will perform" [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue).

The wider point, made repeatedly by Eskildsen, is that this whole coordination layer replaces what would otherwise require Raft/Paxos/ZooKeeper-class infrastructure: "No Raft. No Paxos. No Kafka" for internal coordination [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa). "For low-frequency coordination — indexing job dispatch, metadata updates, leader election — S3 CAS eliminates the need for a separate consensus system. Every node can be fully stateless, which is the unlock that makes the whole architecture possible" (search-result synthesis of turbopuffer's public statements) [S3 conditional writes / turbopuffer architecture](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa). This is also historically dated: Eskildsen notes S3 CAS only shipped in "late 2024" (November 2024, per AWS's own announcement) [Amazon S3 adds new functionality for conditional writes](https://simonwillison.net/2024/Nov/26/s3-conditional-writes/), and he frames it, alongside 2020's read-after-write consistency and cheap cloud NVMe (2017+), as one of exactly three storage-primitive preconditions that made turbopuffer's architecture buildable at all — a database company only being viable when "storage primitives (S3 + NVMe) unavailable to predecessors" newly exist [Latent Space podcast](https://www.latent.space/p/turbopuffer) [CMU Database Seminar](https://db.cs.cmu.edu/events/pg-vs-world-turbopuffer-simon-eskildsen/).

Above this low-frequency CAS coordination layer, per-namespace state (schema, index manifests, WAL pointers) is tracked via manifest files updated through the same CAS pattern (e.g. "Update manifest.json via CAS" after a WAL segment PUT) [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa), meaning there is no separate metadata database (no external Postgres/etcd/ZooKeeper) — object storage itself, accessed with conditional writes, *is* the metadata store.

> Compare against WarpStream's opposite choice — a heavyweight external metadata store (DynamoDB Global Tables/Spanner), see [01-warpstream-architecture.md](01-warpstream-architecture.md) §2 and [06-distributed-systems-design-challenges.md](06-distributed-systems-design-challenges.md) §1. turbopuffer's CAS-only approach works at its throughput ceiling (~5 writes/sec per hot object); a Kafka-scale metadata layer assigning offsets on every produce likely needs WarpStream's heavier approach, but turbopuffer's pattern is directly usable for lower-frequency coordination (leader election, compaction job claims, manifest updates) even in a design that also has an external metadata store for the hot offset-assignment path.

## 5. Multi-Tenancy: Cheap Isolation at Namespace Scale

Multi-tenancy is a foundational design axis, not an add-on. Each logical tenant/dataset is a **namespace**, and "each search namespace is simply a prefix on object storage" [How turbopuffer works synthesis](https://turbopuffer.com/blog/turbopuffer) — namespaces are implicitly created on first document insert, require no provisioning step, and carry effectively zero fixed cost when idle, since an unused namespace is just an (empty) S3 prefix, not a running process, shard, or allocated cluster [Concepts docs](https://turbopuffer.com/docs/concepts). Each namespace has its own isolated WAL, its own index structures, and its own S3 prefix [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa). This lets turbopuffer run "200+ million namespaces in production" [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa) with docs explicitly stating there is "no architectural constraint" on tenant count [Multi-tenancy / namespace search synthesis](https://turbopuffer.com/docs/concepts).

Because any stateless compute node can serve any namespace, but cache locality matters enormously for latency, routing uses **consistent hashing on the namespace key** so a given tenant is (almost) always served by the same node, keeping its cache warm without requiring dedicated/reserved capacity per tenant: "`hash("notion-acme-corp")` always hits Node 47… cache affinity. Same node every time means caches stay warm" [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa). Within a node, resource isolation across the many co-located tenants is enforced via custom user-space scheduling tracking "per-tenant consumption" of CPU, memory, NVMe, network, and S3 operations, following the stated principle that "every layer of complexity must be deserved" [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa) — i.e., they didn't reach for cgroups/VM-level isolation first; they built the minimum scheduling needed and only added more when a real noisy-neighbor problem justified it.

The company's own docs make the business case for this explicit: "turbopuffer is a multi-tenant service, which means each `./tpuf` binary handles requests for multiple tenants. This keeps costs low" [Architecture docs](https://turbopuffer.com/docs/architecture). A customer account (a legal-tech company migrating off OpenSearch) makes the cost-of-alternative concrete: "OpenSearch required minimum shards per namespace with fixed resource overhead, and with hundreds of customers needing isolated namespaces, costs scaled linearly with tenant count regardless of actual usage," which is precisely the "per-tenant infrastructure tax" that a namespace-as-prefix design avoids [Why we chose Turbopuffer for our search infrastructure — search-result summary](https://www.eve.legal/blog/engineering/why-we-chose-turbopuffer-for-our-search-infrastructure). Large customers reportedly run "millions of namespaces" simultaneously (cited for Notion) [TurboPuffer: Object Storage-First Vector Database Architecture](https://jxnl.co/writing/2025/09/11/turbopuffer-object-storage-first-vector-database-architecture/), with per-namespace sharding available to scale any single namespace up to 256TB when a tenant does grow very large [How turbopuffer works synthesis](https://turbopuffer.com/blog/turbopuffer).

## 6. Cost Model

turbopuffer publishes an explicit storage-cost comparison table contrasting its architecture against conventional in-memory/replicated-SSD vector database deployments [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer):

| Storage architecture | Cost / TB / month |
|---|---|
| RAM + 3x replicated SSD (typical incumbent) | $3,600 |
| RAM cache + 3x SSD | $1,600 |
| 3x replicated SSD (no RAM) | $600 |
| S3 + local SSD cache (turbopuffer) | $70 |
| S3 alone (no cache) | $20 |

This assumes roughly "50% disk utilization" and "50% in cache" for the warm-storage ($70/TB) figure [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer). Other primary/secondary sources converge on similar multiples: object storage at ~$0.02/GB versus ~$0.60/GB for 3x-replicated SSD (a ~30x gap) [How to build 10x cheaper with object storage](https://turbopuffer.com/blog/podcast-barrchives-podcast-how-build-10x-cheaper-object-storage), and a managed-vector-DB effective cost of "~$1.40/GB" (accounting for replicas and headroom) versus S3's "~$0.02/GB," a ~70x difference [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa).

Pricing to customers is pure usage-based: charges apply per GB-month of storage, per write, and per query, with `queried_bytes` billed on "the total size of the namespace being searched — all vectors plus all scalar attributes, every time you issue a query," plus tiered monthly minimums ($16/$256/$4,096 depending on tier) [turbopuffer Pricing summary](https://www.usagepricing.com/blueprint/turbopuffer). The original 2023 launch pricing was "$1 per month per million vectors and $4 per million queries," pitched as 10–70x cheaper than then-incumbent vector databases [Turbopuffer: $1/month per million vectors — HN](https://news.ycombinator.com/item?id=37932449). Simon Eskildsen has since admitted this initial pricing was essentially guesswork rather than grounded in a cost model — "vibe pricing" based on napkin math — and that running early large customers' workloads (Cursor) revealed real infrastructure costs diverged meaningfully from the original estimate, forcing rapid pricing and efficiency iteration [Latent Space podcast](https://www.latent.space/p/turbopuffer). More recently (April 2026) turbopuffer added a second pricing dimension, **namespace pinning**: tenants with sustained query volume above roughly 10 QPS can pin a namespace to reserved hot capacity and pay in GB-hours instead of per-query bytes, an acknowledgment that pure serverless/per-query billing doesn't fit consistently-hot tenants well [turbopuffer pricing search summary](https://www.usagepricing.com/blueprint/turbopuffer).

*Caveat/opposing view:* Competitor Zilliz has published a rebuttal arguing turbopuffer's storage-cost framing omits real operational costs (query-time compute, cache-miss variability, egress, and the cost of maintaining warm caches at scale), i.e., that "storage cost isn't the whole story" [Storage Cost Isn't the Whole Story — Zilliz](https://zilliz.com/blog/the-cost-of-consequence-what-no-one-tells-you-about-serverless-vector-databases). This is a vendor-interested source and should be read as one, but it is a reasonable caution that headline $/GB storage comparisons understate total cost of ownership, and is worth flagging in a technical design document as a debate rather than a settled fact.

## 7. Performance Characteristics

Two independent sets of published numbers exist (an earlier 2024 baseline from the founding blog post and docs, and later 2025–2026 posts describing v2/v3 systems), which differ somewhat — plausibly reflecting different benchmark datasets and generations of the storage engine, worth noting as such rather than treating as one single consistent number.

**Founding post (2024), 1M-document/vector scale** [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer):
- 1M 768-dim vectors (3GB): cold query 444ms p90; warm query 10ms p90
- 1M BM25 documents (300MB): cold query 285ms p90; warm query 18ms p90
- Query planning is deliberately bounded to a "maximum of three roundtrips [to object storage] for sub-second cold latency" — the query optimizer and storage engine "work in concert to strike a delicate balance between downloading more data per roundtrip, and doing multiple roundtrips" [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer).

**Docs page (current), 1M documents** [Architecture docs](https://turbopuffer.com/docs/architecture):
- Cold (uncached) query: p50 = 874ms
- Warm (cached) query: p50 = 14ms

## 8. Explicit Engineering Lessons, Tradeoffs, and Things They Got Wrong

turbopuffer is unusually candid, across blog posts and interviews, about design pivots and mistakes:

- **Full re-clustering didn't survive real write volume.** The original (v1) vector index required periodic full re-clustering; this "became untenable at scale (tens of millions of vectors with high write throughput)," forcing a v2 rewrite around an LSM-tree with SPFresh-style incremental clustering [How to build 10x cheaper with object storage](https://turbopuffer.com/blog/podcast-barrchives-podcast-how-build-10x-cheaper-object-storage).
- **Initial pricing was guesswork, not a cost model.** Eskildsen: launch pricing was "vibe pricing" based on napkin math; running Cursor's real workload exposed the gap between assumed and actual infrastructure cost and forced fast iteration [Latent Space podcast](https://www.latent.space/p/turbopuffer).
- **Agentic/LLM traffic broke query-shape assumptions.** Original design anticipated one retrieval call per LLM invocation; agents instead issue "parallel multi-query patterns," requiring architecture changes to absorb concurrent query bursts rather than steady, rationed calls [Latent Space podcast](https://www.latent.space/p/turbopuffer). This same shift (longer, more numerous LLM-generated queries) is what forced the MAXSCORE algorithm adoption for full-text search [Vectorized MAXSCORE over WAND](https://turbopuffer.com/blog/fts-v2-maxscore).
- **Zero-cost abstractions in Rust are not automatically fast in practice.** A concrete production incident: a customer's full-text query regressed to 220ms because a Rust iterator abstraction blocked the compiler from vectorizing/unrolling a hot loop across calls; switching to a batched-iterator pattern (512 KV pairs at a time — "the classic database technique") dropped it to 47ms, and a synthetic merge-iterator benchmark went from 6.5ms to 110 microseconds. Stated lesson: "production profiles trump theory and abstraction" [Rust zero-cost abstractions vs. SIMD](https://turbopuffer.com/blog/zero-cost).
- **Object-storage rate limits are a first-class design constraint, not an edge case.** A naive per-write CAS to a shared metadata object caps out at ~5 writes/sec (further bounded by GCS's 1 RPS object limit); this is why group commit had to be built into the metadata/coordination layer itself, not just the data write path [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue).
- **They deliberately chose simple, boring mechanisms for coordination.** Rather than build a bespoke consensus protocol, they explicitly chose "simple, predictable, easy to be on-call for" CAS-based coordination, accepting its throughput ceiling in exchange for operational predictability [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue).
- **Cross-cloud requirements were solved with unconventional infrastructure investment rather than compromising the architecture.** For a customer (Notion) needing turbopuffer compute in a different cloud/region than their own S3, turbopuffer purchased dark fiber between AWS Oregon and GCP, tuning TCP windows and absorbing egress costs, rather than deviating from the "one source of truth in object storage" design [Latent Space podcast](https://www.latent.space/p/turbopuffer).
- **Correctness measurement had to be continuous and production-based, not benchmark-based.** Rather than trusting academic ANN benchmarks, turbopuffer samples ~1% of production queries and compares results against exhaustive brute-force search on an ongoing basis to track real-world recall, because production filtering and high-dimensionality patterns aren't well represented in standard benchmark datasets [How to build 10x cheaper with object storage](https://turbopuffer.com/blog/podcast-barrchives-podcast-how-build-10x-cheaper-object-storage).
- **Workload shape (100:1 read:write) drove compaction/LSM layout decisions differently than a general-purpose database would.** turbopuffer engineers observed production read:write ratios near 100:1 for AI-retrieval workloads, "fundamentally different from traditional database workloads and requiring distinct compaction and LSM layout strategies" [How to build 10x cheaper with object storage](https://turbopuffer.com/blog/podcast-barrchives-podcast-how-build-10x-cheaper-object-storage).
- **A database company is only viable when new storage primitives exist that predecessors didn't have.** Eskildsen frames turbopuffer's founding thesis as requiring three preconditions simultaneously: a new workload (AI retrieval) that couldn't be served well by existing systems, new low-level storage primitives (S3 read-after-write consistency in 2020, cheap cloud NVMe from 2017, S3 CAS from late 2024) that predecessors lacked, and a willingness to eventually cover every query pattern customers need [CMU Database Seminar](https://db.cs.cmu.edu/events/pg-vs-world-turbopuffer-simon-eskildsen/) [Latent Space podcast](https://www.latent.space/p/turbopuffer).

## 9. Tech Stack

- **Language:** Rust, confirmed directly — turbopuffer's own performance-engineering post is framed entirely around Rust's compilation model, iterator abstractions, and how they map (or fail to map) to SIMD instructions on the target CPU [Rust zero-cost abstractions vs. SIMD](https://turbopuffer.com/blog/zero-cost). Docs also describe the API as routing to "a cluster of Rust binaries" [Architecture docs](https://turbopuffer.com/docs/architecture).
- **Storage backend:** Amazon S3 and Google Cloud Storage (multi-cloud support), used as an LSM-tree-structured storage engine where object storage is the literal source of truth, not a tiering target [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer).
- **Compression/encoding libraries:** A Rust port of Daniel Lemire's `simdcomp` C library, obtained via Quickwit's bitpacking crate, used to compress/decode BM25 posting lists (SIMD bit-packing over 128-posting frames), reaching ~741M postings/sec decode throughput on one core [Designing inverted indexes in a KV-store on object storage](https://turbopuffer.com/blog/fts-v2-postings).
- **Algorithmic influences (not necessarily shared code):** SPFresh (Microsoft) for the centroid-based, incrementally-updatable ANN index structure [Native filtering for high-recall vector search](https://turbopuffer.com/blog/native-filtering); Tantivy and Apache Lucene as architectural references for FTS v2's inverted-index design [FTS v2: up to 20x faster full-text search](https://turbopuffer.com/blog/fts-v2); MAXSCORE (from Lucene) adapted and vectorized for BM25 query pruning [Vectorized MAXSCORE over WAND](https://turbopuffer.com/blog/fts-v2-maxscore); RaBitQ for binary vector quantization with recall guarantees [ANN v3: 200ms p99 query latency over 100 billion vectors](https://turbopuffer.com/blog/ann-v3).
- **CPU-level optimization:** explicit SIMD usage, including AVX-512 popcount kernels for quantized vector distance computation, and manual attention to compiler auto-vectorization boundaries around iterator abstractions [Rust zero-cost abstractions vs. SIMD](https://turbopuffer.com/blog/zero-cost) [ANN v3: 200ms p99 query latency over 100 billion vectors](https://turbopuffer.com/blog/ann-v3).
- **Coordination primitive:** S3/GCS conditional writes (CAS via ETag/`If-Match`, or GCS generation preconditions) used for all cross-node coordination — job queues, leader election, manifest updates — in place of Raft/Paxos/ZooKeeper/etcd [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue) [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa).
- turbopuffer is closed-source/commercial-only by explicit choice — they "rejected free tiers and open-source distribution to maintain high-quality support and rapid development" [Tradeoffs docs](https://turbopuffer.com/docs/tradeoffs) — so no source code is available to verify implementation details beyond what's disclosed in blog posts/docs; an "Ask HN: Is there an open source turbopuffer?" thread confirms the community also doesn't have access to internals beyond what's published [Ask HN: Is there an open source "turbopuffer"?](https://news.ycombinator.com/item?id=46318635).

## 10. Lessons for Building a Kafka-Compatible Queue on Object Storage

Translating the above into implications for a Rust, S3-backed, Kafka-compatible log/queue system (WarpStream-style):

- **Make object storage the single source of truth for both data and metadata, and use conditional writes (S3 CAS / GCS generation preconditions) as your only coordination primitive** for partition-leader election, controller/broker liveness, and segment-manifest updates — this eliminates the need to run and operate a separate Raft/ZooKeeper/etcd cluster, mirroring turbopuffer's "no Raft, no Paxos" stance [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue). Just budget for the CAS-object throughput ceiling (~5 writes/sec on a single hot object, tighter still under GCS's 1 RPS-per-object limit) — this is a hard constraint, not a tuning knob.

- **Layer group commit on top of both the data write path and the metadata/coordination path.** turbopuffer batches concurrent producer writes into a single S3 PUT per commit cycle *and* separately batches concurrent metadata updates into a single CAS write per cycle via a stateless broker. A Kafka-on-S3 design should do the same for partition offset/segment-manifest commits, not just for record batches — otherwise the metadata layer becomes the bottleneck even after the data layer is optimized [How to build a distributed queue in a single JSON file on object storage](https://turbopuffer.com/blog/object-storage-queue).

- **Explicitly separate "durable" from "consumable/indexed," and expose the tradeoff to the client rather than hiding it.** turbopuffer's default (scan the WAL tail synchronously for strong consistency) plus an opt-in eventually-consistent fast path is a good template: durability (WAL/segment committed to S3) should be near-immediate and always synchronous, while "queryable/indexed" (e.g., consumer-visible offset advancement, compacted views) can lag slightly, with the lag bounded and the client able to choose stronger consistency at a latency cost when it matters [Tradeoffs docs](https://turbopuffer.com/docs/tradeoffs) [Concepts docs](https://turbopuffer.com/docs/concepts).

- **Treat compaction/segment-merging exactly like turbopuffer's index compaction: ownerless, CAS-claimed background jobs that any stateless node can pick up.** This directly generalizes to Kafka log compaction and segment coalescing on object storage — a dead compactor is just a stale CAS claim that another node retakes, with no special failover machinery needed [turbopuffer: fast search on object storage](https://turbopuffer.com/blog/turbopuffer).

- **Design segment/block sizing around both the compression codec's natural frame size and the read-amplification cost of small objects**, the way turbopuffer tuned posting-list blocks to ~256 postings to straddle bitpacking's 128-posting frames while amortizing per-object metadata overhead. For a Kafka-like system this argues for choosing batch/segment sizes that are large enough to amortize S3 GET/PUT overhead and small enough to bound read amplification on partial reads, and revisiting that size as codecs change [Designing inverted indexes in a KV-store on object storage](https://turbopuffer.com/blog/fts-v2-postings).

- **Make per-tenant/per-topic-partition cost genuinely proportional to usage, not to provisioned capacity, by keying tenancy off object-storage prefixes rather than dedicated shards/processes.** turbopuffer's "namespace = S3 prefix, created implicitly, zero cost when idle" model is the direct analogue of wanting many small Kafka topics/partitions to cost near-zero when idle instead of each consuming a slice of a fixed broker/shard allocation — this is precisely the customer-articulated pain (OpenSearch's "minimum shards per namespace... costs scaled linearly with tenant count regardless of actual usage") that a prefix-based design avoids [Why we chose Turbopuffer](https://www.eve.legal/blog/engineering/why-we-chose-turbopuffer-for-our-search-infrastructure).

- **Use consistent hashing to route a given tenant/topic-partition to the same compute node for cache locality, while keeping every node able to serve every tenant/partition.** This gets you both good warm-cache hit rates (most traffic to a stateless node hits its own local NVMe cache) and instant failover (any other node can cold-load the same partition from S3 with a one-time latency penalty, no data movement or replica catch-up required) — directly addressing the classic Kafka pain point where "broker loss can mean replica catch-up" and "partition growth can become a data movement project" [WarpStream vs AutoMQ comparison](https://www.automq.com/blog/warpstream-vs-automq-object-storage-backed-kafka).

- **Keep the local cache dead simple (a ring buffer, no LRU) unless production data proves you need more.** turbopuffer's ~200-line eviction-free NVMe ring buffer, justified by the principle "every layer of complexity must be deserved," is a useful default for a queue's local read cache too, since log/queue access patterns (recent-offset-heavy, sequential) are often well served by a simple ring buffer without full LRU machinery [How Turbopuffer Serves 2.5 Trillion Vectors on S3](https://ajay-edupuganti.medium.com/how-turbopuffer-serves-2-5-trillion-vectors-on-s3-7d7ab7f9a7fa).

- **Expect the first version of any index/log-layout scheme to not survive real production write volume, and design for a rewrite.** turbopuffer's v1→v2 index rewrite (full periodic reclustering → incremental LSM-based clustering) is a direct warning: whatever segment/index layout scheme is designed on paper for a Kafka-on-S3 system should be validated against realistic sustained write throughput early, because the mode that looks fine in a demo (batch rebuild) is very likely to become untenable at scale, the same way it did for turbopuffer [How to build 10x cheaper with object storage](https://turbopuffer.com/blog/podcast-barrchives-podcast-how-build-10x-cheaper-object-storage).

- **Instrument and continuously validate correctness/consistency against production traffic, not just synthetic benchmarks**, and be prepared for LLM/agentic-style traffic (bursty, higher concurrency, larger fan-out per logical operation) to break assumptions baked in from more traditional workload modeling — turbopuffer had to redesign around agentic query bursts it hadn't originally planned for, and a queue system serving AI-pipeline workloads should expect analogous producer/consumer burstiness rather than assuming steady, well-behaved traffic [Latent Space podcast](https://www.latent.space/p/turbopuffer).
